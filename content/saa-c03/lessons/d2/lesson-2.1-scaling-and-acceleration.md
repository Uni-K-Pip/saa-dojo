アクセスが急に増えても遅くならず、減ったら無駄な料金を払わない。これがスケーラブルな設計の目標です。このレッスンでは、各部品をどう増減させるか（スケーリング）と、データを利用者の近くや速い場所に置いて速くする方法（キャッシュとエッジ）を学びます。キューやイベントで部品を切り離す方法は、別のレッスン「疎結合とメッセージング」で扱います。

## 基礎

### 垂直スケーリングと水平スケーリング

- **垂直スケーリング（スケールアップ）**: 1 台のサーバーを、より大きなインスタンスタイプに替えます。サイズに上限があり、変更時に停止が必要で、1 台が止まれば全体が止まります。
- **水平スケーリング（スケールアウト）**: 同じ構成のサーバーを台数で増やし、ロードバランサーで振り分けます。上限が高く、一部が壊れても動き続けます。

AWS の設計では、水平スケーリングが基本です。ただし、台数を自由に増減するには、サーバーを**ステートレス**（セッションなどを自分で持たない状態）にし、セッションは ElastiCache や DynamoDB などの外部に置きます。

### キャッシュの考え方

キャッシュは、一度取得したデータを速い場所に置き、次の同じ要求に素早く答える仕組みです。元のデータストアの負荷も減ります。同じデータが何度も読まれる場面に効きます。

## 使い分け

### EC2 Auto Scaling のスケーリングポリシー

Amazon EC2 Auto Scaling は、Auto Scaling グループ（最小・希望・最大の台数を決めたインスタンスの集まり）の台数を自動で増減します。インスタンスの作り方は**起動テンプレート**で定義します（古い起動設定は使いません）。

| ポリシー | 動き | 向く場面 |
|---|---|---|
| ターゲット追跡 | 指標を目標値に保つように台数を調整する（サーモスタットのイメージ） | 負荷が読めない。最初に選ぶ標準 |
| ステップ | しきい値を超えた度合いに応じて、増減する台数を段階的に決める | 細かく制御したい |
| スケジュール | 決めた日時に最小・最大・希望の台数を変える | 時刻と規模が決まっている増加 |
| 予測 | 過去の負荷の日次・週次のパターンから先読みして台数を増やす | 周期的な負荷、起動に時間がかかるアプリ |

ターゲット追跡の定義済みの指標には、グループの平均 CPU 使用率、ネットワークの入出力、ターゲットあたりのリクエスト数（ALBRequestCountPerTarget）があります。起動に時間がかかるときは、ウォームアップ時間を設定します。

### コンテナのスケーリング

コンテナを管理する仕組み（オーケストレーター）には 2 種類あります。

- **Amazon ECS**: AWS 独自のサービスで、Kubernetes を知らなくても使えます。
- **Amazon EKS**: マネージドの Kubernetes です。既存のマニフェストや Helm チャートを活かせます。

コンテナを動かす土台は 2 つから選びます。**EC2** は自分でインスタンスを管理し、細かい設定ができます。**AWS Fargate** はサーバーレスの土台で、インスタンスの管理が不要です。ECS でも EKS でも使えます。

ECS のサービスは、Application Auto Scaling で「タスクの数」を増減します（ポリシーの種類は EC2 Auto Scaling と同様です）。EKS ではポッドの数を Horizontal Pod Autoscaler などで増減し、ノードは Karpenter や Cluster Autoscaler が増減します。

### Lambda とサーバーレスのスケーリング

AWS Lambda は、同時に来たリクエストの数だけ実行環境を自動で増やします。台数の管理は不要で、覚えるのは**同時実行**の考え方です。

- 同時実行数は、おおよそ「1 秒あたりのリクエスト数 × 1 件の処理時間（秒）」です。
- 同時実行数にはアカウント・リージョンごとのクォータがあり、足りなければ引き上げを申請します。超えると、リクエストはスロットリング（拒否）されます。
- **予約された同時実行**: 関数に同時実行数を確保し、同時にその関数の上限にもなります。ほかの関数に枠を奪われず、下流のデータベースを圧迫しすぎることも防げます。追加料金なしです。
- **プロビジョニングされた同時実行**: 実行環境をあらかじめ初期化し、コールドスタート（初回の起動待ち）を避けます。追加料金がかかります。
- 1 回の実行は、通常の関数では最長 15 分です。これを超える処理は Fargate などに向きます。

### データベースのスケーリング

| 対象 | 読み取りを増やす | 書き込みを増やす |
|---|---|---|
| Amazon RDS | リードレプリカを手動で作成（非同期の複製） | インスタンスの大型化（垂直）が基本 |
| Amazon Aurora | Aurora レプリカ（最大 15 個）をリーダーエンドポイントで分散。Aurora Auto Scaling で自動増減 | ライターは 1 つ。大型化、または Aurora Serverless v2 で容量を自動調整 |
| Amazon DynamoDB | オンデマンドモード、またはプロビジョニングモード＋Auto Scaling | 同左（パーティションキーの設計が前提） |

- **リードレプリカ**は、レポートや分析のような重い読み取りを本番から切り離すために使います。複製は非同期なので、わずかな遅れ（レプリカラグ）があります。Multi-AZ のスタンバイは可用性のためのもので、読み取りには使えません。
- **Aurora Serverless v2**（公式ドキュメントでは「Aurora serverless」）は、容量（ACU）を負荷に合わせて自動調整します。
- **DynamoDB のオンデマンドモード**は、容量の見積もりが不要で、予測できない急増に強い選択です。負荷が安定して読めるなら、プロビジョニングモードで費用を抑えられます。
- **RDS Proxy** は、データベースへの接続をまとめて使い回します。Lambda のように接続が急増しやすい場面で、接続数の枯渇を防ぎます。接続の管理機能で、クエリ結果はキャッシュしません。

### キャッシュ・エッジによる高速化

| サービス | 何を速くするか | 要点 |
|---|---|---|
| Amazon CloudFront | 静的・動的コンテンツの配信 | 世界のエッジロケーションにキャッシュ。オリジンは S3、ALB、独自の HTTP サーバーなど |
| AWS Global Accelerator | TCP/UDP のアプリへの接続 | 固定のエニーキャスト IP（2 つ）から AWS のネットワークに入り、正常なリージョンのエンドポイントへ。キャッシュはしない |
| S3 Transfer Acceleration | 遠方から S3 バケットへのアップロード | 専用エンドポイントに送ると、近くのエッジ経由で S3 へ |
| Amazon ElastiCache | データベースの読み取りやセッション、ランキング | インメモリのキャッシュ。Valkey、Redis OSS、Memcached。サーバーレスもある |
| DynamoDB Accelerator（DAX） | DynamoDB の読み取り | DynamoDB 用のインメモリキャッシュ。結果整合性の読み取りが対象 |

S3 バケットを非公開のまま CloudFront から配信するには、オリジンアクセスコントロール（OAC）を使います。1 つのディストリビューションで、パスごとにオリジンとキャッシュの動作を分けられます（静的ファイルはキャッシュ、API はキャッシュしない、など）。

ElastiCache のうち、Redis OSS と Valkey はレプリケーション、Multi-AZ、ソート済みセットがあり、セッションやランキングに向きます。Memcached は単純なキャッシュ向きです。

## 設計パターン

### 予測できる急増と予測できない急増を組み合わせる

毎朝同じ時刻に始まる急増には、スケジュールされたアクション（または予測スケーリング）で先に台数を増やします。インスタンスの準備に 10 分かかるなら、その分早めに増やします。日中の読めない急増にはターゲット追跡を併用し、データベースの読み取りは Aurora Auto Scaling でレプリカを増減します。

### キャッシュの戦略

- **遅延読み込み**: 読み取り時にキャッシュになければデータベースから読み、キャッシュに書きます。要求されたデータだけが入るので無駄がなく、キャッシュノードが空になっても動き続けます。ただし、データベースが更新されても古い値が残ります。
- **書き込みスルー**: データベースを更新するときにキャッシュも更新します。常に新しいデータですが、読まれないデータも入ります。
- **TTL（有効期限）**: どちらの戦略にも付けます。古いデータが残り続けることと、読まれないデータが貯まることを防ぎます。

### 世界の利用者に速く届ける

静的ファイルは S3 に置いて CloudFront で配信し、API もパスを分けて同じ CloudFront から出します。毎回最新の応答が必要なパスはキャッシュしません。TCP/UDP の独自プロトコルや固定 IP アドレスが必要なら Global Accelerator を選びます。

## 試験のポイント

> **試験のポイント**
> 「予測できない負荷への自動対応」は、ALB と複数 AZ の Auto Scaling グループ（ターゲット追跡）。「毎日同じ時刻の急増」は、スケジュールまたは予測です。

> **試験のポイント**
> 「サーバーの管理をしない」「利用量に応じた課金」「実行時間が短い」は Lambda。「15 分を超える」「特定のライブラリに依存する」「コンテナ化済み」は Fargate です。既存の Kubernetes 資産があれば EKS、なければ ECS です。

> **試験のポイント**
> 「重い読み取りを本番から切り離す」はリードレプリカ。「繰り返し読まれるデータを高速に」は ElastiCache（DynamoDB なら DAX）。「世界中の利用者に静的ファイルを近くから」は CloudFront、「遠方から S3 へのアップロード」は S3 Transfer Acceleration です。

## ひっかけ注意

> **ひっかけ注意**
> ターゲット追跡の指標に、ロードバランサーの総リクエスト数（RequestCount）は使えません。インスタンス 1 台あたりの負荷を表す「ターゲットあたり」の値（ALBRequestCountPerTarget）を使います。

> **ひっかけ注意**
> リードレプリカで増やせるのは読み取りだけです。書き込みの増加には効きません。RDS のリードレプリカは自動で増減せず、Aurora のレプリカは Aurora Auto Scaling で増減できます。

> **ひっかけ注意**
> CloudFront と Global Accelerator は別物です。キャッシュで速くするのは CloudFront、キャッシュせずに AWS のネットワークと固定 IP で経路を速く安定させるのは Global Accelerator です。S3 は Global Accelerator のエンドポイントにできません。

> **ひっかけ注意**
> Lambda の「予約された同時実行」は確保と上限で、コールドスタート対策ではありません。避けるのは「プロビジョニングされた同時実行」です。
