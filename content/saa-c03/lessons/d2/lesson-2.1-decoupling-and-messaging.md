システムの部品どうしが直接つながりすぎていると、1か所の不調や急な負荷が全体に広がります。このレッスンでは、部品の間にキュー、トピック、イベントバスなどを置いて、互いの状態に左右されにくい構成（疎結合）にする方法を学びます。

## 基礎

### 同期の呼び出しの弱点

注文を受け付けたアプリケーションが、続けて在庫システムの API を直接呼び、その結果を待つ構成を考えます。

- 在庫システムが止まると、注文の受け付けまで失敗する。
- 注文が急に増えると、在庫システムが処理しきれずに全体が遅くなる。
- 呼び出し先が増えるたびに、呼び出し元のコードを変える必要がある。

疎結合では、間に仲介役を置いて「送る側」と「処理する側」を切り離します。送る側は仲介役に渡せば完了し、処理する側は自分のペースで取り出します。処理の失敗や停止が送る側に伝わらず、処理側だけを増減できるのが利点です。ステートレスな処理側（状態を持たず、どのインスタンスでも同じように処理できる）にしておくと、台数を増やしやすくなります。

### 3つの切り離し方

| 方式 | 仕組み | 代表サービス |
|---|---|---|
| キュー | 送った側と処理する側が1対1。メッセージは処理されるまで溜まる | Amazon SQS |
| パブリッシュ／サブスクライブ | 1つのメッセージを複数の購読者へ配る（ファンアウト） | Amazon SNS |
| イベントバス | イベントの内容を見て、ルールに合う宛先へ振り分ける | Amazon EventBridge |

これに加えて、複数の処理の順序や分岐を管理する AWS Step Functions と、外部にAPIを公開する Amazon API Gateway があります。

## 使い分け

### Amazon SQS

SQS はフルマネージドのキューです。送る側と処理する側は、互いの存在も速度も知る必要がありません。

| | 標準キュー | FIFO キュー |
|---|---|---|
| 配信 | 少なくとも1回（重複しうる） | 送信時の重複を排除（重複排除の期間は5分） |
| 順序 | ベストエフォート | メッセージグループ ID ごとに保たれる |
| スループット | ほぼ無制限 | 上限がある（高スループットモードで引き上げられる） |
| 向く場面 | 大量処理、順序が不要 | 順序が重要、二重送信を避けたい |

押さえておく設定は次のとおりです。

- **可視性タイムアウト**: 取り出されたメッセージが、ほかの処理側から見えなくなる時間。既定は 30 秒、最大 12 時間。処理にかかる最大時間より長くしないと、処理中に別の処理側へ渡って二重に処理される。
- **メッセージの保持期間**: 既定は 4 日。1 分から 14 日まで設定できる。
- **メッセージの大きさ**: 最大 1 MiB。大きなデータは S3 に置き、メッセージには場所だけを入れる。

### デッドレターキュー（DLQ）

何度処理しても失敗するメッセージが、キューに居座って後続を遅らせたり、延々と再試行されたりすることがあります。**DLQ** は、そうしたメッセージを隔離する別のキューです。元のキューにリドライブポリシーを設定し、`maxReceiveCount` 回受信されても削除されなかったメッセージを DLQ へ移します。DLQ は元のキューと同じアカウント・同じリージョンに置きます。

DLQ に入ったメッセージは原因を調べ、直したあとで元のキューへ戻す（リドライブ）ことができます。DLQ の保持期間は、元のキューより長くします。標準キューでは、メッセージの期限が最初にキューへ入った時刻から数えられ、DLQ に移しても延びないためです。

### Amazon SNS

SNS は、トピックにメッセージを発行すると、購読者全員へ配る仕組みです。購読者には、SQS キュー、Lambda 関数、HTTP(S) エンドポイント、Amazon Data Firehose のほか、メール、SMS、モバイルプッシュ通知も選べます。購読者ごとにフィルターポリシーを設定すると、条件に合うメッセージだけを受け取らせることもできます。

SNS は受け取った相手に送り届ける仕組みで、購読者が止まっている間のメッセージを自分では溜めません。そのため、止まる可能性のある処理系へ確実に渡したいときは、SNS の宛先を SQS キューにします。

FIFO トピックと SQS FIFO キューを組み合わせると、順序と重複排除を保ったままファンアウトできます。

### Amazon EventBridge

EventBridge は、イベントを受け取り、ルールに合う宛先（ターゲット）へ届けるサーバーレスのサービスです。

- AWS サービスが出すイベント、自社アプリのカスタムイベント、SaaS などのサードパーティのイベントを、1つのバスに集められる。
- ルールはイベントの内容（イベントパターン）で振り分け、1つのイベントを複数のターゲットへ渡せる。
- EventBridge Scheduler で、cron 式や一度きりの予定時刻に処理を起動できる。
- EventBridge Pipes は、1つのソース（SQS など）から1つのターゲットへ、加工をはさんで直接つなぐ。

カスタムイベントバスには従来型（Classic）と新しい形式がありますが、試験では「ルールで振り分ける」役割を押さえれば十分です。

### SNS と EventBridge の違い

| 観点 | Amazon SNS | Amazon EventBridge |
|---|---|---|
| 主な役割 | 同じメッセージを購読者全員へ配る | 内容を見て宛先を選んで届ける |
| 振り分け | 購読ごとのフィルターポリシー | バスのルールとイベントパターン |
| 得意な相手 | 人への通知（メール、SMS、プッシュ）と、SQS・Lambda への配布 | AWS サービスや SaaS のイベントへの反応、スケジュール実行 |

### AWS Step Functions

Step Functions は、Lambda などの処理を順番、分岐、並列、待機で組み合わせるワークフローを、サーバーなしで作れるサービスです。Retry で再試行、Catch で失敗時の分岐を書けます。

| | 標準ワークフロー | Express ワークフロー |
|---|---|---|
| 最長実行時間 | 1 年 | 5 分 |
| 実行の保証 | 実行はちょうど1回 | 非同期は少なくとも1回、同期は最大1回 |
| 向く場面 | 長時間、人の承認待ち、決済のような繰り返せない処理 | 大量・短時間のイベント処理 |
| コールバック（タスクトークン）、`.sync` | 使える | 使えない |

### Amazon API Gateway

API Gateway は、HTTP の API を公開・管理するサービスです。裏側は Lambda や EC2、ALB などで、キューへ直接つなぐこともできます。

| | REST API | HTTP API |
|---|---|---|
| API キー、使用量プラン（利用者ごとの制限） | 使える | 使えない |
| キャッシュ、リクエストの検証 | 使える | 使えない |
| AWS WAF の連携、プライベートエンドポイント | 使える | 使えない |

API キーや使用量プランは利用者の識別と利用量の制御用で、認証・認可の代わりにはなりません。認可には IAM、Lambda オーソライザー、Amazon Cognito を使います。

### ストリーム処理との位置づけ

Amazon Kinesis Data Streams は、順序つきのデータを保持し、複数の読み手がそれぞれ最初から読み直せる仕組みです。保持期間は既定で 24 時間、最大で 365 日です。SQS は処理が済んだメッセージを削除しますが、ストリームは保持期間内なら残ります。

- 1件ずつのジョブを処理したい、処理側を増減したい → SQS
- 大量の時系列データを複数の用途で読み、やり直しもしたい → Kinesis Data Streams

既存のアプリケーションが JMS、AMQP、STOMP、MQTT などの標準プロトコルのブローカー（ActiveMQ など）を使っているなら、コードを変えずに移せる Amazon MQ を選びます。新規には SQS や SNS が基本です。

## 設計パターン

### キューで負荷をならす

Web 層はジョブを SQS に入れてすぐ応答し、処理側が取り出して処理します。急増した分はキューに溜まり、処理側は自分のペースで進められます。処理側の台数は、キューのメッセージ数に応じて増減させます。
### SNS と SQS のファンアウト

注文の情報を SNS トピックに発行し、在庫、配送、分析の各システムが自分用の SQS キューを購読します。止まっても情報が失われず、システムが増えても購読を足すだけで発行側は変わりません。

### イベント駆動

S3 へのファイル保存などをイベントとして EventBridge に流し、ルールで複数の Lambda 関数を呼びます。処理の追加はルールを足すだけです。

### 長い業務フローは Step Functions

「検証 → 不正検知 → 人の承認 → 支払い」のような手順は、Step Functions の標準ワークフローで書きます。承認待ちはタスクトークンのコールバックで待ち、失敗時は Catch で通知に分岐させます。Lambda 関数の中で呼び連ねたり待機を実装したりするより、運用の手間が少なくなります。

### 失敗と重複に備える

SQS の標準キューや Lambda の非同期呼び出しでは、同じメッセージが複数回届くことがあります。

- **冪等にする**: 同じ処理を2回実行しても結果が変わらないようにする。注文 ID などの一意なキーと、DynamoDB の条件付き書き込みで「まだ処理していない場合だけ書く」ようにする。FIFO の重複排除は送信時の5分間だけなので、代わりにはならない。
- **DLQ を付ける**: SQS では DLQ を使う。Lambda の非同期呼び出しは、既定で失敗時に追加で2回再試行し、それでも失敗したイベントを DLQ か失敗時の送信先に残せる。
- **一部だけ再試行する**: Lambda が SQS を読むとき、`ReportBatchItemFailures` を有効にすると、失敗したメッセージだけがキューに戻る。

## 試験のポイント

> **試験のポイント**
> 「受け付ける側と処理する側を切り離す」「急な増加でもメッセージを失わない」は SQS です。処理側はキューのメッセージ数をもとにスケールさせます。

> **試験のポイント**
> 「1つのメッセージを複数のシステムがそれぞれのペースで処理する」は、SNS トピックと、システムごとの SQS キューの組み合わせです。

> **試験のポイント**
> 「順序どおりに処理」「重複を避ける」は SQS FIFO です。同じ顧客の注文だけ順序を保てばよいなら、顧客 ID をメッセージグループ ID にします。

> **試験のポイント**
> 「複数ステップの順序、再試行、分岐、承認待ち」は Step Functions です。最長 1 年の標準ワークフローで、人の承認はコールバックで待ちます。

> **試験のポイント**
> 「イベントの内容で振り分ける」「AWS サービスのイベントに反応する」は EventBridge、「利用者ごとのレート制限と月間上限」は API Gateway の REST API の使用量プランです。

## ひっかけ注意

> **ひっかけ注意**
> SQS の1つのキューは、メッセージを1つの処理系に渡して削除する仕組みです。同じメッセージを複数のシステムに渡すには、SNS か EventBridge で複数のキューやターゲットに配ります。

> **ひっかけ注意**
> SNS はメッセージを溜めて待ってくれません。止まる可能性のある購読者への配信は、間に SQS キューを置きます。

> **ひっかけ注意**
> FIFO キューでも、順序が保たれるのはメッセージグループ ID の単位です。FIFO の重複排除は送信時のもので、受信側の二重処理は冪等な実装で防ぎます。

> **ひっかけ注意**
> Express ワークフローは最長 5 分で、コールバックも使えません。人の承認を待つなど長い処理には標準ワークフローを選びます。
