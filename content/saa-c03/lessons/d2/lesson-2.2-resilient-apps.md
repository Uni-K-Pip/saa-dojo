サーバーを複数のアベイラビリティーゾーン（AZ）に置くだけでは、システムは壊れにくくなりません。アプリケーションが「依存先が一瞬止まる」「サーバーが入れ替わる」ことを前提に作られていなければ、1 か所の不調が全体に広がります。このレッスンでは、アプリケーションの作り方、データ層の冗長化、切り替えの仕組み、環境の再現性という 4 つの面から、障害に強い設計を学びます。

## 基礎

### 単一障害点と疎結合

単一障害点とは、そこが止まるとシステム全体が止まる部分のことです。冗長化するか、マネージドサービスに任せます。また、部品同士をその場で直接呼び合うと、1 つの遅れや停止が呼び出し元に連鎖します。間にキューを置くなどして、部品同士の依存を弱めることを疎結合と呼びます。

### ステートレス化

ステートレスとは、サーバー自身に利用者のセッションや処理中のデータを持たせない作り方です。状態は、Amazon ElastiCache や Amazon DynamoDB のような外部のデータストア、ファイルは Amazon S3 や Amazon EFS に置きます。こうしておくと、どのサーバーに要求が届いても同じ結果になり、サーバーが 1 台壊れても利用者は影響を受けません。Auto Scaling による増減や入れ替えも安全に行えます。

## 使い分け

### 一時的な障害への備え

ネットワークや依存先の一時的な不調は避けられません。次の部品を組み合わせて、影響を小さくします。

| 部品 | 役割 | 気をつける点 |
|---|---|---|
| タイムアウト | 応答を待ち続けず、早めに失敗にする | 長すぎると待機で処理が詰まる |
| リトライ | 一時的なエラーをやり直して回復する | 指数バックオフ、ジッター、回数の上限を付ける |
| 冪等性 | 同じ要求を何度処理しても結果が同じになるようにする | 一意の ID で重複を防ぐ |
| サーキットブレーカー | 失敗が続く依存先への呼び出しを一時的に止める | 依存先に回復の余裕を与える |
| 縮退運転 | 一部の機能を省いて中核の機能を続ける | 推薦欄を省く、定型の内容を返すなど |

即時の再試行や、全員が同じ間隔で行う再試行は、弱っている依存先にさらに負荷をかけます。AWS SDK の多くは、バックオフ付きの再試行を標準で備えています。タイムアウトした要求は、相手側で処理が済んでいることがあるため、再試行する処理は冪等にします。

### 非同期化とキュー

結果をすぐに返す必要がない処理は、Amazon Simple Queue Service（Amazon SQS）で非同期にします。受け手が止まっていても、メッセージはキューに残り、回復後に処理されます。急なアクセス増加も、キューが吸収して平準化します。

- SQS の標準キューは、メッセージを少なくとも 1 回届けます。まれに同じメッセージが重複したり、順序が前後したりするため、受け手は冪等にします。
- **デッドレターキュー（DLQ）**: 何度処理しても成功しないメッセージの退避先です。ソースキューのリドライブポリシーで `maxReceiveCount`（受信を許す回数）を決めると、超えたメッセージが DLQ に移ります。不良メッセージが処理を妨げ続けるのを防ぎ、原因の調査にも使えます。DLQ はソースキューと同じアカウントとリージョンに作り、保持期間は元のキューより長くします。
- AWS Lambda の非同期呼び出しは、関数がエラーを返すと、既定でさらに 2 回再試行します。それでも失敗したイベントは、DLQ や失敗時の送信先（on-failure destination）に残せます。

### データ層の冗長化とフェイルオーバー

| 構成 | 仕組み | 切り替え |
|---|---|---|
| Amazon RDS の Multi-AZ DB インスタンス | 別の AZ に同期レプリケーションのスタンバイを置く（読み取りには使えない） | 障害時に自動でスタンバイへ。エンドポイントの DNS の向き先が変わる |
| Amazon RDS の Multi-AZ DB クラスター | 2 つのスタンバイを別々の AZ に置き、読み取りにも使える | 自動でスタンバイを昇格 |
| Amazon Aurora | データは 3 つの AZ に複製される。リードレプリカを最大 15 個置ける | リーダーが新しいライターに昇格。クラスターエンドポイントは自動で新しいライターを指す |
| Amazon DynamoDB | リージョン内の複数 AZ に自動で複製される | 利用者の操作は不要。複数リージョンで読み書きするならグローバルテーブル |
| Amazon ElastiCache（Valkey/Redis OSS） | レプリカを別の AZ に置く | Multi-AZ を有効にすると、障害時に自動でレプリカを昇格 |

Aurora のエンドポイントは、書き込みと一般の接続にはクラスターエンドポイント、読み取り専用にはリーダーエンドポイントを使います。特定のインスタンスを指すインスタンスエンドポイントは、フェイルオーバーに追従しません。

**Amazon RDS Proxy** は、アプリケーションとデータベースの間に置くマネージドのプロキシです。接続をプールして再利用するので、Lambda のように同時実行数が急増して DB の接続数が上限に達する場面に向いています。フェイルオーバー時は、アプリケーションからの接続を保ったままスタンバイに接続し直すため、DNS の切り替わりを待つ時間を短くできます。多くのアプリケーションは、接続先をプロキシのエンドポイントに変えるだけで使えます。プロキシは DB と同じ VPC に置き、インターネットからは直接接続できません。

### Amazon Route 53 によるフェイルオーバー

Route 53 のフェイルオーバーは、ヘルスチェックの結果に応じて、DNS の応答を切り替える仕組みです。

- **アクティブ／パッシブ**: フェイルオーバールーティングで、プライマリとセカンダリのレコードを作ります。プライマリが異常なら、Route 53 がセカンダリを返します。
- **アクティブ／アクティブ**: 加重やレイテンシーなど、フェイルオーバー以外のルーティングポリシーにヘルスチェックを組み合わせます。異常なリソースは応答から外れます。
- ヘルスチェックは、エンドポイントの監視、他のヘルスチェックを束ねる計算されたヘルスチェック、CloudWatch アラームの 3 種類です。VPC 内のプライベートなリソースのように、外から確認できないものは、CloudWatch アラームで状態を判断します。
- ALB など、エイリアスレコードにできる AWS リソースでは、個別のヘルスチェックを作らず「ターゲットの正常性を評価」を有効にします。

DNS の切り替えは、クライアントやリゾルバーがキャッシュしている間は反映されません。レコードの TTL が長いと、切り替えが遅れます。

### 環境の再現性と整合性

稼働中のサーバーに手作業でパッチや設定変更を重ねると、サーバーごとに構成が少しずつずれていきます（構成ドリフト）。**イミュータブルインフラストラクチャ**は、稼働中のサーバーを変更せず、変更を含む新しいサーバーで置き換える考え方です。EC2 では、変更を反映した AMI を作り、起動テンプレートの新しいバージョンに指定します。そして EC2 Auto Scaling のインスタンスの更新で、サービスを止めずに順に置き換えます。

**AWS CloudFormation** は、インフラをテンプレート（コード）で定義し、同じ構成を何度でも作れるようにします。スタックの作成に失敗すると、既定では作成済みのリソースを巻き戻します。変更セットで更新前に差分を確認でき、ドリフト検出で、コンソールなどから直接変更されたリソースを洗い出せます。ドリフト検出の対象は、対応するリソースの、テンプレートで明示した設定です。

### マネージドサービスと可視化

自前のソフトウェアを動かすサーバーを冗長化するより、目的に合ったマネージドサービスに置き換えるほうが、可用性も運用負荷も改善します。たとえば、テキストの読み上げは Amazon Polly、音声の文字起こしは Amazon Transcribe、感情分析は Amazon Comprehend、翻訳は Amazon Translate です。

マイクロサービスでは、どこで遅れや失敗が起きているかを AWS X-Ray で追跡できます。リクエストの経路を記録するトレースと、サービス間の依存を示すサービスマップがあります。X-Ray の SDK とデーモンは 2026 年 2 月にメンテナンスモードに入り、AWS は OpenTelemetry による計装を推奨しています。サービス自体は引き続き使えます。

## 設計パターン

### 同期呼び出しの連鎖を断つ

サービス同士が直接呼び合う構成では、呼ばれる側の遅延が連鎖します。呼び出しに短いタイムアウトを付け、バックオフ付きのリトライと冪等な処理、サーキットブレーカー、縮退運転を組み合わせます。結果をすぐに返す必要がない処理は、SQS を挟んで非同期にし、失敗が続くメッセージは DLQ に退避させます。

### 接続が急増する Lambda とデータベース

Lambda から Aurora や RDS に接続する構成は、RDS Proxy を挟みます。

### 構成を再現できる環境

EC2 は AMI と起動テンプレートで入れ替え、周辺リソースは CloudFormation で管理します。変更はテンプレート経由に統一し、定期的にドリフト検出で食い違いを見つけます。

## 試験のポイント

> **試験のポイント**
> 「障害時に待ち続けず、依存先に回復の余裕を与える」は、短いタイムアウト、バックオフとジッター付きのリトライ、サーキットブレーカー、縮退運転の組み合わせです。再試行する処理は冪等にします。

> **試験のポイント**
> 「Lambda から DB への接続数が上限に達する」「フェイルオーバー後の復旧を速くしたい」は、RDS Proxy です。アプリケーションの変更は、接続先エンドポイントの切り替えだけで済みます。

> **試験のポイント**
> 「サーバーの管理をなくしながら可用性を上げる」は、サーバーの冗長化より、目的に合ったマネージドサービスへの置き換えを選びます。

> **試験のポイント**
> 「手作業の変更をなくし、全サーバーを同じ構成に保つ」は、AMI を更新して起動テンプレートの新バージョンで置き換えるイミュータブルな方法です。構成の食い違いの検出は、CloudFormation のドリフト検出です。

## ひっかけ注意

> **ひっかけ注意**
> SQS を挟むと非同期になります。結果をすぐ画面に返す必要がある同期処理の問題を、キューで解決することはできません。

> **ひっかけ注意**
> RDS の Multi-AZ DB インスタンスのスタンバイは、読み取りに使えません。読み取りの負荷分散は、リードレプリカや、Aurora のリーダーエンドポイントの役割です。

> **ひっかけ注意**
> Route 53 のフェイルオーバーは DNS の応答を切り替えるだけです。TTL とキャッシュの影響で、利用者の接続先が変わるまでに時間がかかります。

> **ひっかけ注意**
> CloudFormation の変更セットは更新前のプレビューで、コンソールなどスタックの外で行われた変更の洗い出しには使えません。洗い出しはドリフト検出です。
