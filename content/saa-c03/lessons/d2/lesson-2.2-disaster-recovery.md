マルチ AZ 構成は、データセンター 1 か所の障害には強くなりますが、リージョン全体が使えなくなるような大規模な障害までは防げません。そうした事態に備えて、別のリージョンなどで業務を再開する計画が災害対策（DR: Disaster Recovery）です。このレッスンでは、どの要件にどの DR 戦略を選ぶか、各サービスでリージョンをまたいでデータを守る方法、切り替えの手順を学びます。

## 基礎

### RPO と RTO で戦略を決める

DR の設計は、次の 2 つの数字から始めます。

- **RPO（目標復旧時点）**: 失ってよいデータの量を時間で表したもの。RPO が 15 分なら、障害の 15 分前までのデータは戻せる必要があります。
- **RTO（目標復旧時間）**: 障害から業務を再開するまでに許される時間。

RPO はデータの複製やバックアップの間隔で、RTO は復旧先の準備がどこまで済んでいるかで決まります。どちらも小さくするほど、費用と構成の複雑さが増えます。「最も費用対効果が高い」問題では、要件を満たす最も安い戦略を選びます。

### DR 戦略の 4 種類

| 戦略 | 復旧先リージョンの状態 | RPO・RTO | 費用 |
|---|---|---|---|
| バックアップと復元 | バックアップだけを置く。災害時にインフラを作り直し、データを復元する | 長い（時間単位の目安） | 最も低い |
| パイロットライト | データは常時複製。アプリケーションのサーバーは停止か未配置で、災害時に起動して拡大する | 中程度 | 低い |
| ウォームスタンバイ | 縮小した構成を常時稼働。災害時は拡大するだけで、縮小した容量のまま処理もできる | 短い（分単位の目安） | 中程度 |
| マルチサイトのアクティブ／アクティブ | 複数のリージョンが同時に処理する | ほぼゼロにできる | 最も高い |

パイロットライトとウォームスタンバイの違いは、復旧先がすぐに要求を処理できるかどうかです。パイロットライトは、サーバーを起動してからでないと処理できません。ウォームスタンバイは、縮小した容量ですぐ処理できます。全リージョンで本番相当の容量を持ち、ひとつのリージョンだけが処理して他は待機する構成は「ホットスタンバイ」と呼ばれます。

> **試験のポイント**
> 要件の数字と予算の両方で選びます。RPO・RTO が数時間〜1 日で費用優先 → バックアップと復元。データだけ常時複製し、平常時の費用は抑えたい → パイロットライト。分単位の復旧 → ウォームスタンバイ。ほぼ無停止 → アクティブ／アクティブ。

## 使い分け

### データの置き場所ごとの手段

リージョンをまたぐ DR では、データを別のリージョンにも持つことが前提です。

| データ | 手段 | 特徴 |
|---|---|---|
| EC2・EBS・RDS・EFS など複数のサービス | AWS Backup のクロスリージョンコピー | バックアッププランで自動化。復元は災害時に行うので、バックアップと復元向き |
| Amazon RDS | クロスリージョンリードレプリカ | 非同期で継続複製。災害時にレプリカを昇格させて書き込み可能にする（手動の操作） |
| Amazon Aurora | Aurora Global Database | ストレージレベルで複製し、通常の遅延は 1 秒未満。復旧時は別リージョンのクラスターを昇格させる |
| Amazon DynamoDB | グローバルテーブル | どのリージョンのレプリカでも読み書きできるマルチアクティブ。同時更新は最後の書き込みが勝つ（既定の整合性モード） |
| Amazon S3 | クロスリージョンレプリケーション（CRR） | 要バージョニング。S3 Replication Time Control で 15 分以内の複製を目標にでき、超過を検知できる |
| Amazon EFS | EFS レプリケーション | 別リージョンのファイルシステムへ継続的に複製する |
| オンプレミス・EC2 のサーバー | AWS Elastic Disaster Recovery | ブロックレベルで継続複製し、災害時に復旧用インスタンスを起動する |

S3 のレプリケーションは、設定した後に書き込まれたオブジェクトだけが対象です。すでにあるオブジェクトを複製するには S3 バッチレプリケーションを使います。DynamoDB のグローバルテーブルには、強い整合性を選べる「マルチリージョン強整合性」もあります。選んだ整合性モードは作成後に変えられません。

### Aurora Global Database の Switchover と Failover

どちらも「別リージョンのセカンダリクラスターをプライマリに昇格させる」操作ですが、使う場面が違います。

| 項目 | Switchover（計画的な切り替え） | Failover（障害時の切り替え） |
|---|---|---|
| 想定する場面 | 保守、リージョンの輪番運用、障害後に元のリージョンへ戻す（フェイルバック） | プライマリのリージョンの予期しない障害 |
| データ損失 | なし（RPO は 0）。昇格の前に、セカンダリを最新の状態に同期する | あり得る。複製が追いついていない分は失われる |
| 前提 | すべてのクラスターが正常 | プライマリが使えない状態でもよい |
| 旧称・オプション | 旧称は「マネージド計画フェイルオーバー」 | AWS CLI では `--allow-data-loss` を付ける |

どちらも、複製の遅れ（CloudWatch の AuroraGlobalDBRPOLag など）は事前に確認しておく項目です。Switchover は、昇格先のクラスターを元のプライマリと同期してから切り替えるため、遅れが大きいと時間がかかります。Failover では遅れが大きいほど失うデータも増えます。アプリケーションは、リージョンが変わっても値が変わらないグローバルライターエンドポイントに接続しておくと、接続先の変更が不要です。

### 切り替えの方法

復旧先へのトラフィックの切り替えは、Amazon Route 53 のフェイルオーバールーティングとヘルスチェックで自動化できます。ただし、誤検知による不要な切り替えは、それ自体がデータ損失と停止を招きます。手動で切り替える設計もよく使われ、その場合も手順は自動化して「ボタンを押すだけ」にします。

AWS は切り替えの操作そのものに、可用性の高いデータプレーン（実際にサービスを提供する側）の API を使うことを勧めています。コントロールプレーン（環境を設定する側）の操作は、障害時に使えなくなる可能性があるためです。Amazon Application Recovery Controller（ARC）のルーティングコントロールは、Route 53 のヘルスチェックを手動のオン・オフのスイッチとして使い、データプレーンの API で切り替えます。ARC の Region switch は、複数リージョンの復旧手順を計画として登録して実行します。なお、ARC の準備状況チェック（readiness check）は 2026 年 4 月 30 日から新規のお客様には提供されておらず、類似の用途には Region switch が案内されています。

## 設計パターン

### 低コストな DR（バックアップと復元）

RPO・RTO が 1 日程度なら、AWS Backup のプランで別リージョンのバックアップボールトにコピーし、インフラは AWS CloudFormation のテンプレートで定義しておきます。災害時にテンプレートで環境を作り、バックアップから復元します。バックアップを同じリージョンに置いただけでは、リージョンの災害に備えられません。バックアップの保護（別アカウントへのコピーや Vault Lock）は、バックアップのレッスンで扱います。

### 平常時の費用を抑えた DR（パイロットライト）

データベースだけ別リージョンに複製し、アプリケーション層は AMI とテンプレートを用意して停止させておきます。災害時に、データベースのレプリカを昇格させ、Auto Scaling グループの希望容量を増やして拡大します。

### 改修できないサーバーの DR

ベンダーのサポートが終わったアプリケーションのように、構成を変えられないサーバーには AWS Elastic Disaster Recovery を使います。サーバーにエージェントを入れると、AWS 側のステージング領域に安価なストレージと最小限のコンピューティングで継続的に複製されます。災害時や訓練時には、最新または過去の時点の状態から、復旧用インスタンスを数分で起動できます。本番を止めずに行う復旧ドリルと、元の環境へのフェイルバックにも対応します。アプリケーションの変更が不要で、平常時の費用が低いことが決め手になります。

### 復旧先の準備を忘れない

> **試験のポイント**
> パイロットライトやウォームスタンバイでは、復旧先のリージョンで EC2 のオンデマンドインスタンスの vCPU 数などのクォータを、本番と同じ規模まで事前に引き上げておきます。クォータの多くはリージョンごとで、引き上げの申請には時間がかかるためです。DR 訓練で実際に拡大して確かめるのが有効です。

## 試験のポイント

> **試験のポイント**
> 「リージョン全体の障害」に備える要件は、別リージョンにデータを持つ構成です。Multi-AZ、同じリージョンのスナップショット、同じリージョンの別 AZ への複製では満たせません。

> **試験のポイント**
> 「改修できないオンプレミスのサーバーを分単位で復旧し、平常時の費用を抑える」は AWS Elastic Disaster Recovery です。

> **試験のポイント**
> 「計画した切り替えでデータを失いたくない」は Aurora Global Database の Switchover、「リージョンの障害でプライマリが使えない」は Failover（データ損失の可能性あり）です。

## ひっかけ注意

> **ひっかけ注意**
> レプリケーションは、誤った削除やデータの破損もそのまま複製します。DR 用の複製とは別に、特定の時点に戻せるバックアップも必要です。S3 は、バージョニングを使うと過去のバージョンから復元できます。

> **ひっかけ注意**
> クロスリージョンリードレプリカの昇格は自動のフェイルオーバーではなく、非同期の複製のため、遅れた分のデータは失われる可能性があります。Multi-AZ の自動フェイルオーバーはリージョン障害には効きません。

> **ひっかけ注意**
> 定期バックアップの間隔が、そのまま最悪の RPO になります。毎日のバックアップで RPO を数分にすることはできません。

> **ひっかけ注意**
> AWS Elastic Disaster Recovery は、サーバーのブロックを複製するサービスです。Amazon RDS のようなマネージドデータベースの複製には、RDS や Aurora の複製機能を使います。

## 確認問題

- `saa-2.2-g5-004`: 24 時間の RPO・RTO で、費用を最優先にした DR 戦略を選ぶ
- `saa-2.2-g5-010`: パイロットライトの復旧先で、災害時に必要な台数を起動できるようにする
- `saa-2.2-w2c-001`: S3 を別リージョンに 15 分以内に複製し、既存のオブジェクトも複製する
- `saa-2.2-w2c-012`: オンプレミスの仮想マシンを、分単位で復旧し平常時の費用も抑える
- `saa-2.2-w2c-018`: バックアップを別アカウントへコピーし、削除できないよう保護する
