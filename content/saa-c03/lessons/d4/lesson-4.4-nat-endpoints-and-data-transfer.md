ネットワークのコストは、見落とされがちですが、構成によって大きく変わります。特に、プライベートサブネットからの通信の経路と、データ転送の料金には注意が必要です。このレッスンでは、NAT ゲートウェイ、VPC エンドポイント、データ転送料金の考え方を学びます。

## 基礎

### NAT ゲートウェイの料金と構成

NAT ゲートウェイは、プライベートサブネットのリソースがインターネットに送信するためのマネージドなサービスです。

- **料金**: 稼働している時間あたりの料金と、処理したデータ量に応じた料金。
- **配置**: 1 つの AZ のパブリックサブネットに作られる。AZ をまたぐ冗長化はされない。
- **AZ ごとに作る理由**: ある AZ に障害が起きても、他の AZ の通信を守る。AZ をまたぐデータ転送料金も避ける。
- **NAT インスタンス**: 自分で管理する EC2 インスタンス。パッチ適用やスケーリングなどの運用が必要。小規模・低コストの用途以外では、NAT ゲートウェイが基本。

### データ転送料金の基本

| 通信 | 料金の目安 |
|---|---|
| 同じ AZ 内のプライベート IP アドレス間 | 無料 |
| AZ をまたぐ通信 | 双方向に課金 |
| リージョンをまたぐ通信 | 課金 |
| インターネットへの送信（アウト） | 課金（量に応じて段階的に安くなる） |
| インターネットからの受信（イン） | 無料 |
| AWS のオリジンから CloudFront への転送 | 無料 |

## 使い分け

### VPC エンドポイントの種類とコスト

| 種類 | 対象 | 料金 |
|---|---|---|
| ゲートウェイエンドポイント | Amazon S3、Amazon DynamoDB | 追加料金なし |
| インターフェイスエンドポイント（AWS PrivateLink） | 多くの AWS サービス、他社の PrivateLink サービス | AZ ごとの時間あたりの料金＋処理量に応じた料金 |

- 同じリージョンの S3／DynamoDB への通信は、**ゲートウェイエンドポイント**にすると NAT ゲートウェイのデータ処理料金を避けられる。
- それ以外の AWS サービスに大量に通信するなら、インターフェイスエンドポイントのほうが NAT ゲートウェイより低コストになることがある（通信量が少ないと、時間あたりの料金のほうが大きくなる）。

### NAT ゲートウェイの構成の選び方

| 状況 | 構成 |
|---|---|
| 本番、複数 AZ、可用性が重要 | AZ ごとに NAT ゲートウェイ＋AZ ごとのルートテーブル |
| 開発・検証、可用性の要件が低い | NAT ゲートウェイ 1 つでコストを抑える |

## 設計パターン

### コストを見直す手順

1. 請求やコストエクスプローラーで、NAT ゲートウェイのデータ処理料金や、AZ 間のデータ転送が大きくないかを調べる。
2. VPC フローログで、どの通信が多いかを調べる。
3. S3／DynamoDB 向けはゲートウェイエンドポイントに、その他の大量の AWS サービス向けはインターフェイスエンドポイントに切り替える。
4. 同じ AZ の中で通信を完結させる（AZ ごとの NAT ゲートウェイ、AZ を意識したリクエスト先の選択）。

## 試験のポイント

> **試験のポイント**
> 「プライベートサブネットから S3 や DynamoDB への通信コストを下げる」はゲートウェイ VPC エンドポイントです。

> **試験のポイント**
> 「NAT ゲートウェイの可用性と AZ 間のデータ転送料金」は、AZ ごとに NAT ゲートウェイを作って同じ AZ から向ける構成が答えです。

## ひっかけ注意

> **ひっかけ注意**
> ゲートウェイ VPC エンドポイントに対応しているのは S3 と DynamoDB だけです。Kinesis や SQS などにはインターフェイスエンドポイントを使います。

> **ひっかけ注意**
> NAT ゲートウェイは自動でスケールするので、サイズを大きくしてもデータ処理料金は下がりません。
