データベースは、データを整理して保存し、すばやく取り出せるようにする仕組みです。AWS には、用途ごとに作られたデータベースがたくさんあります。試験では「どのデータベースを選ぶか」がよく問われるので、まず 4 つの基本の種類を押さえましょう。

## 基礎

### リレーショナルデータベース

リレーショナルデータベース（RDB）は、データを行と列からなる「表（テーブル）」で管理します。

- 表どうしを共通の項目で結び付け（結合、JOIN）、SQL という言語で複雑な検索や集計ができます。
- 「注文を登録したら在庫も必ず減らす」のように、複数の処理を「全部成功するか、全部取り消すか」でまとめて実行できます（トランザクション）。
- 表の形（スキーマ）を先に決めて使います。
- 書き込みの性能を上げるには、主にサーバーを大きくします（スケールアップ）。読み取りは、読み取り専用のコピー（リードレプリカ）に分散できます。

AWS では、MySQL、PostgreSQL、MariaDB、Oracle、Microsoft SQL Server、Db2 を使える **Amazon RDS** と、MySQL・PostgreSQL と互換性があり AWS が独自に作った **Amazon Aurora** があります。どちらもハードウェアの用意、パッチの適用、バックアップなどを AWS が行うマネージドサービスです。

### キーバリュー型データベース（NoSQL）

キーバリュー型は、「キー（名前）」と「値（データ）」の組でデータを保存し、キーを指定して読み書きします。リレーショナル以外のデータベースをまとめて NoSQL と呼びます。

- 表の形を厳密に決めなくてよく、項目ごとに属性が違ってもかまいません。
- サーバーを横に増やす形で、ほぼ無制限に規模を広げられます。
- その代わり、複数の表の結合（JOIN）のような複雑な検索は苦手です。

**Amazon DynamoDB** は、サーバーレスでフルマネージドの NoSQL データベースです。どんな規模でも 1 桁ミリ秒の応答を安定して返します。サーバーの用意やパッチの適用は不要で、データは自動で 3 つの AZ に複製されます。

### インメモリデータベース・キャッシュ

インメモリデータベースは、データをディスクではなくメモリ（RAM）に置きます。メモリはディスクより桁違いに速いので、マイクロ秒単位で応答できます。よく使うデータの一時的な置き場所（キャッシュ）として、データベースの前に置くのが典型的な使い方です。

- **Amazon ElastiCache**: Valkey、Redis OSS、Memcached を使えるインメモリのデータストア・キャッシュです。サーバーレスで使う方法と、ノード（サーバー）の数や種類を選ぶ方法があります。
- **Amazon DynamoDB Accelerator（DAX）**: DynamoDB 専用のインメモリキャッシュです。

### データウェアハウス

データウェアハウスは、大量のデータを集めて「分析」するためのデータベースです。データを列ごとにまとめて保存する（列指向）ため、「1 年分の売上を地域別に集計する」のように、多くの行の特定の列を読む処理が得意です。

**Amazon Redshift** は、ペタバイト規模のデータを SQL で分析できるフルマネージドのデータウェアハウスです。サーバーの管理が不要な Amazon Redshift Serverless もあります。

### OLTP と OLAP

| 種類 | 処理の内容 | 例 | 向いているデータベース |
|---|---|---|---|
| OLTP（オンライントランザクション処理） | 1 件ずつの登録・更新を大量に、速く正確に行う | 注文の登録、在庫の更新、ログイン | RDS、Aurora、DynamoDB |
| OLAP（オンライン分析処理） | 大量のデータをまとめて集計・分析する | 売上の傾向分析、経営向けのレポート | Redshift |

## 使い分け

| 要件 | 選ぶもの |
|---|---|
| 複数の表をまたぐ検索やトランザクションが必要。既存の MySQL や PostgreSQL などのアプリケーションを移したい | Amazon RDS、Amazon Aurora |
| アクセスが急に増えても一定の速さで、キーで読み書きしたい。サーバーを管理したくない | Amazon DynamoDB |
| データベースの読み取りを速くし、負荷を減らしたい。ログイン中の利用者の情報（セッション）を置きたい | Amazon ElastiCache |
| 大量のデータを集計して分析したい | Amazon Redshift |

このほかにも、目的に合わせたデータベースがあります。

| データの形 | サービス | 例 |
|---|---|---|
| ドキュメント（JSON のような形） | Amazon DocumentDB（MongoDB 互換） | 商品カタログ、コンテンツ管理 |
| グラフ（つながり） | Amazon Neptune | SNS の友人関係、不正の検出 |
| ワイドカラム | Amazon Keyspaces（Apache Cassandra 互換） | Cassandra のアプリケーションの移行 |
| 時系列 | Amazon Timestream | センサーの計測値、サーバーの監視データ |

## 設計パターン

### データベースの前にキャッシュを置く

1. アプリケーションは、まず ElastiCache にデータがあるかを確かめる
2. あればそれを返す（速い）
3. なければデータベースから読み、結果を ElastiCache に保存してから返す

同じデータを何度も読むアプリケーションでは、データベースへの問い合わせが減り、応答も速くなります。

### 分析は本番のデータベースと分ける

注文などを処理する本番のデータベースで重い集計をすると、利用者の操作が遅くなります。分析用のデータは Redshift に移して、そこで集計します。

## 試験のポイント

> **試験のポイント**
> 問題文のキーワードでデータベースを絞り込みます。「SQL」「結合」「トランザクション」「既存のリレーショナルデータベース」なら RDS か Aurora、「サーバーレス」「どんな規模でも 1 桁ミリ秒」「キーバリュー」なら DynamoDB、「マイクロ秒」「キャッシュ」「セッション」なら ElastiCache（DynamoDB の読み取りを速くするなら DAX）、「ペタバイト規模の分析」「BI」なら Redshift です。

## ひっかけ注意

> **ひっかけ注意**
> DynamoDB は結合（JOIN）ができません。複数の表を組み合わせた複雑な検索や集計が中心なら、リレーショナルデータベースや Redshift を選びます。

> **ひっかけ注意**
> ElastiCache をキャッシュとして使うときは、元のデータをデータベースに残しておきます。キャッシュは「消えても作り直せるデータ」を置く場所です。

> **ひっかけ注意**
> Redshift は分析のためのデータベースで、注文の登録のような 1 件ずつの頻繁な更新には向きません。
