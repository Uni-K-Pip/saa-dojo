AWS のセキュリティで最も重要なのは、「だれが」「どのリソースに」「何をしてよいか」を正しく決めることです。そのためのサービスが AWS Identity and Access Management（IAM）です。このレッスンでは、認証と認可の違いから始めて、IAM のユーザー、グループ、ロール、ポリシーを学びます。

## 基礎

### 認証と認可

| 用語 | 確かめること | 例 |
|---|---|---|
| 認証（Authentication） | あなたはだれか | ユーザー名とパスワード、多要素認証（MFA） |
| 認可（Authorization） | あなたに何を許すか | 「この S3 バケットのファイルを読んでよい」という権限 |

会社にたとえると、社員証で本人であることを確かめて建物に入るのが認証、入れる部屋が役割によって決まっているのが認可です。

### IAM とは

IAM は、AWS リソースへのアクセスを安全に制御するサービスです。だれを認証し（サインインさせ）、だれに何の権限を与えるか（認可）を管理します。IAM は追加料金なしで使え、特定のリージョンに属さないグローバルなサービスです。

### ルートユーザー

AWS アカウントを作ったときのメールアドレスとパスワードでサインインするのが「ルートユーザー」です。アカウントのすべての権限を持つため、次のように扱います。

- 日常の作業には使わない
- MFA を設定する
- アクセスキー（プログラム用の認証情報）を作らない

### IAM の 4 つの要素

| 要素 | 内容 |
|---|---|
| IAM ユーザー | AWS を使う人やアプリケーションを表す。コンソール用のパスワードや、CLI・API 用のアクセスキーという長期的な認証情報を持てる |
| IAM グループ | IAM ユーザーの集まり。グループにポリシーを付けると、所属するユーザー全員に権限が付く。グループの中にグループは入れられない |
| IAM ロール | 必要なときに一時的に「引き受ける」権限のセット。長期的な認証情報を持たない。引き受けると、AWS STS（AWS Security Token Service）から有効期限付きの一時的な認証情報が発行される |
| ポリシー | 権限を定義する JSON 形式の文書。ユーザー、グループ、ロールやリソースに付ける |

### ポリシーの読み方

次のポリシーは「`example-bucket` という S3 バケットのオブジェクトを読むことを許可する」という意味です。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```

| 要素 | 意味 |
|---|---|
| Effect | 許可（Allow）か拒否（Deny）か |
| Action | 対象の操作（`サービス名:操作名`） |
| Resource | 対象のリソース。ARN（Amazon Resource Name）という AWS 共通の識別子で書く |
| Condition | 任意。「特定の IP アドレスからだけ」「MFA でサインインしたときだけ」などの条件 |

### 許可されるかどうかの判断

1. 何も書かれていなければ、すべて拒否されます（暗黙的な拒否）。
2. ポリシーで明示的に許可（Allow）されていれば、許可されます。
3. どこかのポリシーに明示的な拒否（Deny）があれば、許可があっても拒否が優先されます。

## 使い分け

### ポリシーを付ける場所

| 種類 | 付ける場所 | 決めること | 例 |
|---|---|---|---|
| アイデンティティベースのポリシー | ユーザー、グループ、ロール | その人（やアプリケーション）が何をできるか | AWS 管理ポリシー、自分で作るカスタマー管理ポリシー |
| リソースベースのポリシー | S3 バケットなどのリソース | そのリソースにだれがアクセスできるか（Principal で相手を書く） | S3 バケットポリシー |

### ユーザーとロールの使い分け

| 場面 | 使うもの |
|---|---|
| EC2 インスタンス上のアプリケーションが S3 を読む | EC2 インスタンスに IAM ロールを付ける（一時的な認証情報は自動で更新される） |
| Lambda 関数が DynamoDB に書き込む | Lambda 関数の実行ロール |
| 別の AWS アカウントの担当者に作業を任せる | そのアカウントから引き受けられる IAM ロール |
| 社員が複数の AWS アカウントにサインインする | AWS IAM Identity Center（旧称 AWS Single Sign-On）で一元管理し、一時的な認証情報で使う |
| AWS の外のツールで、どうしても長期のアクセスキーが必要 | IAM ユーザーのアクセスキー（必要に応じて更新し、使わなくなったら削除する） |

AWS は、人もアプリケーションも、できるだけ一時的な認証情報を使うことを勧めています。長期的なアクセスキーは、漏れたときに悪用され続ける危険があるからです。

## 設計パターン

- **最小権限の原則**: 作業に必要な操作とリソースだけを許可します。最初は AWS 管理ポリシーで始め、使い方が固まったら、必要な権限だけに絞ったカスタマー管理ポリシーに置き換えます。
- **人の権限はグループで管理する**: 「開発者」「運用担当」などのグループに権限を付け、異動のときはグループの所属を変えます。
- **MFA を必須にする**: 特に管理者やルートユーザーには必ず設定します。
- **複数のアカウントの上限を決める**: AWS Organizations のサービスコントロールポリシー（SCP）で、アカウント全体に「これ以上の権限は与えられない」という枠をはめます（ドメイン 1 で学びます）。

## 試験のポイント

> **試験のポイント**
> 「EC2 インスタンスや Lambda 関数で動くアプリケーションに、AWS のサービスを安全に呼び出させたい」と書かれていたら、IAM ロールを付けます。アクセスキーをコードや設定ファイルに書き込む選択肢は誤りです。

> **試験のポイント**
> 明示的な拒否（Deny）は、どの許可（Allow）よりも優先されます。「許可しているのにアクセスできない」という問題では、どこかに拒否がないかを疑います。

## ひっかけ注意

> **ひっかけ注意**
> 「ルートユーザーのアクセスキーを作って、自動化スクリプトに使う」は誤りです。ルートユーザーは日常的に使わず、作業には権限を絞った IAM ロールなどを使います。

> **ひっかけ注意**
> IAM グループの中に別のグループは入れられません。また、IAM はグローバルなサービスなので、リージョンごとにユーザーを作り直す必要はありません。
