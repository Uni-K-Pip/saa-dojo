システムを部品に分け、部品どうしを直接つながないようにすると、1 つの部品の障害や遅れがシステム全体に広がりにくくなります。この考え方を「疎結合」と呼びます。このレッスンでは、疎結合を実現するサービスと、出来事をきっかけに処理を動かす「イベント駆動」、サーバーを管理しない「サーバーレス」の基本を学びます。

## 基礎

### 密結合と疎結合

ネットショップで「注文を受け付ける」「在庫を減らす」「確認メールを送る」という処理があるとします。

- **密結合**: 注文の処理が、在庫の処理とメールの処理を直接呼び出し、終わるのを待つ形です。メールのサーバーが止まると、注文そのものが失敗します。
- **疎結合**: 注文の処理は「注文が入った」という連絡（メッセージ）を置き場所に置いて、すぐに終わります。在庫やメールの処理は、それぞれ自分のペースで置き場所から受け取って処理します。メールのサーバーが止まっても、注文は受け付けられ、復旧後にメールが送られます。

| 疎結合の効果 | 内容 |
|---|---|
| 障害が広がらない | 一部が止まっても、ほかの部分は動き続ける |
| 処理の速さの違いを吸収する | 注文が急に増えても、メッセージがたまるだけで、受け手は自分のペースで処理できる |
| 部品ごとに拡張できる | 忙しい部品だけサーバーを増やせる |

### 同期と非同期

- **同期**: 相手の返事を待ってから次に進む（電話のようなやり取り）
- **非同期**: 依頼を置いて、返事を待たずに次に進む（メールのようなやり取り）

疎結合では、非同期のやり取りがよく使われます。

### Amazon SQS（メッセージキュー）

Amazon SQS は、メッセージを一時的にためておく「キュー」のサービスです。

1. 送り手がメッセージをキューに入れる
2. 受け手がキューからメッセージを取り出して処理する
3. 処理が終わったら、受け手がメッセージを削除する

受け手が処理の途中で失敗すると、一定時間（可視性タイムアウト）の後にメッセージが再び取り出せるようになり、処理をやり直せます。メッセージは既定で 4 日、最大 14 日間保存できます。何度やっても失敗するメッセージは、デッドレターキューという別のキューに移して後で調べられます。

| キューの種類 | 特徴 |
|---|---|
| 標準キュー | ほぼ無制限の処理量。メッセージは少なくとも 1 回届くが、まれに 2 回以上届いたり、順番が入れ替わったりする |
| FIFO キュー | 送った順番を守り、重複なく 1 回だけ処理できる。処理量には上限がある |

### Amazon SNS（Pub/Sub）

Amazon SNS は、1 つのメッセージを、登録している複数の受け手（サブスクライバー）にまとめて届けるサービスです。送り手は「トピック」にメッセージを発行し、SNS が受け手へ押し出します（プッシュ）。受け手には、SQS のキュー、Lambda 関数、HTTP のエンドポイント、メールなどを指定できます。1 つのメッセージを複数の SQS キューに届ける形を「ファンアウト」と呼びます。

### Amazon EventBridge（イベントバス）

イベントは、「ファイルがアップロードされた」「EC2 インスタンスが停止した」「注文が入った」のような出来事の知らせです。Amazon EventBridge は、AWS のサービス、SaaS、自分のアプリケーションから届いたイベントを、ルール（条件）に合わせて目的の処理（ターゲット）に振り分けます。決まった時刻に処理を動かすスケジュールも作れます。

### AWS Step Functions（ワークフロー）

AWS Step Functions は、複数の処理を「順番に」「条件で分けて」「失敗したらやり直して」実行する流れ（ワークフロー）を組み立てるサービスです。

### サーバーレス

サーバーレスは、サーバーがないという意味ではなく、「利用者がサーバーを用意・管理しなくてよい」という意味です。

- サーバーの用意、OS の更新、台数の調整を AWS が行う
- 負荷に合わせて自動で拡張・縮小する
- 使った分だけ支払う（何も処理していなければ、処理の料金はかからない）
- 複数の AZ で動く高可用性が、最初から組み込まれている

**AWS Lambda** は、イベントをきっかけにコード（関数）を実行するサーバーレスのコンピューティングサービスです。料金は、リクエストの回数と実行時間で決まります。通常の Lambda 関数は、1 回の実行が最大 15 分（900 秒）までです。

| 分野 | サーバーレスのサービス |
|---|---|
| コンピューティング | AWS Lambda、AWS Fargate（コンテナを、サーバーを管理せずに動かす） |
| API | Amazon API Gateway |
| データ | Amazon DynamoDB、Amazon S3 |
| 連携 | Amazon SQS、Amazon SNS、Amazon EventBridge、AWS Step Functions |

## 使い分け

| サービス | 届け方 | 向いている場面 |
|---|---|---|
| Amazon SQS | 受け手が取りに行く（プル）。1 つのメッセージを 1 つの受け手が処理する | 処理の急増を吸収したい、確実に処理したい |
| Amazon SNS | SNS が押し出す（プッシュ）。1 つのメッセージを多くの受け手に届ける | 1 つの知らせを複数のシステムに同時に届けたい |
| Amazon EventBridge | ルールに合ったイベントを、ターゲットに届ける | AWS のサービスや SaaS のイベントを条件で振り分けたい、スケジュールで動かしたい |
| AWS Step Functions | 決めた順番と条件で、処理を呼び出す | 複数の処理の順番、分岐、やり直しを管理したい |

## 設計パターン

| パターン | 構成 |
|---|---|
| 画像の自動処理 | S3 に画像がアップロードされたら、イベント通知で Lambda 関数を動かし、縮小画像を別のバケットに保存する |
| 注文の受け付けのバッファ | Web サーバーは注文を SQS に入れて、すぐに利用者に応答する。処理サーバーはキューから取り出して処理し、キューにたまったメッセージの数に応じて EC2 Auto Scaling で台数を増減する |
| ファンアウト | 注文の知らせを SNS のトピックに発行し、在庫・発送・メールのそれぞれの SQS キューに届ける |
| サーバーレスの API | Amazon API Gateway で受けたリクエストを Lambda 関数で処理し、DynamoDB に保存する |

## 試験のポイント

> **試験のポイント**
> 「コンポーネントを疎結合にしたい」「処理の急増を吸収したい」「メッセージを失わずに、受け手のペースで処理したい」と書かれていたら、Amazon SQS です。「1 つのイベントを複数の受け手に同時に届けたい」なら SNS のファンアウトか EventBridge です。

> **試験のポイント**
> 「サーバーを管理せずに、イベントが起きたときだけコードを動かしたい」「使った分だけ支払いたい」と書かれていたら AWS Lambda です。「メッセージを順番どおりに、重複なく処理したい」なら SQS の FIFO キューです。

## ひっかけ注意

> **ひっかけ注意**
> 通常の Lambda 関数は、1 回の実行が最大 15 分です。何時間もかかる処理を、1 回の Lambda 関数の実行で終わらせる設計は選べません。処理を分割するか、コンテナや EC2 などを使います。

> **ひっかけ注意**
> SQS の標準キューでは、同じメッセージが 2 回以上届くことがあります。何度処理しても結果が変わらないように作るか、FIFO キューを使います。

> **ひっかけ注意**
> SNS は受け手へメッセージを押し出す仕組みで、受け手が後から自分のペースで取りに行く使い方には向きません。受け手のペースで確実に処理したいなら、SNS の受け手に SQS キューを指定します。
