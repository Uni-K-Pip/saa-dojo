クラウドでは、セキュリティを AWS と利用者が分担して守ります。この分担の考え方を「責任共有モデル」と呼びます。どこまでが AWS の仕事で、どこからが自分の仕事かを知ることは、セキュリティの問題を解く出発点です。

## 基礎

### クラウド「の」セキュリティと、クラウド「における」セキュリティ

AWS は責任の分担を、次の 2 つの言葉で説明しています。

| 担当 | 呼び方 | 内容 |
|---|---|---|
| AWS | クラウド**の**セキュリティ（Security **of** the Cloud） | AWS のすべてのサービスを動かすインフラ（ハードウェア、ソフトウェア、ネットワーク、施設）を守る |
| 利用者 | クラウド**における**セキュリティ（Security **in** the Cloud） | 利用者がクラウドに置くもの（データ、アクセス権限、各サービスの設定など）を守る |

大事なのは、利用者の責任の範囲が「使うサービスによって変わる」ことです。

### AWS が必ず受け持つこと

- データセンターの物理的なセキュリティ（入館の管理や警備）、電源や空調
- サーバー、ストレージ、ネットワーク機器などのハードウェア
- 1 台の物理サーバーを複数の仮想マシンに分ける仕組み（仮想化の基盤）

利用者は AWS のデータセンターに入ることも、機器に触れることもできません。物理的な対策は AWS に任せます。

### 利用者が必ず受け持つこと

- **データ**: 何を置くか、どう分類するか、暗号化を使うかどうか
- **アクセス権限**: IAM でだれに何を許すか。パスワード、多要素認証（MFA）、アクセスキーの管理
- **設定**: S3 バケットを公開するかどうか、どの通信を許可するかなど

どのサービスを使っても、この 3 つは利用者の責任として残ります。

## 使い分け

### サービスの種類による違い

| 項目 | Amazon EC2（インフラ型） | Amazon RDS（マネージド型） | AWS Lambda・Amazon S3・Amazon DynamoDB（抽象化型） |
|---|---|---|---|
| 施設・ハードウェア | AWS | AWS | AWS |
| OS の更新（パッチ適用） | 利用者（ゲスト OS） | AWS | AWS |
| データベースなどのソフトウェアの更新 | 利用者（自分で入れたもの） | AWS（適用する時間帯は利用者が選ぶ） | AWS |
| アプリケーション・コード | 利用者 | 利用者（スキーマや SQL） | 利用者（Lambda のコードなど） |
| 通信の許可（ファイアウォール） | 利用者（セキュリティグループ） | 利用者（セキュリティグループ） | 利用者（公開範囲やポリシーの設定） |
| データ・アクセス権限・暗号化の設定 | 利用者 | 利用者 | 利用者 |

- **インフラ型（EC2）**: 仮想サーバーを借りる形です。EC2 インスタンスの OS は「ゲスト OS」と呼ばれ、その更新やセキュリティ対策は利用者が行います。自由度が高いぶん、利用者の仕事が多くなります。
- **マネージド型（RDS）**: データベースを動かすサーバーの OS やデータベースソフトウェアの更新、バックアップの実行などを AWS が受け持ちます。
- **抽象化型（Lambda、S3、DynamoDB）**: AWS がインフラ、OS、プラットフォームを運用し、利用者は API を通じてデータやコードを扱います。利用者の責任は、主にデータ、アクセス権限、設定です。

### 両者がそれぞれの範囲で受け持つもの

AWS は、次のような項目を「共有されるコントロール」と呼んでいます。同じ種類の作業を、AWS と利用者がそれぞれの範囲で行います。

| 項目 | AWS の範囲 | 利用者の範囲 |
|---|---|---|
| パッチ管理 | インフラの欠陥の修正 | ゲスト OS とアプリケーションの更新 |
| 構成管理 | インフラ機器の設定 | ゲスト OS、データベース、アプリケーションの設定 |
| 意識向上とトレーニング | AWS の従業員の教育 | 自社の従業員の教育 |

一方、データセンターの物理的・環境的な対策は、利用者が AWS からそのまま受け継ぐ（継承する）ものです。AWS がこれらの対策を正しく行っていることは、第三者による監査レポートで確かめられます。監査レポートは AWS Artifact からダウンロードできます。

## 設計パターン

- **責任の範囲を小さくする**: EC2 にデータベースを自分で入れる代わりに Amazon RDS を使えば、OS やデータベースソフトウェアの更新作業を AWS に任せられます。サーバーの管理そのものをなくしたいなら、AWS Lambda などのサーバーレスを選びます。
- **利用者の責任をきちんと果たす**: 利用者の責任で起きやすい事故は、設定ミスです。S3 バケットの意図しない公開を防ぐ設定、IAM の最小権限、MFA の有効化などで防ぎます。これらは基礎講座の後半とドメイン 1 で学びます。

## 試験のポイント

> **試験のポイント**
> 「EC2 インスタンスの OS にセキュリティパッチを当てるのはだれか」は利用者です。「OS のパッチ適用の手間をなくしたい」「運用負荷を減らしたい」と書かれていたら、マネージドサービスやサーバーレスへの移行が答えの方向です。

> **試験のポイント**
> 「AWS のセキュリティやコンプライアンスの監査レポート（第三者の認証）を入手したい」と書かれていたら、AWS Artifact です。

## ひっかけ注意

> **ひっかけ注意**
> マネージドサービスや抽象化型のサービスでも、データの暗号化を有効にするか、だれにアクセスを許すかは利用者が決めます。「S3 なら AWS が全部守ってくれる」わけではありません。

> **ひっかけ注意**
> データセンターの入館管理や機器の廃棄といった物理的な対策は AWS の責任です。利用者がこれらのための対策や製品を用意する必要はありません。
