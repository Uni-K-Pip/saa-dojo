データを暗号化しておけば、ディスクや通信が盗み見られても中身を読まれずに済みます。ただし、暗号化がどれだけ役に立つかは「鍵をだれが持ち、だれが使えるか」で決まります。このレッスンでは、AWS で保存データと通信を暗号化する方法と、鍵を安全に管理する方法を学びます。

## 基礎

### 保存時の暗号化と転送中の暗号化

- **保存時の暗号化**: ディスクやストレージに書き込むデータを暗号化します。Amazon S3、Amazon EBS、Amazon RDS などは、設定するだけでサービス側が暗号化と復号を行います（サーバー側の暗号化）。
- **転送中の暗号化**: ネットワークを流れるデータを TLS で暗号化します。ブラウザに表示される「https://」がその例です。TLS には、サーバーの身元を証明する証明書が必要です。

アプリケーションがデータを暗号化してから保存する方式を「クライアント側の暗号化」と呼びます。この場合、保存先のサービスは暗号化されたデータしか受け取りません。

### AWS KMS とエンベロープ暗号化

AWS Key Management Service（AWS KMS）は、暗号化の鍵（KMS キー）を作成・管理するサービスです。KMS キーは FIPS 140-3 レベル 3 の認定を受けた HSM（鍵を守る専用の装置）の中で生成・使用され、暗号化されていない状態で外に出ることはありません。

KMS の Encrypt API で直接暗号化できるのは 4,096 バイトまでです。大きなデータは、次の「エンベロープ暗号化」で守ります。

1. KMS からデータキーを受け取る（平文のデータキーと、KMS キーで暗号化したデータキーの 2 つ）
2. 平文のデータキーでデータを暗号化し、平文のデータキーはすぐに消す
3. 暗号化したデータキーを、データと一緒に保存する
4. 読むときは、暗号化したデータキーを KMS で復号してから、データを復号する

S3 や EBS のサーバー側の暗号化も、内部ではこの仕組みを使っています。

## 使い分け

### KMS キーの種類

| 種類 | 作成・管理 | キーポリシーの変更 | 無効化・削除 | ローテーション |
|---|---|---|---|---|
| カスタマーマネージドキー | 利用者 | できる | できる | 自動（90〜2,560 日で指定、既定は 365 日）とオンデマンド |
| AWS マネージドキー（aws/s3 など） | AWS のサービス | できない | できない | 毎年自動（変更できない） |
| AWS 所有のキー | AWS | できない | できない | サービスが管理 |

カスタマーマネージドキーと AWS マネージドキーの使用は AWS CloudTrail に記録されます。AWS 所有のキーは利用者のアカウントにはなく、使用を監査することもできません。

### Amazon S3 の暗号化の方式

| 方式 | 鍵の管理 | 向いている要件 |
|---|---|---|
| SSE-S3 | S3 | 特別な要件がない（新しいオブジェクトは既定でこの方式で暗号化される） |
| SSE-KMS | KMS | 鍵の利用者の制御、使用の監査、鍵の無効化 |
| DSSE-KMS | KMS | 規制で 2 層の暗号化が求められる |
| クライアント側の暗号化 | 利用者 | S3 に送る前に暗号化する必要がある |

SSE-KMS でオブジェクトが多いときは、S3 バケットキーを有効にすると KMS へのリクエストが減り、コストを下げられます。

### AWS KMS と AWS CloudHSM

| 項目 | AWS KMS | AWS CloudHSM |
|---|---|---|
| HSM | AWS が管理する HSM を共用 | 自分の VPC に置かれる専用（シングルテナント）の HSM |
| 利用者の管理範囲 | 鍵とポリシー | HSM のユーザーや鍵の管理まで |
| AWS サービスとの統合 | S3、EBS、RDS など多数 | KMS のカスタムキーストアを通して使う |
| 主な用途 | ほとんどの暗号化 | 専用の HSM が必須の規制、PKCS #11 や JCE を使う既存アプリケーションの移行 |

KMS の使いやすさのまま鍵を専用の HSM に置きたいときは、CloudHSM クラスターを使う KMS のカスタムキーストア（AWS CloudHSM キーストア）を使います。

## 設計パターン

### 鍵を使える人を決める

KMS キーへのアクセスは、キーポリシーを中心に決まります。別のアカウントにキーを使わせるには、キーを持つアカウントのキーポリシーと、使う側のアカウントの IAM ポリシーの両方で許可します。SSE-KMS のオブジェクトを読むには kms:Decrypt、暗号化して書き込むには kms:GenerateDataKey が必要です。AWS マネージドキーはキーポリシーを変えられないため、アカウントをまたいで共有するデータには使えません。

### 鍵のローテーションと削除

- 定期的なローテーションは、カスタマーマネージドキーの自動ローテーションで行います。キー ID や ARN は変わらず、古いキーマテリアルも残るので、既存のデータはそのまま復号できます。
- 鍵を止めたいときは、まず無効にします。無効化は元に戻せます。削除は 7〜30 日の待機期間の後に実行され、取り消せません。削除した鍵で暗号化したデータは、二度と復号できません。

### 転送中の暗号化

- **ACM**: AWS Certificate Manager（ACM）で発行したパブリック証明書を、Application Load Balancer や Amazon CloudFront に設定します。DNS 検証の証明書は ACM が自動で更新します。CloudFront で使う証明書は、米国東部（バージニア北部）リージョンで発行またはインポートします。
- **S3**: バケットポリシーで aws:SecureTransport が false のリクエストを拒否すると、HTTPS 以外のアクセスを禁止できます。

### 秘密情報の管理

データベースのパスワードや API キーは、コードや設定ファイルに書かずに AWS Secrets Manager に保存します。Secrets Manager は秘密情報を KMS キーで暗号化して保管し、自動ローテーション（マネージドローテーション、または AWS Lambda 関数によるローテーション）でパスワードを定期的に変更できます。

## 試験のポイント

> **試験のポイント**
> 「鍵の使用を監査したい」「鍵を使える人を制御したい」「鍵を無効にできるようにしたい」は、カスタマーマネージドキーによる SSE-KMS のサインです。

> **試験のポイント**
> 「専用（シングルテナント）の HSM で鍵を管理する必要がある」なら AWS CloudHSM です。AWS のサービスと統合して使いたいなら、KMS のカスタムキーストアと組み合わせます。

> **試験のポイント**
> 「証明書の更新作業をなくしたい」なら、ACM の DNS 検証のパブリック証明書を ALB や CloudFront で使います。

## ひっかけ注意

> **ひっかけ注意**
> 古い教材には「FIPS 140-2 レベル 3 が必要なら CloudHSM」とありますが、現在は KMS の HSM も FIPS 140-3 レベル 3 の認定を受けています。CloudHSM を選ぶ決め手は、専用の HSM を自分で管理する必要があるかどうかです。

> **ひっかけ注意**
> ACM にインポートした証明書は、自動では更新されません。期限の前に自分で入れ替える必要があります。

> **ひっかけ注意**
> 利用者が用意した鍵を使う SSE-C は、2026 年 4 月から新しいバケットでは既定で無効になっています。鍵を自分で管理したい要件では、まずカスタマーマネージドキーによる SSE-KMS を検討します。

> **ひっかけ注意**
> キーをローテーションしても、既存のデータは暗号化し直されません。古いデータは、暗号化に使った古いキーマテリアルで復号されます。
