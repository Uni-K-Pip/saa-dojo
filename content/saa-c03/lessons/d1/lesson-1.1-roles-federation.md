長期的なパスワードやアクセスキーを配らずに、必要な人やプログラムに、必要なときだけ権限を渡す。その中心になるのが IAM ロールと、社外や社内の ID を AWS につなぐフェデレーションです。このレッスンでは、ロールを使ったアカウント間のアクセス、リソースベースのポリシーの使いどころ、従業員と顧客それぞれの ID サービスの選び方を学びます。

## 基礎

### IAM ロールの 2 つのポリシー

IAM ロールには、役割の違う 2 種類のポリシーがあります。

- **信頼ポリシー**: だれがこのロールを引き受けられるかを決めます。別の AWS アカウント、EC2 などの AWS サービス、ID プロバイダーなどを指定します。
- **アクセス許可ポリシー**: ロールを引き受けた後に何ができるかを決めます。

ロールを引き受けるときは、AWS STS（AWS Security Token Service）の API を使います。

| API | 使う場面 |
|---|---|
| AssumeRole | IAM ユーザーやロールが別のロールを引き受ける（ロールの切り替え、クロスアカウントアクセス） |
| AssumeRoleWithSAML | SAML 2.0 の ID プロバイダーで認証したユーザーがロールを引き受ける |
| AssumeRoleWithWebIdentity | OIDC の ID プロバイダーが発行したトークン（JWT）でロールを引き受ける |

発行される一時的な認証情報には有効期限があり、期限が切れると使えなくなります。漏えいしたときの影響を小さくできることが、長期的なアクセスキーとの大きな違いです。

### 別のアカウントのリソースを使う 2 つの方法

1. **ロールを引き受ける**: アクセスされる側のアカウントにロールを作り、信頼ポリシーでアクセス元を指定します。引き受けている間は元の権限を手放し、ロールの権限だけを使います。マネジメントコンソールでは「ロールの切り替え」で行います。
2. **リソースベースのポリシーで許可する**: S3 のバケットポリシーのように、リソースに付けるポリシーで別アカウントのプリンシパルを許可します。プリンシパルは自分の ID と権限のままアクセスできます。

アカウントをまたぐ場合は、アクセスする側のアイデンティティベースのポリシーと、リソース側のポリシーの両方で許可が必要です。どちらか一方だけでは足りません。

## 使い分け

### クロスアカウントアクセスの方法

| 観点 | ロールを引き受ける | リソースベースのポリシー |
|---|---|---|
| 使えるサービス | すべてのサービス | リソースベースのポリシーをサポートするサービス（S3、SNS、SQS、KMS、Lambda など） |
| 元の権限 | 引き受けている間は手放す | そのまま使える |
| 向いている場面 | 多くのサービスにまたがる作業、コンソールでの作業 | 2 つのアカウントのリソースを同時に扱う処理（データのコピーなど） |

### ID サービスの使い分け

| サービス | 主な利用者 | 何をするか |
|---|---|---|
| AWS IAM Identity Center（旧称 AWS Single Sign-On） | 従業員 | 複数の AWS アカウントやアプリケーションへのシングルサインオン。権限セットでアカウントごとの権限を一元管理する |
| IAM の SAML・OIDC フェデレーション | 従業員、ワークロード | アカウントごとに ID プロバイダーを登録し、ロールを引き受けさせる |
| AWS Directory Service | Active Directory を使う組織 | AWS Managed Microsoft AD、AD Connector、Simple AD を提供する |
| Amazon Cognito | 自社アプリの利用者（顧客） | ユーザープールでサインアップ・サインイン、ID プールで AWS の一時的な認証情報を発行する |

### Directory Service の 3 つの選択肢

| 種類 | 特徴 | 選ぶ場面 |
|---|---|---|
| AD Connector | オンプレミスの AD へのリクエストを中継するゲートウェイ。ディレクトリの情報をクラウドにキャッシュしない | 既存の AD の認証情報をそのまま使い、AWS にディレクトリを置きたくない |
| AWS Managed Microsoft AD | AWS が運用する Microsoft Active Directory。オンプレミスの AD と信頼関係を結べる | AWS 上で AD 自体が必要、AD に依存するワークロードを動かす |
| Simple AD | Samba 4 ベースの小規模向けのディレクトリ | 基本的な AD の機能だけで足りる小規模な環境。IAM Identity Center の ID ソースにはできない |

## 設計パターン

### 従業員のシングルサインオン

IAM Identity Center の ID ソースは、Identity Center ディレクトリ、Active Directory、外部 ID プロバイダーのうち 1 つを選びます。Okta や Microsoft Entra ID のような外部 ID プロバイダーとは、SAML 2.0 で認証を連携し、SCIM でユーザーとグループを自動的にプロビジョニングします。オンプレミスの AD を使う場合は、AD Connector か AWS Managed Microsoft AD を経由して接続します。

権限は権限セットとして定義し、ユーザーやグループとアカウントの組み合わせに割り当てます。割り当てると、各アカウントに対応する IAM ロールが自動で作られ、利用者は AWS アクセスポータルから一時的な認証情報で各アカウントを操作します。

### 第三者へのアクセスの委任と外部 ID

SaaS 事業者などの第三者に自社アカウントへのアクセスを許すときは、事業者の AWS アカウントを信頼するロールを作ります。事業者が多数の顧客を持つ場合、別の顧客がこのロールの ARN を指定して、事業者経由でアクセスする「混乱した代理（confused deputy）」の問題が起こりえます。これを防ぐため、事業者が顧客ごとに一意に発行する外部 ID を、信頼ポリシーの sts:ExternalId 条件で必須にします。

### アプリの利用者に AWS のリソースを使わせる

モバイルアプリの利用者が自分の写真を S3 に直接アップロードするような場合は、Amazon Cognito を使います。ユーザープールで利用者を認証し、ID プールでトークンを AWS の一時的な認証情報に交換します。ID プールはサインインしていないゲストに、権限を絞った認証情報を発行することもできます。アプリにアクセスキーを埋め込む必要はありません。

## 試験のポイント

> **試験のポイント**
> 「従業員が複数のアカウントにシングルサインオン」「権限を一元管理」なら IAM Identity Center と権限セットです。「外部 ID プロバイダーのユーザーやグループを自動で同期」なら SCIM です。

> **試験のポイント**
> 「オンプレミスの AD の認証情報を使う」「AWS にディレクトリの情報を置かない」なら AD Connector、「AWS 上でも AD が必要」なら AWS Managed Microsoft AD です。

> **試験のポイント**
> 「元の権限を保ったまま別アカウントのリソースを使う」ならリソースベースのポリシー、「そのサービスがリソースベースのポリシーをサポートしていない」ならクロスアカウントのロールです。

## ひっかけ注意

> **ひっかけ注意**
> Amazon Cognito は自社アプリの利用者のためのサービスです。従業員が AWS マネジメントコンソールにサインインするために Cognito を使う選択肢は誤りです。

> **ひっかけ注意**
> ロールの ARN は秘密の情報ではありません。「ARN を公開しない」ことは混乱した代理の対策になりません。また、外部 ID は顧客ではなく事業者が発行します。

> **ひっかけ注意**
> クロスアカウントのアクセスでは、リソース側だけ、またはアクセスする側だけの許可では足りません。SSE-KMS で暗号化されたオブジェクトなら、KMS キーのキーポリシーでの許可も必要です。
