ワークロードや環境ごとに AWS アカウントを分けると、障害やセキュリティ事故の影響範囲を小さくでき、費用もアカウントごとに把握できます。一方で、アカウントが増えるほど、共通のルールをどう守らせるかが課題になります。このレッスンでは、AWS Organizations、SCP、AWS Control Tower を使った複数アカウントの統制と、リージョンを意識したアクセス設計を学びます。

## 基礎

### AWS Organizations

AWS Organizations は、複数の AWS アカウントを 1 つの組織としてまとめて管理するサービスです。

- **管理アカウント**: 組織を作ったアカウントです。組織全体の請求をまとめて支払い、組織の設定を管理します。
- **メンバーアカウント**: 組織に参加しているその他のアカウントです。
- **OU（組織単位）**: アカウントをまとめるフォルダーのようなものです。本番用、開発用、セキュリティ用などに分けて、入れ子にもできます。

### SCP（サービスコントロールポリシー）

SCP は、組織のルート、OU、アカウントにアタッチして、メンバーアカウントの IAM ユーザーとロールが使える権限の**上限**を定めるポリシーです。

- SCP は権限を与えません。実際に操作するには、IAM ポリシーなどでも許可されている必要があります。
- SCP はメンバーアカウントのルートユーザーにも適用されます。アカウントの管理者は、自分のアカウントにかかる SCP を外せません。
- OU にアタッチした SCP は、配下の OU やアカウントに加えて、後から OU に追加されたアカウントにも適用されます。
- 管理アカウントには SCP が適用されません。そのため、管理アカウントではワークロードを動かさないのが基本です。

リソースの側に上限を定める RCP（リソースコントロールポリシー）もあります。SCP が「組織のプリンシパルが何をできるか」を絞るのに対して、RCP は「組織のリソースに対してだれが何をできるか」を絞ります。

## 使い分け

### 予防的・発見的・事前対応型の統制

| 種類 | 仕組みの例 | 効果 |
|---|---|---|
| 予防的 | SCP、IAM ポリシーの Deny | 操作そのものを止める |
| 発見的 | AWS Config ルール、AWS Security Hub | 違反を見つけて知らせる（必要なら自動で修復する） |
| 事前対応型 | CloudFormation フック（Control Tower の事前対応型のコントロール） | リソースを作る前にテンプレートを検査して止める |

「違反を事後に検知するのではなく防ぐ」と書かれていたら予防的な統制、「準拠状況を把握する」なら発見的な統制を選びます。

### 自分で組み立てるか、Control Tower を使うか

| 方法 | 内容 | 向いている場面 |
|---|---|---|
| Organizations と StackSets などを自分で組み合わせる | OU、SCP、Config ルール、ログの集約を自社で設計・構築・保守する | 独自の要件が多く、仕組みを自分で管理したい |
| AWS Control Tower | ベストプラクティスに沿ったランディングゾーンを自動で構築し、コントロールと Account Factory を提供する | 少ない運用負荷で、統制の効いたマルチアカウント環境をすぐに用意したい |

## 設計パターン

### Control Tower のランディングゾーン

AWS Control Tower は、Organizations、IAM Identity Center、AWS Service Catalog などを組み合わせて、ランディングゾーンと呼ばれるマルチアカウント環境を構築します。ログを集約するログアーカイブアカウントと、セキュリティチームが使う監査アカウントが用意され、コントロール（ガードレールとも呼ばれます）で環境を統制します。予防的なコントロールは SCP や RCP、発見的なコントロールは Config ルール、事前対応型のコントロールは CloudFormation フックで実装されています。新しいアカウントは、Account Factory から承認済みの構成で作成できます。

### すべてのアカウントに同じロールを配る

監査やセキュリティ運用のために、すべてのメンバーアカウントに同じ IAM ロールを用意したいことがあります。AWS CloudFormation StackSets のサービスマネージド型のアクセス許可を使うと、組織全体や OU を対象にスタックを展開できます。自動デプロイを有効にすれば、後から追加されたアカウントにも自動でロールが作られます。なお、管理アカウントには展開されません。

### メンバーアカウントのルートユーザーを一元管理する

Organizations では、メンバーアカウントのルートユーザーの認証情報（パスワード、アクセスキー、MFA など）を削除し、ルートユーザーが必要な一部の作業を管理アカウントや委任管理者から行う「ルートアクセスの一元管理」が使えます。たとえば、すべてのプリンシパルを拒否してしまった S3 のバケットポリシーの削除も、この方法で行えます。ルートユーザーの認証情報を残す場合は、SCP でメンバーアカウントのルートユーザーの操作を制限することもできます。

### リージョンを意識したアクセス設計

AWS のサービスの多くはリージョンごとに提供されますが、IAM はアカウント全体で使うグローバルなサービスです。アクセスを設計するときは、次の点を押さえておきます。

- **使えるリージョンを制限する**: グローバル条件キー aws:RequestedRegion を使った SCP で、許可したリージョン以外への操作を拒否できます。IAM のようなグローバルサービスのエンドポイントは us-east-1 にあるため、NotAction で除外しないと使えなくなります。
- **AWS STS はリージョンのエンドポイントを使う**: AWS は、ワークロードのあるリージョンの STS エンドポイントを使うことを推奨しています。
- **IAM の変更はすぐには行き渡らない**: IAM は世界中のサーバーにデータを複製しているため、変更が反映されるまでに時間がかかることがあります（結果整合性）。アプリケーションの重要な処理の途中で IAM の設定を変更しないようにします。
- **IAM Identity Center はプライマリリージョンで動く**: IAM Identity Center は有効にしたリージョンにデータを保存します。追加のリージョンにレプリケートし、プライマリリージョンが使えないときもアカウントへのアクセスを続けられるようにする機能もあります。

## 試験のポイント

> **試験のポイント**
> 「管理者やルートユーザーも含めて組織全体で禁止する」「新しいアカウントにも自動で適用する」なら、OU や組織のルートにアタッチする SCP です。

> **試験のポイント**
> 「ベストプラクティスに沿ったマルチアカウント環境を素早く」「運用負荷を最小に」なら AWS Control Tower です。

> **試験のポイント**
> 「特定のリージョン以外を使わせない」なら aws:RequestedRegion を条件にした SCP の Deny で、グローバルサービスは NotAction で除外します。

## ひっかけ注意

> **ひっかけ注意**
> SCP に Allow を書いても権限は増えません。「SCP で監査チームにアクセスを許可する」のような選択肢は誤りです。

> **ひっかけ注意**
> SCP は管理アカウントには効きません。管理アカウントのユーザーを SCP で制限する選択肢は成り立ちません。

> **ひっかけ注意**
> AWS Config ルールや Security Hub は発見的な統制です。「操作の時点で防ぐ」という要件は満たしません。
