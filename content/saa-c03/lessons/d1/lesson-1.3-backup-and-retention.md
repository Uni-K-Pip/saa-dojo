データは、壊れたり消えたりしたときに元に戻せなければ、守れているとはいえません。また、法令や社内規程で「何年間は消してはいけない」「期限が来たら消す」と決められていることもあります。このレッスンでは、バックアップと復旧、データの保持を AWS でどう設計するかを学びます。

## 基礎

### RPO と RTO

- **RPO（目標復旧時点）**: どの時点までのデータを取り戻せればよいか。RPO が 1 時間なら、失ってよいのは最大 1 時間分のデータです。
- **RTO（目標復旧時間）**: 障害が起きてから、どのくらいの時間で復旧すればよいか。

RPO を小さくするには、バックアップの頻度を上げるか、継続的なバックアップを使います。RTO を小さくするには、復元の手順を自動化したり、待機用の環境を用意したりします。

### バックアップとレプリケーションの違い

レプリケーション（複製）は、データの最新の状態を別の場所に常に写しておく仕組みです。障害が起きたときにすぐ切り替えられますが、誤って削除したデータや壊れたデータもそのまま複製されます。バックアップは過去の時点のデータを保存しておく仕組みで、誤操作やランサムウェアの被害から元に戻すために必要です。

## 使い分け

### サービスごとの復旧の方法

| サービス | 主な方法 | 戻せる時点 |
|---|---|---|
| Amazon RDS | 自動バックアップ（保持期間は最大 35 日）とポイントインタイムリカバリ、手動スナップショット | 保持期間内の任意の時点（新しい DB インスタンスとして復元） |
| Amazon DynamoDB | ポイントインタイムリカバリ（復旧期間 1〜35 日）、オンデマンドバックアップ | 復旧期間内の任意の時点（新しいテーブルとして復元） |
| Amazon EBS | スナップショット（増分）、ごみ箱（Recycle Bin） | スナップショットを取得した時点 |
| Amazon S3 | バージョニング | 残っている以前のバージョン |

Multi-AZ 配置やリードレプリカは可用性のための仕組みで、誤操作からの復旧には使えません。EBS のごみ箱は、誤って削除した EBS スナップショット、EBS ボリューム、AMI を、保持ルールで決めた期間内なら復元できる機能です。

### AWS Backup

AWS Backup は、複数のサービスのバックアップを一元的に自動化するサービスです。Amazon EC2、Amazon EBS、Amazon RDS、Amazon DynamoDB、Amazon EFS、Amazon S3 など多くのリソースに対応しています。

- **バックアッププラン**: 頻度、保持期間、別のリージョンや別のアカウントへのコピーをルールとして設定する
- **リソースの割り当て**: リソースの種類、ID、タグで対象を選ぶ
- **バックアップボールト**: バックアップ（復旧ポイント）を保管する入れ物
- **AWS Backup Vault Lock**: ボールトのバックアップを、保持期間が終わるまで削除できないようにする

Vault Lock には 2 つのモードがあります。ガバナンスモードは、十分な IAM 権限を持つユーザーならロックを外せます。コンプライアンスモードは、設定した猶予期間が過ぎると、ルートユーザーや AWS でもロックを解除・変更できなくなります。

### S3 のデータ保護と保持の機能

| 機能 | 役割 |
|---|---|
| S3 バージョニング | 上書きや削除の前のバージョンを残し、誤操作から復元できるようにする |
| MFA 削除 | バージョンの完全な削除やバージョニングの設定変更に MFA を求める |
| S3 Object Lock | 保持期間中のバージョンの削除や上書きを禁止する（WORM） |
| S3 レプリケーション | 同じリージョンや別のリージョンのバケットに、オブジェクトを非同期で複製する |
| S3 ライフサイクル | 日数に応じてストレージクラスを移したり、オブジェクトや古いバージョンを削除したりする |

S3 Object Lock には 2 つのモードがあります。ガバナンスモードでは、特別な権限（s3:BypassGovernanceRetention）を持つユーザーなら保持の設定を変えたり削除したりできます。コンプライアンスモードでは、ルートユーザーを含めてだれも、保持期間を短くしたり保持期間中のバージョンを削除したりできません。期限を決めずに保護したい場合は、リーガルホールドを使います。

## 設計パターン

### 誤った削除に備える S3 バケット

バージョニングを有効にして、最新ではなくなってから一定日数が過ぎたバージョンを削除するライフサイクルルールを組み合わせます。復元できる期間を保ちながら、古いバージョンのストレージ料金を抑えられます。

### ランサムウェアに備えるバックアップ

AWS Backup で、同じ組織の別のアカウント（バックアップ専用のアカウント）や別のリージョンにバックアップをコピーし、コピー先のボールトに Vault Lock をかけます。本番のアカウントの管理者の認証情報が盗まれても、バックアップを削除されにくくなります。

### 規制による長期保存

「7 年間は変更も削除もできない状態で保存する」といった要件は、S3 Object Lock のコンプライアンスモードで満たします。保持期間が終わった後に自動で削除したい場合は、ライフサイクルルールの有効期限を組み合わせます。

## 試験のポイント

> **試験のポイント**
> 「誤操作の直前の状態に戻す」は、RDS や DynamoDB のポイントインタイムリカバリです。どちらも、新しい DB インスタンスやテーブルとして復元されます。

> **試験のポイント**
> 「複数のサービスのバックアップを一元管理する」「別のリージョンや別のアカウントにも保存する」は、AWS Backup のバックアッププランです。

> **試験のポイント**
> 「ルートユーザーも含めてだれも削除できない」は、S3 Object Lock のコンプライアンスモードや、AWS Backup Vault Lock のコンプライアンスモードです。

## ひっかけ注意

> **ひっかけ注意**
> Multi-AZ のスタンバイ、リードレプリカ、DynamoDB のグローバルテーブルは、誤った削除も複製します。バックアップの代わりにはなりません。

> **ひっかけ注意**
> S3 Object Lock の保持期間が終わっても、オブジェクトは自動では削除されません。不要になったバージョンは、ライフサイクルルールで削除します。

> **ひっかけ注意**
> S3 レプリケーションは、設定した後に作成されたオブジェクトだけを複製します。既存のオブジェクトを複製するには、S3 バッチレプリケーションを使います。
