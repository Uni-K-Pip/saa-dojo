AWS を安全に使う第一歩は、「だれが使っているのか（認証）」と「その人や仕組みに何を許すのか（認可）」を正しく決めることです。このレッスンでは、AWS と利用者の役割分担を決める責任共有モデルと、AWS Identity and Access Management（IAM）の基本的な部品、そして試験で繰り返し問われる最小権限の考え方を学びます。

## 基礎

### 責任共有モデル

AWS のセキュリティは、AWS と利用者が分担して守ります。AWS は「クラウドのセキュリティ」として、データセンターの施設、ハードウェア、ネットワーク、サービスを動かすソフトウェアを守ります。利用者は「クラウドにおけるセキュリティ」として、自分が作るものの設定とデータを守ります。

利用者が担当する範囲は、使うサービスによって変わります。

| サービスの例 | AWS の担当 | 利用者の担当 |
|---|---|---|
| Amazon EC2（仮想サーバー） | 物理ホスト、ハイパーバイザー、ネットワーク、施設 | ゲスト OS のパッチ、アプリケーション、セキュリティグループの設定、データ |
| Amazon S3、Amazon DynamoDB（抽象化されたサービス） | インフラストラクチャ、OS、プラットフォーム | データ、暗号化の選択、アクセス権限の設定 |

どのサービスでも、「だれにアクセスを許すか」と「データをどう守るか」は利用者の責任です。そのための中心的な道具が IAM です。

### IAM の部品

IAM は AWS へのアクセスを管理するサービスで、特定のリージョンではなく AWS アカウント全体で使われます。

- **ルートユーザー**: アカウントを作ったときのメールアドレスとパスワードでサインインする ID です。アカウント内のすべての操作ができ、IAM ポリシーで権限を絞れません。
- **IAM ユーザー**: アカウント内に作る個別の ID で、パスワードやアクセスキーといった**長期的な認証情報**を持ちます。
- **IAM グループ**: IAM ユーザーをまとめる入れ物です。グループにポリシーを付けると、所属するユーザー全員に権限が及びます。グループに入れられるのは IAM ユーザーだけです。
- **IAM ロール**: 特定の人に結び付かない、「引き受けて使う」ための ID です。引き受けると AWS STS（AWS Security Token Service）から**一時的な認証情報**が発行され、一定時間がたつと使えなくなります。
- **ポリシー**: 許可や拒否を JSON で書いた文書です。どの操作（Action）を、どのリソース（Resource）に、どんな条件（Condition）で許可または拒否するかを書きます。

### ポリシーの評価の基本

リクエストは、どのポリシーでも許可されていなければ拒否されます（暗黙の拒否）。どこかのポリシーで許可されれば許可されますが、関係するポリシーのどこか 1 か所にでも明示的な拒否（Deny）があれば、許可より優先して拒否されます。

## 使い分け

### 長期的な認証情報と一時的な認証情報

| 対象 | 推奨される方法 | 避けたい方法 |
|---|---|---|
| 従業員（人） | ID プロバイダーからのフェデレーション（IAM Identity Center など）で一時的な認証情報を使う | 1 人ずつ IAM ユーザーを作って長期的なパスワードやキーを配る |
| AWS 上のプログラム | EC2 のインスタンスプロファイルや Lambda の実行ロールで IAM ロールを渡す | アクセスキーをコードや設定ファイルに書く |
| どうしても長期キーが必要な場合 | IAM ユーザーのアクセスキーを最小権限で発行し、不要になったら更新・削除する | ルートユーザーのアクセスキーを使う |

### ポリシーの種類

| 種類 | 付ける場所 | 役割 |
|---|---|---|
| アイデンティティベースのポリシー | IAM ユーザー、グループ、ロール | その ID ができることを許可する |
| リソースベースのポリシー | S3 バケット、SQS キューなどのリソース | そのリソースをだれが使えるかを許可する |
| アクセス許可の境界 | IAM ユーザー、ロール | 付与できる権限の上限を決める（権限は与えない） |
| SCP | AWS Organizations の組織、OU、アカウント | アカウント内のプリンシパルの権限の上限を決める（権限は与えない） |

AWS 管理ポリシーは手軽に使えますが、多くの利用者に向けて作られているため、必要以上の権限を含みがちです。運用に入ったら、用途に合わせたカスタマー管理ポリシーに絞り込みます。

## 設計パターン

### ルートユーザーを守る

- ルートユーザーにはアクセスキーを作りません。見つかったら、代わりの手段に切り替えてから削除します。
- ルートユーザーは強力なパスワードと MFA（多要素認証）で保護します。現在は、すべての種類のアカウントでルートユーザーへの MFA の登録が求められます。
- 日常の作業には管理用のユーザーやロールを使い、ルートユーザーはアカウントの解約など、ルートユーザーにしかできない作業のときだけ使います。

### 最小権限に絞り込む

最小権限とは、必要な操作を、必要なリソースに対してだけ、必要な条件のもとで許可することです。最初は広い権限で始めても、次の道具で絞り込みます。

- **IAM Access Analyzer のポリシー生成**: AWS CloudTrail の証跡（最大 90 日分）を分析し、実際に使われた操作をもとにポリシーのテンプレートを作ります。
- **最終アクセス情報**: しばらく使われていないサービスや権限を見つけて削除します。
- **ポリシーの条件**: TLS の使用やタグなどの条件で、さらに絞り込みます。

### タグで認可する（ABAC）

職務ごとにポリシーを作る方法（RBAC、ロールベースのアクセス制御）では、プロジェクトやリソースが増えるたびにポリシーを更新する必要があります。ABAC（属性ベースのアクセス制御）では、プリンシパルのタグとリソースのタグが一致するときだけ許可するポリシーを 1 つ書きます。新しいプロジェクトはタグの値が増えるだけなので、ポリシーを変更せずに済みます。フェデレーションでサインインする場合は、ID プロバイダーの属性をセッションタグとして渡せます。

## 試験のポイント

> **試験のポイント**
> 「EC2 上のアプリケーションに権限を与える」なら、アクセスキーではなく IAM ロールをインスタンスプロファイルでアタッチします。Lambda なら実行ロールです。

> **試験のポイント**
> 「実際の利用状況に合わせて最小権限のポリシーを作る」なら IAM Access Analyzer のポリシー生成です。文法や危険な記述をチェックするポリシー検証とは別の機能です。

> **試験のポイント**
> 「プロジェクトが頻繁に増える」「異動が多い」「ポリシーの数を増やしたくない」は ABAC のサインです。

## ひっかけ注意

> **ひっかけ注意**
> ルートユーザーのアクセスキーを「ローテーションする」「AWS Secrets Manager に保管する」という選択肢は、もっともらしく見えても正解になりません。ルートユーザーにはアクセスキーを作らないのが原則です。

> **ひっかけ注意**
> IAM グループに入れられるのは IAM ユーザーだけです。ロールやフェデレーションでサインインするユーザーをグループに入れる選択肢は成り立ちません。グループの入れ子もできません。

> **ひっかけ注意**
> アクセス許可の境界や SCP は上限を決めるだけで、権限を与えません。これらに Allow を書けばアクセスできる、という選択肢は誤りです。

> **ひっかけ注意**
> EC2 のゲスト OS のパッチは利用者の責任ですが、Amazon S3 や Amazon DynamoDB のような抽象化されたサービスでは、OS やプラットフォームの管理は AWS の担当です。サービスの種類によって責任の範囲が変わります。
