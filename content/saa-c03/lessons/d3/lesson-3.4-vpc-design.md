AWS でシステムを作るとき、最初に決めるのが「ネットワークの形」です。Amazon VPC（Virtual Private Cloud）の中をどう区切り、どこへ通信を通し、IP アドレスをどれだけ用意するかを最初にきちんと決めておくと、あとでシステムが大きくなっても作り直さずに済みます。このレッスンでは、サブネットの階層、ルーティング、IP アドレスの設計、リソースの配置場所の選び方を学びます。

## 基礎

### VPC とサブネット

VPC は、AWS の中に作る自分専用の仮想ネットワークです。1 つのリージョンの中に作り、そのリージョンのすべてのアベイラビリティーゾーン（AZ）にまたがります。VPC を作るときは、使う IP アドレスの範囲を CIDR 表記（例 10.0.0.0/16）で指定します。「/16」は先頭の 16 ビットが固定という意味で、10.0.0.0/16 なら 65,536 個のアドレスを使えます。

VPC の中は「サブネット」に区切って使います。サブネットは必ず 1 つの AZ に属します。そのため、複数の AZ にまたがって高可用性を確保したいときは、AZ ごとにサブネットを作ります。VPC とサブネットの大きさは、どちらも /16（65,536 個）から /28（16 個）の間で指定します。各サブネットでは、先頭の 4 つと最後の 1 つ、合わせて 5 つのアドレスを AWS が予約しているため、/24（256 個）のサブネットで使えるのは 251 個です。

### ルートテーブルとゲートウェイ

サブネットから出ていく通信の行き先は、サブネットに関連付けた「ルートテーブル」で決まります。ルートテーブルには、VPC の中どうしで通信するためのローカルルートが自動で入っています。

- **インターネットゲートウェイ**: VPC とインターネットの間の出入り口です。0.0.0.0/0（すべての宛先）をインターネットゲートウェイに向けたルートを持つサブネットを「パブリックサブネット」、持たないサブネットを「プライベートサブネット」と呼びます。インターネットゲートウェイ経由で IPv4 の通信をするには、インスタンスにパブリック IP アドレスか Elastic IP アドレスが必要です。
- **NAT ゲートウェイ**: プライベートサブネットのインスタンスが、外部へ「自分から」接続するための仕組みです。外部から接続を始めることはできません。従来の NAT ゲートウェイは 1 つの AZ で動作し、パブリックサブネットに作成します。新しく選べるようになったリージョン単位の NAT ゲートウェイ（リージョナル NAT ゲートウェイ）は、パブリックサブネットを用意しなくても、ワークロードのある AZ へ自動で広がります。
- **Egress-Only インターネットゲートウェイ**: IPv6 で外向きの通信だけを許可したいときに使います。

## 使い分け

### サブネットの階層

インターネットに公開する部分と、隠しておきたい部分を、サブネットの階層で分けるのが基本です。

| 階層 | 置くものの例 | 0.0.0.0/0 の宛先 | インターネットとの通信 |
|---|---|---|---|
| パブリックサブネット | インターネット向けの ALB、ゾーン単位の NAT ゲートウェイ | インターネットゲートウェイ | 双方向 |
| プライベートサブネット | アプリケーションサーバー、コンテナ | NAT ゲートウェイ | 内側から外へだけ |
| 分離されたサブネット | データベース | なし（ローカルルートだけ） | なし |

セキュリティグループは「通してよい通信」を決める仮想のファイアウォールですが、サブネットがパブリックかどうかを決めるのはルートテーブルです。この 2 つは役割が違います。

### リソースの配置場所

ほとんどのワークロードはリージョンの複数の AZ に置きますが、特定の場所の近くで動かしたい場合は次の選択肢があります。

| 配置場所 | どこにあるか | 向いている用途 |
|---|---|---|
| リージョンの AZ | AWS のデータセンター | ほとんどのワークロード。複数の AZ に分けて高可用性を確保する |
| AWS Local Zones | 大都市圏や産業の中心地の近くにある AWS の施設 | その地域の利用者に低いレイテンシーで提供する |
| AWS Wavelength | 通信事業者の 5G ネットワークの中 | モバイル端末向けに低いレイテンシーで提供する |
| AWS Outposts | 顧客のデータセンターや工場 | オンプレミスの設備との低レイテンシーの通信、データの現地処理 |

どれも VPC にサブネットを作り、Amazon EC2 などをリージョンと同じ API で使えます。違いは「物理的にどこにあるか」です。

## 設計パターン

### 3 層構成を複数の AZ に広げる

Web アプリケーションの典型的な構成では、2〜3 個の AZ それぞれに、パブリック、プライベート、分離の 3 種類のサブネットを作ります。インターネット向けの ALB は各 AZ のパブリックサブネットに、アプリケーションサーバーはプライベートサブネットに、データベースは分離されたサブネットに置きます。ゾーン単位の NAT ゲートウェイを使う場合は、1 つの AZ の障害でほかの AZ の外向き通信が止まらないよう、AZ ごとに用意してその AZ のサブネットから向けます。

### 将来の拡張に備えた IP アドレスの設計

VPC とサブネットの CIDR ブロックは、作成後にサイズを変えられません。次の点を最初に決めておきます。

- **余裕のある大きさにする**: 将来のサブネットや AZ の追加、コンテナの増加を見込んで範囲を確保します。
- **重複させない**: VPC ピアリング接続や AWS Transit Gateway、AWS Direct Connect でつなぐ予定のネットワークとは、範囲を重複させません。組織全体の割り当てを台帳などで一元管理すると安全です。
- **足りなくなったら追加する**: VPC にはセカンダリ CIDR ブロックを追加して、新しいサブネットを作れます。ただし追加できる範囲には制限があり、例えばプライマリが 10.0.0.0/8 の範囲なら、172.16.0.0/12 や 192.168.0.0/16 の範囲は追加できません。
- **IPv6 も検討する**: デュアルスタックにすると、IPv4 アドレスの不足を和らげられます。

## 試験のポイント

> **試験のポイント**
> 「インターネットから直接アクセスされないが、外部へは接続したい」と書かれていたら、プライベートサブネットから NAT ゲートウェイへのルートを考えます。「インターネットと一切通信しない」データベースは、ローカルルートだけのサブネットに置きます。

> **試験のポイント**
> 「IP アドレスが足りない」「VPC を広げたい」と書かれていたら、セカンダリ CIDR ブロックの追加が第一候補です。既存の CIDR ブロックやサブネットを大きくする選択肢は実行できません。

> **試験のポイント**
> 配置場所の問題は「だれの近くで動かすか」と「データをどこに置くか」で選びます。自社の施設の中で動かすなら AWS Outposts、都市の利用者の近くなら AWS Local Zones、5G のモバイル端末向けなら AWS Wavelength です。

## ひっかけ注意

> **ひっかけ注意**
> セキュリティグループでインバウンドを拒否しても、サブネットはプライベートになりません。パブリックかどうかはルートテーブルで決まります。また、パブリック IP アドレスのないインスタンスは、インターネットゲートウェイへのルートがあってもインターネットへ接続できません。

> **ひっかけ注意**
> ゾーン単位の NAT ゲートウェイは 1 つの AZ で動作します。1 つだけ作ってすべての AZ から向けると、その AZ の障害でほかの AZ の外向き通信も止まります。リージョン単位の NAT ゲートウェイなら、ワークロードのある AZ へ自動で広がります。

> **ひっかけ注意**
> AWS Local Zones も特定の地域にデータを置く要件に使えますが、AWS の施設です。「自社の敷地の外にデータを出せない」と書かれていたら、選べるのは AWS Outposts です。
