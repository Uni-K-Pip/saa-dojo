アプリケーションやデバイスが生み出すデータを、分析できる場所へ集める作業を「取り込み（インジェスト）」と呼びます。取り込みの方法は、データが届く頻度と、読み手の使い方で変わります。このレッスンでは、ストリーミングデータの取り込みに使う Kinesis 系のサービスと Amazon MSK の使い分けを学びます。

## 基礎

### バッチとストリーミング

- **バッチ**: データをある程度ためてから、まとめて取り込む方式です。夜間に 1 日分のファイルを読み込むような処理が当てはまります。遅延は大きくなりますが、仕組みが単純でコストも抑えやすい方式です。
- **ストリーミング**: データが発生するたびに、連続して取り込む方式です。数秒〜数分以内に処理や分析をしたいときに使います。

問題文の「ほぼリアルタイム」「毎秒数千件のイベント」「センサーから連続して」といった言葉は、ストリーミングを使うサインです。

### Kinesis のサービス群

| サービス | 役割 |
|---|---|
| Amazon Kinesis Data Streams | ストリームにデータを保持し、複数のコンシューマーが独自のコードで読み出す。データはシャード単位で管理する |
| Amazon Data Firehose（旧称 Amazon Kinesis Data Firehose） | 受け取ったデータをバッファリングして、S3、Amazon Redshift、Amazon OpenSearch Service などへ自動で届ける。サーバーレスでコンシューマーのコードが要らない |
| Amazon Managed Service for Apache Flink（旧称 Amazon Kinesis Data Analytics for Apache Flink） | ストリームのデータをリアルタイムに集計・変換する |
| Amazon Kinesis Video Streams | 動画を取り込んで保存・処理する |

> なお、SQL でストリームを処理していた Amazon Kinesis Data Analytics for SQL Applications は提供を終了しています。新しい設計では Apache Flink を使います。

## 使い分け

### Data Streams と Firehose

| 観点 | Kinesis Data Streams | Amazon Data Firehose |
|---|---|---|
| 読み出し | 自分のコンシューマーが読む（複数可） | 宛先へ自動配信（読み出しのコードが不要） |
| データの保持 | 24 時間〜最長 365 日。過去から読み直せる | 保持しない。配信するだけ |
| 容量の管理 | シャード数（オンデマンドモードもある） | 自動でスケール |
| 遅延 | 約 1 秒以内で読み出せる | バッファの設定による。最短でもバッファ分の遅れ |
| 主な用途 | 独自処理、リプレイ、複数の読み手 | S3 などへの保存、形式の変換 |

選び方の目安は、「S3 などに届けるだけ」なら Firehose、「自分のコードで読み、順序を保ち、必要なら読み直したい」なら Data Streams です。

### 順序とパーティションキー

Data Streams は、レコードを送るときのパーティションキーで、どのシャードに入れるかを決めます。**同じパーティションキーのレコードは同じシャードに入り、順序が保たれます**。車両や端末の ID をキーにすれば、車両ごとの順序を保てます。ただし、特定のキーにデータが集中すると、そのシャードだけが過負荷になります（ホットシャード）。キーはできるだけ分散させます。

### Data Streams の読み出し

コンシューマーが複数あるとき、既定の読み出しでは 1 シャードあたりの読み出し帯域を共有します。**拡張ファンアウト**を使うと、コンシューマーごとに専用の帯域が割り当てられ、互いに影響しません。

### Amazon MSK

Apache Kafka を使っている既存のアプリケーションや、Kafka のエコシステムを使いたいときは、Amazon Managed Streaming for Apache Kafka（Amazon MSK）を選びます。Kafka のクラスターの運用をマネージドにできます。アプリケーションを変えずに移したいときに向いています。新しく作るもので Kafka の知識や資産がなければ、運用の軽い Kinesis を選ぶのが基本です。

### 容量モードとホットシャード

Data Streams の容量モードは 2 つです。**プロビジョニング済みモード**はシャード数を自分で決め（1 シャードの書き込みは毎秒 1 MB または 1,000 レコードまで）、負荷が予測できて安定しているときにコストを最適化しやすい方式です。**オンデマンドモード**は容量が自動で増減し、シャードの計画が不要です。予測できない急な増加や、運用を減らしたいときに向きます。

特定のシャードだけが上限に達するのは**ホットシャード**です。パーティションキーの値が少ない、偏っている場合に起きます。対策は、値の種類が多いキー（デバイス ID など）への変更、ホットなシャードの分割、オンデマンドモードへの変更です。保持期間や拡張ファンアウト（読み取り側）は、書き込みの上限とは無関係です。

### リアルタイムの集計

時間ウィンドウを使った集計や、状態を保持する処理は、**Amazon Managed Service for Apache Flink** が得意です。Lambda はレコード単位の単純な処理向けです。

## 設計パターン

### ストリームから S3 のデータレイクへ

端末 → Firehose → S3 → Athena という流れが基本形です。Firehose の設定で、次のことができます。

- **バッファ**: サイズと時間で、S3 のオブジェクトをまとめる（小さなファイルの大量発生を避ける）
- **形式変換**: JSON を Parquet や ORC に変換する（AWS Glue Data Catalog のテーブルのスキーマを使う。コードは不要）
- **動的パーティション**: キーの値に応じて S3 のプレフィックスを分ける

### 取り込み口へのセキュアなアクセス

- **IAM**: ストリームに書き込むロールだけに、`kinesis:PutRecord` などを許可します（最小権限）。
- **VPC エンドポイント**: プライベートサブネットのサーバーが、インターネットを経由せずに Kinesis に接続するには、**インターフェイス VPC エンドポイント**（AWS PrivateLink）を使います。ゲートウェイ型のエンドポイントがあるのは S3 と DynamoDB だけです。
- **暗号化**: Data Streams や Firehose は AWS KMS で保存時の暗号化を有効にでき、通信は TLS で暗号化されます。

## 試験のポイント

> **試験のポイント**
> 「コンシューマーを開発・運用したくない」「S3 や Redshift に届けるだけ」は Firehose です。「複数のアプリケーションが同じデータを独立して読む」「過去のデータを読み直す」は Data Streams です。

> **試験のポイント**
> 順序の保証が必要なら、同じ順序で処理したい単位（車両 ID、顧客 ID など）をパーティションキーにします。

> **試験のポイント**
> 「既存の Kafka アプリケーションをできるだけ変えずに移行」は Amazon MSK です。

## ひっかけ注意

> **ひっかけ注意**
> Firehose は、バッファリングしてから配信するので、秒単位の遅延が要件なら Data Streams を検討します。ただし最近の Firehose はバッファ時間を短く（ゼロを含めて）設定できます。

> **ひっかけ注意**
> SQS はメッセージを処理して削除するキューで、ストリームのように複数の読み手が同じデータを読んだり、読み直したりする用途には向きません。

> **ひっかけ注意**
> Kinesis Data Streams にゲートウェイ VPC エンドポイントはありません。プライベートに接続するときはインターフェイス VPC エンドポイントです。
