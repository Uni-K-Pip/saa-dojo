世界中の利用者に速く安定してアプリケーションを届けるには、「利用者の近くで通信を受け止める仕組み」と「届いた通信を複数のサーバーに振り分ける仕組み」を組み合わせます。前者が Amazon CloudFront や AWS Global Accelerator などのエッジサービス、後者が Elastic Load Balancing（ELB）です。このレッスンでは、それぞれの仕組みと、試験でよく問われる使い分けを学びます。

## 基礎

### エッジロケーションと AWS のグローバルネットワーク

AWS は、リージョンとは別に、世界中の都市に「エッジロケーション」という拠点を置いています。利用者の通信を近くのエッジロケーションで受け取り、そこから先は AWS が管理するグローバルネットワークを通してリージョンまで運ぶと、混雑しやすい公衆インターネットを通る区間が短くなり、遅延やその揺らぎ（ジッター）が小さくなります。

### Amazon CloudFront

CloudFront はコンテンツ配信ネットワーク（CDN）です。Amazon S3 バケットや Application Load Balancer、任意の HTTP サーバーを「オリジン」として登録し、利用者には近くのエッジロケーションからコンテンツを返します。

- 画像や動画、JavaScript などをエッジでキャッシュするため、応答が速くなり、オリジンの負荷も下がります。
- キャッシュしない動的なコンテンツでも、エッジからオリジンまで AWS のネットワークを使うため高速化できます。
- 扱うのは HTTP と HTTPS（WebSocket を含む）です。AWS WAF と組み合わせると、エッジで不正なリクエストを遮断できます。
- S3 バケットをオリジンにするときは、オリジンアクセスコントロール（OAC）で CloudFront からのアクセスだけを許可できます。

### AWS Global Accelerator

Global Accelerator は、2 つの静的なエニーキャスト IP アドレスを入り口として提供し、TCP と UDP の通信を AWS のグローバルネットワーク経由で最適なリージョンのエンドポイントへ届けるサービスです。

- エンドポイントには、リージョンごとのエンドポイントグループに登録した Network Load Balancer、Application Load Balancer、Amazon EC2 インスタンス、Elastic IP アドレスを指定します。
- ヘルスチェックで異常を検知すると、1 分未満で正常なエンドポイントへ振り向けます。IP アドレスは変わらないので、クライアントの DNS キャッシュに左右されません。
- トラフィックダイヤルでリージョンごとの通信の割合を調整できます。
- コンテンツをキャッシュする機能はありません。

### Elastic Load Balancing

ELB は、複数の AZ にあるターゲット（EC2 インスタンスやコンテナなど）に通信を振り分け、ヘルスチェックで異常なターゲットを外すサービスです。通信量に応じてロードバランサー自体も自動でスケールします。

## 使い分け

### CloudFront と Global Accelerator

| 観点 | Amazon CloudFront | AWS Global Accelerator |
|---|---|---|
| 扱う通信 | HTTP・HTTPS（WebSocket を含む） | TCP・UDP（HTTP 以外も可） |
| キャッシュ | エッジでキャッシュする | キャッシュしない |
| 入り口 | 通常はディストリビューションの DNS 名 | 2 つの静的なエニーキャスト IP アドレス |
| リージョンの切り替え | オリジングループによるオリジンフェイルオーバー | ヘルスチェックによる自動の切り替え |
| 典型的な用途 | Web サイト、画像や動画の配信、API の高速化 | ゲーム、音声通話、固定 IP が必要なアプリケーション |

### ロードバランサーの種類

| 種類 | 動作する層 | 主な特徴 | 向いている用途 |
|---|---|---|---|
| Application Load Balancer（ALB） | レイヤー 7 | パス、ホスト名、HTTP ヘッダーなどで振り分ける。HTTP/2、gRPC、WebSocket に対応。AWS Lambda 関数もターゲットにできる | Web アプリケーション、マイクロサービス |
| Network Load Balancer（NLB） | レイヤー 4 | TCP・UDP・TLS を扱い、大量の接続を低いレイテンシーで処理する。AZ ごとに Elastic IP アドレスを割り当てられる | 独自プロトコル、固定 IP が必要な通信、AWS PrivateLink のエンドポイントサービス |
| Gateway Load Balancer（GWLB） | レイヤー 3 | すべての IP パケットを GENEVE でカプセル化し、仮想アプライアンスに透過的に振り分ける | サードパーティ製のファイアウォール、IDS/IPS |
| Classic Load Balancer | レイヤー 4・7 | 旧世代のロードバランサー | 新しい構成では選ばない |

### Amazon Route 53 のルーティングポリシー

Route 53 は DNS の応答を変えることで通信を振り分けます。主なルーティングポリシーは、決めた割合で分ける「加重」、レイテンシーが最も低いリージョンを返す「レイテンシー」、ヘルスチェックで正常な側を返す「フェイルオーバー」、利用者の国や大陸で分ける「位置情報」、リソースとの距離で分ける「地理的近接性」などです。DNS の仕組みなので、URL のパスは見えず、切り替えにはクライアントや DNS リゾルバーのキャッシュの影響が出ます。

## 設計パターン

### グローバルな Web アプリケーション

Route 53 で独自ドメインを CloudFront に向け、静的なファイルは S3 バケット、動的な処理は ALB の背後のアプリケーションをオリジンにします。ALB はパスベースのルーティングでマイクロサービスごとのターゲットグループに振り分けます。

### HTTP 以外の通信を世界中に届ける

ゲームや音声通話のような UDP の通信は、Global Accelerator の背後に複数のリージョンの NLB を置きます。利用者は 2 つの静的 IP アドレスに接続するだけで、最寄りのリージョンへ届き、障害時は自動で別のリージョンへ切り替わります。

### 固定 IP アドレスと高度な振り分けの両方が必要なとき

ALB の IP アドレスは固定できません。接続先の IP アドレスを固定したいが、パスによる振り分けも必要な場合は、Global Accelerator のエンドポイントに ALB を登録するか、NLB のターゲットに ALB を登録します。

## 試験のポイント

> **試験のポイント**
> 「UDP」「HTTP 以外のプロトコル」「静的 IP アドレス」「DNS キャッシュに左右されないリージョンの切り替え」と書かれていたら AWS Global Accelerator、「キャッシュ」「静的コンテンツ」「オリジンの負荷を下げる」と書かれていたら Amazon CloudFront です。

> **試験のポイント**
> ロードバランサーは扱う層で選びます。URL のパスやホスト名で振り分けるなら ALB、TCP・UDP で大量の接続や固定 IP が必要なら NLB、サードパーティ製のアプライアンスを透過的に挟むなら GWLB です。

## ひっかけ注意

> **ひっかけ注意**
> Global Accelerator はキャッシュしません。「よくアクセスされる画像の配信を速くしたい」なら CloudFront です。逆に、CloudFront は UDP の独自プロトコルを中継できません。

> **ひっかけ注意**
> NLB はレイヤー 4 で動作するので、URL のパスでは振り分けられません。Route 53 の加重ルーティングも DNS の応答を割合で分けるだけで、パスは見えません。

> **ひっかけ注意**
> CloudFront でも、申請すれば利用者側の許可リスト向けに Anycast 静的 IP アドレスの一覧を使えるようになっています。「静的 IP アドレス」だけで決めず、プロトコル（HTTP かどうか）とキャッシュの要否もあわせて判断します。
