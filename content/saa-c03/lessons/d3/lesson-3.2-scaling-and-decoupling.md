負荷の変化に合わせて処理能力を増減させるには、「構成要素を独立してスケールできるように分けること」と「スケーリングのきっかけになる指標を正しく選ぶこと」が重要です。このレッスンでは、キューやメッセージングによる疎結合と、EC2 Auto Scaling の使い方を学びます。

## 基礎

### 疎結合とは

システムを構成要素（Web 層、処理層、データ層など）に分け、構成要素どうしを直接呼び出さずに、キューやメッセージングを間に置いてつなぐ設計です。

- 片方が遅れたり止まったりしても、もう片方に影響しにくい。
- 構成要素ごとに独立してスケールできる。
- 構成要素の追加や入れ替えが、ほかに影響しにくい。

### メッセージングのサービス

| サービス | 仕組み | 特徴 |
|---|---|---|
| Amazon SQS | キュー。メッセージを保持し、処理する側が取り出す | 標準キューは少なくとも 1 回の配信と順序のベストエフォート。FIFO キューは順序と重複排除 |
| Amazon SNS | パブリッシュ／サブスクライブ。発行したメッセージを購読先すべてにプッシュ | 購読先は SQS、Lambda、HTTP、メールなど |
| Amazon EventBridge | イベントバス。ルールでイベントを振り分ける | AWS サービスや SaaS のイベントの連携 |

SQS では、可視性タイムアウト（処理中のメッセージを一時的に隠す時間）、ロングポーリング、デッドレターキュー（処理に失敗したメッセージの退避先）を設定します。

### EC2 Auto Scaling の方式

| 方式 | 仕組み |
|---|---|
| ターゲット追跡 | 指標を目標値に保つように台数を自動で増減する |
| ステップ／シンプル | CloudWatch アラームのしきい値に応じて、台数を段階的に増減する |
| スケジュール | 日時を指定して容量を変更する |
| 予測 | 過去のパターンから将来の負荷を予測して事前に調整する。「予測のみ」（予測を確認するだけ）と「予測とスケーリング」（実際に事前に台数を調整）のモードがあり、ターゲット追跡と併用できる |

## 使い分け

### ファンアウト（SNS＋SQS）

1 つのイベントを複数のシステムがそれぞれ独立して処理する場合は、SNS のトピックに、システムごとの SQS キューをサブスクライブします。すべてのキューに同じメッセージのコピーが届き、停止中のシステムの分は、キューに保持されます。1 つのキューを複数のシステムで共有すると、メッセージを取り合うため、各システムが全メッセージを受け取る用途には使えません。

### スケーリングの指標

| ワークロード | 適した指標 |
|---|---|
| CPU を使う Web アプリ | 平均 CPU 使用率 |
| Web サーバーへのリクエストの偏り | ALB のターゲットあたりのリクエスト数（ALBRequestCountPerTarget） |
| キューからジョブを処理するワーカー | キューの長さ（ApproximateNumberOfMessagesVisible）を、台数で割った「インスタンスあたりのバックログ」 |
| メモリが律速のアプリ | CloudWatch エージェントで収集したメモリ使用率（カスタムメトリクス） |

> メモリ使用率は標準では EC2 のメトリクスに含まれないため、CloudWatch エージェントでカスタムメトリクスとして収集する必要があります。

## 設計パターン

- **Web 層とワーカー層の分離**: ALB の背後の Web 層と、SQS からジョブを取り出すワーカー層を、別々の Auto Scaling グループにし、それぞれの指標でスケールさせる。
- **急な負荷への対処**: SQS をバッファにして、バックエンドを一定の速度で処理する（負荷の平準化）。
- **ヘルスチェック**: Auto Scaling グループに ELB のヘルスチェックを使わせると、アプリケーションが応答しないインスタンスも自動で置き換えられる。
- **機能ごとの Auto Scaling グループ**: パス（/upload/*、/view/* など）ごとにターゲットグループと Auto Scaling グループを分け、ALB のリスナールールで振り分けると、機能ごとに独立してスケールできる。
- **静的コンテンツのオフロード**: CloudFront のキャッシュに任せ、Web 層の負荷を減らす。

## 試験のポイント

> **試験のポイント**
> 「1 つのイベントを複数のシステムが独立して処理」は SNS＋SQS のファンアウトです。

> **試験のポイント**
> 「キューに溜まったジョブの数に応じて台数を増減」は、キューの長さに基づくスケーリング（インスタンスあたりのバックログ）です。

> **試験のポイント**
> 「構成要素ごとに独立してスケール」は、層を分離して、キューや ALB で疎結合にすることです。

## ひっかけ注意

> **ひっかけ注意**
> 同期的な呼び出しでつないだ構成では、呼び出し先が止まると呼び出し元も止まります。疎結合にするには、間にキューを置きます。

> **ひっかけ注意**
> SQS の標準キューは、同じメッセージが複数回配信されることがあります。処理を冪等にし、成功後にメッセージを削除します。

> **ひっかけ注意**
> CPU 使用率が低くても、キューに大量のメッセージが溜まっていることがあります。ワーカーのスケーリングは、CPU ではなくキューの長さが適切な指標になる場合があります。
