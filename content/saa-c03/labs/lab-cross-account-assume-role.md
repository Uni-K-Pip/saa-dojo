アカウント A（111122223333）の利用者が、アカウント B（444455556666）の S3 バケット example-bucket にあるオブジェクトを、B のロール example-cross-account-role を引き受けて読みます。B のバケットポリシーは使いません。

## ゴール

アカウント B にロールを作り、アカウント A の利用者がそのロールを引き受けて、B のバケットのオブジェクトを読めるようにします。完成すると、次の図の構成になります。

![完成した構成](#/diagrams/dg-cross-account-role-build-up)

満たす要件は次の 3 つです。

- 長期的なアクセスキーを、アカウント B に作らない。
- 読み取りだけを許し、書き込みなどはできないようにする。
- 引き受けられるのは、アカウント A の中で許可した利用者だけにする（信頼ポリシーでアカウント A を指定し、A の側の許可で利用者を絞る）。

## 手順

### 1. アカウント B にロールを作り、信頼ポリシーで A を指定する

- **作るもの**: アカウント B のロール example-cross-account-role。信頼ポリシー: Effect Allow、Principal にアカウント A の ARN（arn:aws:iam::111122223333:root）、Action sts:AssumeRole
- **なぜ**: だれがこのロールを引き受けられるかは、信頼ポリシーが決めます。Principal にアカウント A の ARN を書くと、アカウント A 全体への委任になります。ロールは長期的なパスワードやアクセスキーを持たず、引き受けたときに一時的な認証情報が得られるので、B に長期のアクセスキーを作らずに済みます。

![ロールと信頼ポリシーを作った時点](#/diagrams/dg-cross-account-role-build-up?step=1)

信頼ポリシーは、次のように読めます。

![アカウント B のロールの信頼ポリシー](#/artifacts/ar-trust-policy-cross-account)

### 2. ロールにアクセス許可ポリシーを付ける

- **作るもの**: ロールに付けるアクセス許可ポリシー。Effect Allow、Action s3:GetObject、Resource arn:aws:s3:::example-bucket/\*、Condition: Bool の aws:SecureTransport が true
- **なぜ**: 引き受けたあとに何ができるかは、アクセス許可ポリシーが決めます。最小権限とは、必要な操作を、必要なリソースに対してだけ、必要な条件のもとで許可することです。ここでは、操作は s3:GetObject だけ、リソースは example-bucket のオブジェクトだけ、条件は TLS で送られた要求のときだけ、に絞っています。aws:SecureTransport は、要求が TLS で送られたかを true か false で表す条件キーで、TLS を使った要求だけを許可する用途に使います。

![アクセス許可ポリシーを付けた時点](#/diagrams/dg-cross-account-role-build-up?step=2)

![TLS の要求だけに example-bucket の読み取りを許すポリシー](#/artifacts/ar-iam-policy-s3-read-tls)

### 3. アカウント A の利用者に、B のロールを引き受ける許可を付ける

- **作るもの**: アカウント A の利用者に付けるアイデンティティベースのポリシー。Effect Allow、Action sts:AssumeRole、Resource arn:aws:iam::444455556666:role/example-cross-account-role
- **なぜ**: 別のアカウントのロールを引き受けるには、そのロールの信頼ポリシーが自分のアカウントを信頼していることに加えて、自分側の管理者が AssumeRole を許可している必要があります。Resource をこのロールの ARN だけにすると、引き受けてよいロールを B の 1 つに限れます。

![引き受ける許可を付けた時点](#/diagrams/dg-cross-account-role-build-up?step=3)

![アカウント A の利用者に、B のロールを引き受けることを許すポリシー](#/artifacts/ar-iam-policy-assume-role)

### 4. A の利用者が AssumeRole を呼び、一時的な認証情報を受け取る

- **やること**: アカウント A の利用者が、AWS STS の AssumeRole を呼びます。ロール: example-cross-account-role。STS から、一時的な認証情報が返ります
- **なぜ**: 長期的なパスワードやアクセスキーを埋め込んだり配ったりせずに済むためです。一時的な認証情報には有効期限があり、期限が切れると使えなくなります。

![AssumeRole を呼んだ時点](#/diagrams/dg-cross-account-role-build-up?step=4)

### 5. 一時的な認証情報で、B のバケットのオブジェクトを読む

- **やること**: 受け取った一時的な認証情報で、アカウント B のバケット example-bucket のオブジェクトを読みます（s3:GetObject）
- **なぜ**: ロールを引き受けている間は、元の権限を手放し、ロールの権限だけを使います。ここで使えるのは、手順 2 のアクセス許可ポリシーが許した範囲です。

![オブジェクトを読んだ時点](#/diagrams/dg-cross-account-role-build-up?step=5)

## 動作を確かめる

組み上げた構成で、呼ぶ、返る、読む、期限が切れる、の順に追います。

![ロールを引き受けて S3 を読む流れ](#/diagrams/dg-assume-role-flow)

- **呼ぶ**: A の利用者が AWS STS に AssumeRole を呼び、B のロールの ARN を指定します。引き受けられるのは、B のロールの信頼ポリシーが A を信頼し、A の側でも AssumeRole を許可しているときです。
- **返る**: STS が一時的な認証情報を利用者に返します。この認証情報には有効期限があります。
- **読む**: 利用者はその認証情報で、B の S3 のバケットを読みます。引き受けている間は元の権限を手放し、ロールの権限（アクセス許可ポリシー）だけを使います。
- **期限が切れる**: 期限が切れると、認証情報は使えなくなります。

## 壊してみる

設定を 1 か所だけ変えたら何が起きるかを、先に予想してから理由を読みます。

### 信頼ポリシーの Principal を別のアカウントにする

B のロールの信頼ポリシーで、Principal をアカウント A ではない別のアカウントに変えます。A の利用者の許可（手順 3）は、そのままです。

> **その場の確認**
> 信頼ポリシーの Principal を、A ではない別のアカウントに変えました。A の利用者は、このロールを引き受けられますか？
>
> - [ ] 引き受けられる。A の側で AssumeRole を許可しているから
> - [x] 引き受けられない
>
> だれがロールを引き受けられるかは、信頼ポリシーが決めます。信頼ポリシーが A を信頼していなければ、A の側で AssumeRole を許可していても、引き受けられません。

### A の利用者から引き受ける許可を外す

信頼ポリシーはそのままで、A の利用者に付けた sts:AssumeRole の許可（手順 3）を外します。

> **その場の確認**
> 信頼ポリシーはそのままで、A の利用者から AssumeRole の許可を外しました。この利用者は、B のロールを引き受けられますか？
>
> - [x] 引き受けられない
> - [ ] 引き受けられる。信頼ポリシーが A を信頼しているから
>
> 別のアカウントのロールを引き受けるには、ロールの信頼ポリシーが自分のアカウントを信頼していることに加えて、自分側の管理者が AssumeRole を許可している必要があります。

### 引き受けたまま、A のバケットに書き込む

A の利用者は、自分のアカウントのポリシーで、A にあるバケット example-logs-bucket に書き込めます。この利用者が B のロールを引き受け、一時的な認証情報を使っているところを考えます。

> **その場の確認**
> 利用者はロールを引き受けた一時的な認証情報のまま、A のバケット example-logs-bucket に書き込もうとしました。書き込めますか？
>
> - [ ] 書き込める。A のアカウントのポリシーで許可されているから
> - [x] 書き込めない
>
> 引き受けている間は元の権限を手放し、ロールの権限だけを使います。ロールのアクセス許可ポリシーが許すのは example-bucket の読み取りだけなので、example-logs-bucket への書き込みは許可されません。

## 料金がかかり続けるもの

- **IAM と STS**: IAM と AWS STS は、アカウントの機能として追加料金なしで提供されます。
- **使ったサービス**: 課金されるのは、STS の一時的な認証情報などを使って利用したサービスの料金だけです。ここでは S3 の料金です。

## 試験での出方

- 「別のアカウントのリソースを使う」「長期的な認証情報を作らない」→ 別のアカウントにロールを作り、信頼ポリシーでアクセス元を指定して、AssumeRole で一時的な認証情報を受け取る。
- 「第三者の事業者にアクセスを委任する」→ 事業者のアカウントを信頼するロールを作り、事業者が顧客ごとに一意に発行する外部 ID を、信頼ポリシーの sts:ExternalId 条件で必須にする。
- 「元の権限を保ったまま、別のアカウントのリソースを使う」→ ロールではなく、リソースベースのポリシー。ロールを引き受けると、元の権限は手放す。

## 確認問題

- `saa-1.1-g1-008`: 第三者の SaaS 事業者に、外部 ID を使ってアクセスを委任する問題
- `saa-1.1-g1-010`: ロールを切り替えずに、別のアカウントの S3 バケットを読み取るための設定を選ぶ問題
- `saa-1.1-w2c-004`: 別のアカウントの SQS キューに、コードを変えずにメッセージを送る設定を選ぶ問題
