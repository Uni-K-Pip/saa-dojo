## ゴール

2 つの AZ にまたがる 3 層の Web アプリケーションのネットワークを、部品を 1 つずつ足して組み立てます。完成すると、次の図の構成になります。

![完成した構成](#/diagrams/dg-vpc-build-up)

満たす要件は次の 4 つです。

- インターネットからの HTTPS は、ロードバランサー（ALB）だけが受ける。
- アプリケーションサーバーは、インターネットから直接アクセスされないが、外部へは接続できる。
- データベースは、インターネットと一切通信しない。
- 1 つの AZ が止まっても、もう 1 つの AZ で動き続ける。

## 手順

### 1. VPC を作る

- **作るもの**: VPC。IPv4 CIDR ブロック: 10.0.0.0/16
- **なぜ**: VPC とサブネットの CIDR ブロックは、作成後に大きさを変えられません。あとでサブネットや AZ を足せるよう、余裕のある範囲を最初に確保します。将来つなぐネットワークと範囲を重ねないことも、この時点で決めます。

![VPC を作った時点](#/diagrams/dg-vpc-build-up?step=1)

### 2. サブネットを AZ ごとに 3 つずつ作る

- **作るもの**: AZ-a と AZ-c のそれぞれに、パブリック、プライベート、分離のサブネット（合わせて 6 つ）。例: CIDR ブロック 10.0.0.0/24 から 10.0.5.0/24
- **なぜ**: サブネットは必ず 1 つの AZ に属します。複数の AZ で動かすには、AZ ごとにサブネットを作ります。/24 のサブネットでは、AWS が予約する 5 つを除いた 251 個のアドレスを使えます。この時点では 6 つとも、ルートテーブルにローカルルートしかありません。

![サブネットを作った時点](#/diagrams/dg-vpc-build-up?step=2)

### 3. インターネットゲートウェイを付け、パブリックのルートを足す

- **作るもの**: インターネットゲートウェイ（VPC に関連付ける）と、パブリックサブネット用のルートテーブル。ルートテーブル: 送信先 0.0.0.0/0、ターゲット インターネットゲートウェイ
- **なぜ**: サブネットがパブリックかどうかは、ルートテーブルで決まります。このルートを持つサブネットだけがパブリックサブネットになります。

![インターネットゲートウェイを付けた時点](#/diagrams/dg-vpc-build-up?step=3)

### 4. ALB をパブリックサブネットに置く

- **作るもの**: インターネット向けの ALB。サブネット: 2 つの AZ のパブリックサブネット。セキュリティグループ: インバウンド TCP 443、送信元 0.0.0.0/0。リスナー: HTTPS（443）、証明書は AWS Certificate Manager（ACM）で作ったもの、デフォルトルールの転送先は次の手順のサーバーを登録するターゲットグループ
- **なぜ**: ALB は 2 つ以上の AZ を有効にする必要があります。インターネットから受けるのは ALB だけにし、うしろのサーバーは隠します。セキュリティグループで 443 を許可するだけでは待ち受けません。リスナーがプロトコルとポートで待ち受け、ルールで転送先のターゲットグループを決めます。HTTPS リスナーには、少なくとも 1 つのサーバー証明書が要ります。

![ALB を置いた時点](#/diagrams/dg-vpc-build-up?step=4)

### 5. アプリケーションサーバーをプライベートサブネットに置く

- **作るもの**: EC2 インスタンス（AZ ごとに 1 台）。サブネット: プライベートサブネット。パブリック IP アドレス: なし。セキュリティグループ: インバウンド TCP 443、送信元 ALB のセキュリティグループ。作ったインスタンスを、ALB のターゲットグループに登録する
- **なぜ**: ALB はプライベート IP アドレスでターゲットに転送するので、サーバーにパブリック IP アドレスは要りません。送信元にセキュリティグループを指定すると、台数が増減してもルールを書き換えずに済みます。

![アプリケーションサーバーを置いた時点](#/diagrams/dg-vpc-build-up?step=5)

セキュリティグループのルールは、次のように読めます。

![アプリケーションサーバーのセキュリティグループ](#/artifacts/ar-sg-rules-app-tier)

### 6. NAT ゲートウェイを AZ ごとに作る

- **作るもの**: ゾーン単位のパブリック NAT ゲートウェイ（AZ ごとに 1 つ。パブリックサブネットに作り、それぞれに Elastic IP アドレスを関連付ける。関連付けないと作成できない）と、AZ ごとのプライベートサブネット用のルートテーブル。ルートテーブル: 送信先 0.0.0.0/0、ターゲット 同じ AZ の NAT ゲートウェイ
- **なぜ**: NAT ゲートウェイは、プライベートサブネットのサーバーが「自分から」外へ接続するための仕組みで、外から接続を始めることはできません。ゾーン単位の NAT ゲートウェイは 1 つの AZ で動作するので、1 つの AZ の障害でほかの AZ の外向き通信が止まらないよう、AZ ごとに作って同じ AZ から向けます。

![NAT ゲートウェイを作った時点](#/diagrams/dg-vpc-build-up?step=6)

### 7. データベースを分離されたサブネットに置く

- **作るもの**: RDS の DB インスタンス。配置: Multi-AZ（プライマリと、別の AZ のスタンバイ）。サブネット: 分離されたサブネット。セキュリティグループ: インバウンド TCP 3306（MySQL の場合）、送信元 アプリケーションサーバーのセキュリティグループ
- **なぜ**: 分離されたサブネットのルートテーブルにはローカルルートしかないので、インターネットとは一切通信しません。Multi-AZ では、プライマリから別の AZ のスタンバイへ同期で複製します。

![データベースを置いた時点](#/diagrams/dg-vpc-build-up?step=7)

## 動作を確かめる

できあがった構成で、通信がどこを通るかを段階表示で追います。「次へ」を押すと、利用者のリクエスト、アプリケーションからデータベースへの読み書き、外へ出る通信、データベースの複製の順に進みます。

![3 層の VPC の通信の経路](#/diagrams/dg-vpc-three-tier)

- 利用者のリクエストは、インターネットゲートウェイから ALB に入り、プライベートサブネットのアプリケーションサーバーへ振り分けられます。
- アプリケーションサーバーが外へ出る通信は、同じ AZ の NAT ゲートウェイとインターネットゲートウェイを通ります。
- データベースへは、アプリケーションサーバーからだけ届きます。

## 壊してみる

設定を 1 か所だけ変えたら何が起きるかを、先に予想してから理由を読みます。

### パブリックのルートを消す

パブリックサブネットのルートテーブルから、0.0.0.0/0 をインターネットゲートウェイへ向けるルートを消します。セキュリティグループは変えません。

> **その場の確認**
> パブリックサブネットのルートテーブルから 0.0.0.0/0 のルートを消しました。インターネットの利用者は、ALB に接続できますか？
>
> - [ ] 接続できる。セキュリティグループで HTTPS を許可しているから
> - [x] 接続できない
>
> サブネットがパブリックかどうかは、ルートテーブルで決まります。インターネットゲートウェイへのルートがなくなると、セキュリティグループで許可していても、インターネットとは通信できません。

### NAT ゲートウェイを 1 つにまとめる

AZ-c の NAT ゲートウェイを消し、AZ-c のプライベートサブネットの 0.0.0.0/0 も、AZ-a の NAT ゲートウェイへ向けます。

> **その場の確認**
> NAT ゲートウェイを AZ-a の 1 つにまとめたあと、AZ-a で障害が起きました。AZ-c のアプリケーションサーバーは、外へ接続できますか？
>
> - [ ] 接続できる。サーバーは AZ-c で動いているから
> - [x] 接続できない
>
> ゾーン単位の NAT ゲートウェイは 1 つの AZ で動作します。1 つだけ作ってすべての AZ から向けると、その AZ の障害で、ほかの AZ の外向き通信も止まります。

### データベースのサブネットから NAT へ向ける

分離されたサブネットのルートテーブルに、0.0.0.0/0 を NAT ゲートウェイへ向けるルートを足します。

> **その場の確認**
> 分離されたサブネットから NAT ゲートウェイへのルートを足しました。インターネットの側から、データベースへの接続を始められるようになりますか？
>
> - [ ] 始められるようになる
> - [x] 始められない
>
> NAT ゲートウェイは、内側から外へ接続するための仕組みで、外から接続を始めることはできません。ただし、0.0.0.0/0 のルートを持つので、このサブネットはもう、ローカルルートだけの分離されたサブネットではありません。

## 料金がかかり続けるもの

| もの | 料金の単位 | 止めたとき |
|---|---|---|
| NAT ゲートウェイ | 動いている時間と、処理したデータ量 | 削除するまで時間の料金がかかる。AZ ごとに作ると、その台数分かかる |
| ALB | 動いている時間（1 時間に満たない分は 1 時間分）と、キャパシティーユニット（LCU）の使用量 | うしろのサーバーを止めても、ALB を削除するまで時間の料金がかかる |
| EC2 インスタンス（オンデマンド） | 動いている時間 | 停止中はインスタンスの料金がかからない |
| RDS の DB インスタンス | 動いている時間と、ストレージ・バックアップのストレージ | 一時停止中は時間の料金がかからないが、ストレージとバックアップのストレージにはかかり続ける。一時停止は最大 7 日で、過ぎると自動で起動する |
| パブリック IPv4 アドレス | 実行中のインスタンスに付くものと Elastic IP アドレスを含め、すべてのパブリック IPv4 アドレス | VPC の中で使うプライベート IPv4 アドレスにはかからない。サーバーをロードバランサーの背後に置き、パブリック IP アドレスの自動割り当てを無効にすると（手順 5）、使うアドレスの数を減らせる |
| EC2 インスタンスと NAT ゲートウェイの間のデータ転送 | 両者が異なる AZ にあるときに、両者の間のデータ転送料金がかかる | ゾーン単位の NAT ゲートウェイを同じ AZ から向ける配置（手順 6）にすると、この AZ 間の転送料金を避けられる |

## 試験での出方

- 「インターネットから直接アクセスされないが、外部へは接続したい」→ プライベートサブネットから NAT ゲートウェイへのルート。
- 「インターネットと一切通信しない」データベース → ローカルルートだけの分離されたサブネット。
- 「NAT ゲートウェイの可用性」「AZ 間のデータ転送料金」→ AZ ごとに NAT ゲートウェイを作り、同じ AZ から向ける。
- 「台数が増減するアプリケーション層からだけ、データベースへの接続を許可する」→ データベースのセキュリティグループの送信元に、アプリケーション層のセキュリティグループを指定する。
- 「セキュリティグループで拒否してプライベートにする」は誤り。パブリックかどうかはルートテーブルで決まる。
