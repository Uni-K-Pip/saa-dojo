# シミュレーターの設計書（共通の枠）

`visual-materials-design.md` 10 章のシミュレーターを、どの仕組みでも同じ形で作るための共通の枠を決める文書です。シナリオのデータ、画面の流れ、エンジンの置き場所、`expect` との一致の検査、検証状態、記録を扱います。シミュレーターごとの規則は、別の文書に 1 つずつ書きます（Sim3 は `sim-cidr-design.md`）。

この文書は設計です。実装が済んだものは `content-guide.md` と `app-spec.md` に移します。

## 1. 考え方

- シミュレーターは、1 つの仕組みを、小さな専用のエンジン（純粋な関数）で計算して見せます。汎用のエンジンは作りません（設計書 10.1）。
- シナリオはデータです。エンジンは、シナリオの設定から結果を計算します。シナリオに書いた `expect` とエンジンの結果が食い違えば、validate とアプリのビルドが止まります。書いた人の理解とエンジンの実装を、互いの検査に使います。
- 数値の規則（大きさの範囲、予約の数など）は、エンジンの規則の表に 1 か所だけ置き、図鑑の検証済みの事実を指します。シナリオの文には規則の数値を直接書かず、差し込みの記法（3.5）で表から出します。
- どのシミュレーターも、扱わないことを画面に出します。単純化したモデルを、実際の動作と取り違えさせないためです。

## 2. 置き場所

| もの | 置き場所 | 中身 |
|---|---|---|
| シナリオ | `content/saa-c03/sims/<sim>/<id>.json` | 1 件 1 ファイル。`<sim>` はシミュレーターの id（Sim3 は `cidr`） |
| エンジン | `scripts/lib/sims/<sim>.mjs`（型は同じ名前の `.d.mts`） | 計算の関数、規則の表、扱わないこと、出力の項目の一覧。依存のない純粋な JavaScript |
| シミュレーターの一覧 | `scripts/lib/sims/index.mjs` | id、名前、エンジン、並び順 |
| 共通の検査 | `scripts/lib/sim.mjs` | シナリオの検査（`checkSimScenario`）、規則の表の検査、差し込みの解決。validate とアプリのビルドが同じ関数を使う |
| 設定のスキーマ | `scripts/lib/schema.mjs` | 共通の項目（`SimScenarioSchema`）と、シミュレーターごとの `config` のスキーマ（`SIM_CONFIG_SCHEMAS`） |
| 画面 | `app/src/pages/SimsPage.tsx`（一覧・シナリオの一覧・実行）、`app/src/sims/`（流れの部品）、`app/src/sims/<sim>/`（結果の表示と、自由に試す操作） | |

エンジンを `scripts/lib/` に置くのは、validate（Node）とアプリ（ブラウザー）の両方から同じ実装を使うためです。前例は、本文の行単位の検査（`scripts/lib/inline-check.mjs`）と参照の読み方（`scripts/lib/diagram-refs.mjs`）で、アプリは `.d.mts` の型つきで読み込んでいます。設計書 13 章は W10 の置き場所を `app/src/sims/` としていましたが、エンジンだけは `scripts/lib/sims/` に置き、画面は `app/src/sims/` に置きます。

エンジンは zod などのライブラリを読み込みません（アプリのバンドルに入るため）。設定の形の検査は、validate とビルドの側で `schema.mjs` が行い、エンジンは形の正しい設定を受け取る前提で計算します。自由に試す操作（4.4）で学習者が入れた値は、エンジンの入力の検査の関数（各エンジンが持つ、依存のない小さな関数）を通してから計算します。

## 3. シナリオのデータ

### 3.1 例

```json
{
  "id": "sim-cidr-reserved-addresses",
  "title": "小さなサブネットに何台置けるか",
  "intro": "管理用のサーバーを置くために、VPC の中に 10.0.0.0/28 のサブネットを作ります。サーバーは 1 台ごとにプライベート IPv4 アドレスを 1 つ使います。",
  "predict": {
    "text": "このサブネットで、サーバーに割り当てられるアドレスはいくつですか。",
    "key": "usable",
    "choices": [
      { "text": "16 個", "value": 16 },
      { "text": "15 個", "value": 15 },
      { "text": "11 個", "value": 11 },
      { "text": "14 個", "value": 14 }
    ]
  },
  "config": { "op": "size", "role": "subnet", "cidr": "10.0.0.0/28" },
  "toggles": [
    { "id": "prefix-27", "label": "/27 にする", "set": { "cidr": "10.0.0.0/27" } },
    { "id": "prefix-24", "label": "/24 にする", "set": { "cidr": "10.0.0.0/24" } },
    { "id": "prefix-29", "label": "/29 にする", "set": { "cidr": "10.0.0.0/29" } }
  ],
  "expect": {
    "initial": { "total": 16, "usable": 11, "allowed": true },
    "toggles": {
      "prefix-27": { "total": 32, "usable": 27, "allowed": true },
      "prefix-24": { "total": 256, "usable": 251, "allowed": true },
      "prefix-29": { "allowed": false, "sizeIssue": "too-small" }
    }
  },
  "explain": {
    "initial": "/28 のアドレスは {{out:total}} 個です。サブネットでは {{rule:reserved}} を AWS が予約するので、残りの {{out:usable}} 個だけを割り当てられます。",
    "toggles": {
      "prefix-27": "…",
      "prefix-24": "…",
      "prefix-29": "…"
    }
  },
  "factRefs": ["vpc.subnet-reserved-ips", "vpc.cidr-size"],
  "lessonRefs": ["lesson-basics-ip-subnet-routing"],
  "createdBy": "…"
}
```

### 3.2 項目と上限

| 項目 | 形 | 上限・規則 |
|---|---|---|
| `id` | `sim-<sim>-<英小文字・数字・ハイフン>` | ファイル名と同じ。`<sim>` は置き場所のフォルダーと同じ |
| `title` | 文字列 | 4〜60 字 |
| `intro` | 文字列（Markdown。インラインだけ） | 20〜300 字。状況と、最初の設定を文で書く |
| `predict` | `{ text, key, choices }` | `text` 10〜120 字。`key` はエンジンの出力の項目（3.4）。`choices` は 2〜4 個で、それぞれ `{ text（1〜40 字）, value }`。`value` は文字列・数・真偽のどれかで、`key` の出力の種類と同じ種類にする。エンジンが出しうる値でなくてよい（よくある誤解を誤答の選択肢にするため）。`value` が重なる選択肢はエラー |
| `config` | シミュレーターごとの形（3.3） | `SIM_CONFIG_SCHEMAS[<sim>]` で検査する |
| `toggles` | `[{ id, label, set }]` | 1〜4 個。`id` は英小文字・数字・ハイフンで、シナリオの中で重ならない。`label` 2〜30 字。`set` は `config` の最上位の項目を 1 つだけ変える（キーがちょうど 1 つ。`op` は変えられない）。`set` を当てた設定も、`config` と同じスキーマで検査する。最初の設定と同じになる `set` はエラー |
| `expect` | `{ initial, toggles: { <toggle の id>: … } }` | それぞれ、エンジンの出力の一部（3.4）。すべての toggle に `expect` が要る。知らない toggle の id はエラー |
| `explain` | `{ initial, toggles: { <toggle の id>: … } }` | それぞれ 20〜400 字（Markdown。インラインだけ。差し込みは展開する前の字数で数える）。すべての toggle に要る |
| `factRefs`・`lessonRefs` | id の配列 | 合わせて 1 つ以上。存在しない id はエラー。さらに、そのシナリオの実行で使った規則の裏づけを含む（3.5） |
| `createdBy` | 文字列 | 記録の欄。ハッシュに含めない |

シナリオの一覧は `id` の順に並べます。並びを決める別のファイルは作りません。学習の順に並べたいときは、学習コースのユニットに並べて表します。

### 3.3 シミュレーターごとに違う `config`・`toggles`・`expect`

- `config` は、`op`（そのシミュレーターの中の操作の種類）を判別の項目にした、操作ごとの形のどれかです。形は `schema.mjs` の `SIM_CONFIG_SCHEMAS.<sim>`（zod の discriminatedUnion）に置きます。共通の `SimScenarioSchema` は `config` を `unknown` として受け取り、`checkSimScenario` がフォルダー名の `<sim>` で形を選んで検査します。
- `toggles` の `set` は共通の形（最上位の項目 1 つ）にし、値の形は `config` のスキーマで検査します。入れ子の項目を変える書き方（パス）は作りません。入れ子を変えたいときは、その最上位の項目をまるごと書き直します。
- `expect` の形は、エンジンが持つ出力の項目の一覧（`OUTPUT_KEYS[op]`。項目の名前と、文字列・数・真偽・配列の種類）で検査します。`expect` に書いた項目だけを比べる（部分一致）ので、書く人は、そのシナリオで大事な項目だけを書けます。一覧にない項目の名前はエラーです。

### 3.4 `expect` とエンジンの結果の一致

`checkSimScenario` が、次の順に検査します。どれもエラーです。

1. 共通の項目のスキーマ（3.2）と、`config` の形（3.3）
2. `config` と、各 toggle を当てた設定を、エンジンで実行する。エンジンが入力のエラーを返したら止める（シナリオの設定が、エンジンの扱う範囲の外にある）
3. `expect.initial` と最初の設定の結果、`expect.toggles.<id>` とその toggle の結果を、書いた項目ごとに比べる（配列は順も含めて等しいこと）。食い違いは、シナリオ・実行（最初か toggle の id）・項目・期待した値・エンジンの値を出す（`sim-expect`）
4. `predict.key` が出力の項目の一覧にあり、その種類が文字列・数・真偽のどれかで、`choices` の `value` がどれもその種類と同じ。`value` のうち、最初の設定の結果と等しいものがちょうど 1 つ（`sim-predict`）。0 個なら正解がない。ほかの `value` は、エンジンが出しうる値かどうかを問わない
5. 差し込み（3.5）が解決できる。規則の裏づけがシナリオの `factRefs`・`lessonRefs` に入っている（`sim-rule-ref`）

規則の表そのものの検査（`sim-rule-fact`。3.5）はシナリオごとではなく、シミュレーターごとに 1 回行います。

この検査は、次の段で走ります。

| 段 | 何をするか | 止めるもの |
|---|---|---|
| `npm run validate`（ルート） | すべてのシナリオに `checkSimScenario`。検証状態にかかわらず、全部を検査する | エラー 1 つ以上で失敗（今の validate と同じ）。CI と公開の手順は最初に validate を回すので、ここで止まる |
| アプリのビルド（`app/scripts/build-content.mjs`） | 出すシナリオも除くシナリオも、同じ `checkSimScenario` で検査する | エラー 1 つ以上でビルドを止める（図・実物の検査のエラーと同じ扱い） |
| エンジンの単体テスト（`app` の Vitest） | エンジンの関数そのもの（境界の値、重なり、分割など） | テストの失敗 |

設計書の「一致しなければビルドを止める」は、上の 2 段で満たします。`npm run dev`（`--include-unverified`）でも同じ検査をかけるので、開発中に `expect` を誤ると、その場でわかります。シナリオのすべてを Vitest でも回す案は採りません（validate と同じ検査を 2 か所に持つことになるため）。

`expect` をわざと違えたシナリオで止まることは、validate の検査のテスト（`scripts/` のテストの見本のデータ）で確かめます。

### 3.5 規則の表と、文への差し込み

各エンジンは規則の表（`RULES`）を持ちます。

```js
export const RULES = {
  'size-range': { label: 'VPC とサブネットの大きさ', value: { min: 16, max: 28 }, text: '/16〜/28', factRef: 'vpc.cidr-size', evidence: ['/16', '/28'] },
  reserved: { label: 'サブネットで予約されるアドレス', value: { head: 4, tail: 1 }, text: '先頭の 4 つと最後の 1 つ（合わせて 5 つ）', factRef: 'vpc.subnet-reserved-ips', evidence: ['先頭の 4 つと最後の 1 つ', '5 つ'] },
  'address-math': { label: 'アドレスの数の計算', lessonRef: 'lesson-basics-ip-subnet-routing' },
};
```

- 規則は、図鑑の事実（`factRef`）かレッスン（`lessonRef`）のどちらかで裏づけます。数値を持つ規則（`value` がある）は、`factRef` が要ります。
- `evidence` は、事実の本文にそのまま含まれるはずの文字列です。validate は、`factRef` の事実が存在し、本文に `evidence` のすべてが含まれることを確かめます（`sim-rule-fact`。エラー）。事実の本文が変わって数値が合わなくなったとき、エンジンの数値の古さに気づくためです。事実の実効の状態が `verified` でないときは警告にします（`sim-rule-fact-unverified`）。図鑑の作業では、直した事実を置いてから検証し直すまでのあいだにも validate を回すので、エラーにすると図鑑の作業が止まるためです（図と実物の `factRefs` も、存在だけをエラーで確かめている）。
- エンジンは、実行の結果に、その実行で使った規則の id の一覧（`rules`）を入れます。シナリオの `factRefs`・`lessonRefs` は、最初の設定と全 toggle の実行で使った規則の裏づけをすべて含みます（`sim-rule-ref`）。
- シナリオの文（`intro`・`predict.text`・`explain`）に規則の数値を書くときは、`{{rule:<規則の id>}}` と書き、表の `text` に置き換えます。結果の値は `{{out:<出力の項目>}}` と書き、その実行（`explain.initial` は最初の設定、`explain.toggles.<id>` はその toggle）の結果に置き換えます。知らない id・項目はエラーです。置き換えはアプリのビルドが行い、アプリは置き換え済みの文を表示します。規則の差し込みは、図鑑のその事実へのリンク（`#/services/<entry>?f=<スラッグ>`）にします。ただし、その事実を図鑑が表示しない状態（`needs-fix`・`rejected`。エントリごと出さない場合を含む）のときは、リンクにせず文字だけにします（開くと事実が見つからないリンクを作らないため）。未検証の事実は図鑑に「未検証」の札つきで出るので、リンクにします。
- `{{out:…}}` の書式: 数は 3 桁ごとに「,」で区切ります（`65,536`）。アドレスと CIDR の文字列はそのまま出します。決まった語の中から選ぶ文字列（`sizeIssue` など）、真偽、配列の項目は差し込めず、エラーです（画面の語は結果の表示の部品が決めるため）。差し込める項目は、エンジンの出力の項目の一覧（`OUTPUT_KEYS`）に種類（`number`・`address`）として書きます。その実行の結果にない項目（範囲の外で出さない `usable` など）を差し込むのもエラーです。`intro` と `predict.text` には `{{out:…}}` を書けません（予想の前に答えが見えるため）。
- `intro` の状況の値（「10.0.0.0/28 のサブネット」など、`config` に書いた入力）は、そのまま書いてかまいません。選択肢の `text` も、結果の値（「11 個」）をそのまま書きます（`value` との一致は 3.4 の 4 で検査する）。
- シナリオの文に規則の数値をそのまま書いていないかは、機械では確かめません（入力の値と区別できないため）。検証役が、公式の資料と照らすときに確かめます。

## 4. 画面

### 4.1 ルートと一覧

| ルート | 画面 |
|---|---|
| `/sims` | シミュレーターの一覧。シナリオが 1 件以上出ているシミュレーターだけを、名前・学ぶこと（1 文）・シナリオの数で並べる |
| `/sims/:sim` | 出すシナリオが 1 件以上あるときだけ開ける（6.1）。そのシミュレーターの説明、扱わないこと（開いた一覧）、シナリオの一覧（題、未検証の札、実行したことがあれば「実行済み」と前回の予想の当たり外れ）、自由に試す（4.4） |
| `/sims/:sim/:id` | シナリオの実行（4.2） |

- 存在しないシミュレーター・シナリオと、ビルドで除いたシナリオの id は「見つかりません」と、シナリオがないか検証が済んでいないことを出します（図・実物と同じ）。
- 学習コースのユニットにシミュレーターを並べるのは、この枠の実装には含めません（コースの項目の種類が足されたあとの作業）。

### 4.2 流れ（`/sims/:sim/:id`）

1 つの縦の列に、段を上から順に開いていきます。画面を切り替えず、前の段は残します（読み返せるように）。

1. **状況**: 題、未検証の札、`intro`、最初の設定の表（「項目: 値」の縦並び。シミュレーターごとの部品が描く）。下に「このシミュレーターが扱わないこと」を閉じた `<details>` で出す
2. **予想**: `predict.text` と選択肢のボタン（その場の確認と同じ見た目）。選ぶまで「実行する」は押せない。選んだ選択肢は印を付け、選び直せる
3. **実行**: 「実行する」で、エンジンが最初の設定を計算する。結果の段（シミュレーターごとの部品）を開き、予想の当たり外れ（「予想どおり」「予想と違う」と、正しい選択肢）を出す。フォーカスは結果の見出しへ移し、結果の要約は `aria-live` で読ませる
4. **理由**: `explain.initial`（差し込み済み）。規則の差し込みは図鑑へのリンク。下に裏づけ（レッスン・図鑑の事実へのリンク）
5. **1 か所変えて、もう一度**: toggle のボタン（`label`）を並べる。押すと、変えた設定を「項目: 前の値 → 新しい値」で示し、その設定の結果と `explain.toggles.<id>` を出す。結果は、最初の設定の結果と並べて比べられるようにする（幅が狭いときは縦に重ねる）。toggle は何度でも押し直せ、「最初の設定に戻す」で 5 の段を閉じる。toggle では予想を求めない（流れを短く保つため。予想するのは最初の 1 回）

「最初からやり直す」で、予想を消して 1 に戻します。開き直したときに、前の予想は出しません（その場の確認と同じ）。

### 4.3 幅 360px での見せ方

- 1 列だけにし、横にスクロールしません。設定と結果の表は「項目: 値」の縦並びにします（実物の表と同じ考え方）。
- 結果の図（数直線の帯など）は、幅いっぱいに描き、ラベルは帯の上下に逃がします。文字は 12px より小さくしません。
- ボタンは指で押せる大きさ（高さ 44px 以上）にし、選択肢と toggle は 1 行に 1 つ並べます（幅 600px 以上では折り返して並べる）。
- 明るい背景と暗い背景の両方で、CSS の変数の色を使います。当たり外れは色だけで示さず、文字（「予想どおり」）と印を付けます。

### 4.4 自由に試す

`/sims/:sim` の下に、シミュレーターごとの操作（Sim3 ではプレフィックス長のスライダーなど）を置きます。シナリオと違い、`expect` と `explain` はなく、結果だけを出します。入力は各エンジンの入力の検査を通し、扱わない入力（Sim3 の IPv6 など）は、扱わないことの文を出して計算しません。自由に試した結果は記録しません。

### 4.5 扱わないこと

- 各エンジンが `NOT_COVERED`（1〜6 個の文。それぞれ 10〜80 字）を持ち、validate が個数と字数を検査します。シミュレーターの性質なので、シナリオごとには書きません。
- `/sims/:sim` では開いた一覧、シナリオの実行の画面では「状況」の下の閉じた `<details>`、自由に試すで扱わない入力を入れたときは、その入力に当たる 1 文を、出します。
- 文は「〜は扱いません」の形にし、扱わない理由が試験に関わるとき（「実際は〜も確かめられます」）は、図鑑やレッスンへのリンクを添えます。

## 5. 記録（`sim-run`）

```ts
interface SimRunEvent extends EventBase {
  type: 'sim-run';
  sim: string;        // シミュレーターの id
  scenarioId: string;
  run: string;        // 'initial' か toggle の id
  choice?: number;    // 選んだ予想（1 から）。run が 'initial' のときだけ
  correct?: boolean;  // 予想が当たったか。run が 'initial' のときだけ
}
```

- 「実行する」を押したときと、toggle を押したときに 1 件ずつ記録します。同じ toggle を押し直したときも記録します（回数は使わず、実行したかどうかだけを使う）。
- 使い道は、`/sims/:sim` の「実行済み」と前回の当たり外れの表示と、あとで作る学習コースの進み具合（「最初の設定を 1 回実行した」で済み、とする案）です。合格準備度、復習の予定、弱点分析には使いません。
- `choice` の意味は、選択肢の並びが変わると変わります。正誤は `correct` を正とし、`choice` は参考にとどめます（その場の確認の `check-answer` と同じ）。今のシナリオにない `scenarioId` と toggle の id の記録は、表示に使いません。
- 書き出し・読み込み・同期は、ほかのイベントと同じに扱います（`isEventLike` の範囲で、知らないイベントの種類を落とさない今の仕組みのまま）。

## 6. 検証状態

- `material-status.json` の区分の名前は `sims` にします（置き場所のフォルダー名とルートに合わせる）。鍵はシナリオの id（`sim-<sim>-…`）です。シミュレーター（エンジン）そのものは記録しません。エンジンの誤りは、`expect` との一致とエンジンの単体テストで見つけます。
- ハッシュは、検証役が見る範囲の全部から作ります。シナリオの画面には、シナリオに書いた欄だけでなく、エンジンの出力の全部（予約の 5 つのアドレスと用途、範囲の最初と最後など。`expect` は部分一致なので、書いていない項目も画面に出る）、規則の表の文、扱わないことの文が出るためです。シナリオの欄だけから作ると、エンジンや規則の表を変えて表示が変わっても、検証済みのシナリオが検証済みのままになります。ハッシュの元は、次の 4 つをまとめたオブジェクトです。
  1. `createdBy` を除く、シナリオの全部の欄
  2. 最初の設定と、全部の toggle のエンジンの結果の全部（`rules` を含む）
  3. それらの実行で使った規則の、表の項目（`label`・`value`・`text`・`factRef`・`lessonRef`・`evidence`）
  4. そのシミュレーターの `NOT_COVERED`
- このオブジェクトは `scripts/lib/sim.mjs` の 1 つの関数（`simHashSubject`）で組み立て、`materialHash('sims', …)` に渡します（作り方は図・実物と同じ、キー順をそろえた JSON の SHA-256 の先頭 12 桁）。validate、アプリのビルド、検証の記録の道具が同じ関数を使います。表示の変わらない作り直し（エンジンの中の書き方を変えただけなど）ではハッシュは変わらず、表示が変わる変更では未検証に戻ります。`expect` の部分一致の検査（3.4）は、書いた人とエンジンの突き合わせとして、これとは別に残します。
- アプリのビルドは、既定では検証済みのシナリオだけを出し、`--include-unverified` のときだけ未検証のシナリオを「未検証」の札つきで出します。`needs-fix`・`rejected` はどちらでも出しません。除くシナリオにも検査はすべてかけます（3.4）。除いた数を状態ごとに出力に表示し、`manifest.json` の `counts.sims`・`counts.simsExcluded` に書きます。
- 「検証済みなのにどこからも参照されていない」の警告は、シナリオには出しません。シナリオはレッスンの本文からではなく、`/sims` と学習コースから開くためです（`MATERIAL_SECTIONS` に、参照の警告を出さない印を足す）。
- 本文（レッスン・早見表・ガイド）からシナリオを指す記法は作りません。本文に `#/sims/...` へのふつうのリンクを書くのはかまいませんが、validate はその参照を数えません。

### 6.1 検証済みのシナリオが 0 件のあいだ

- 公開のビルドにシナリオが 1 件もないあいだは、メニューに「シミュレーター」を出しません。`/sims` を直接開くと「表示できるシミュレーターはまだありません」と出します（図・実物の一覧と同じ）。
- 出すシナリオが 0 件のシミュレーターは、`/sims/:sim`（「自由に試す」を含む）も開けず、同じく「まだありません」と出します。検証済みのシナリオが 1 件もないのに、エンジンの結果だけが公開のビルドに出る道を作らないためです。
- 開発用のビルド（`--include-unverified`）では、未検証のシナリオがあればメニューに出し、シナリオには「未検証」の札を付けます。
- メニューと横のナビ（幅の広い画面）に出すかどうかは、出すシナリオが 1 件以上あるかで決めます。件数は manifest の `counts.sims` で見ます（ミニラボ・設計パターンと同じ仕組み。manifest が読めないあいだは出さない）。

## 7. ビルドの出力と遅延読み込み

- アプリのビルドは、シナリオごとに、差し込みを済ませた文と設定を `sims/<id>`（manifest のキーは `sim:<id>`）に、一覧を `sim-index`（シミュレーターごとの id・名前・学ぶこと・扱わないこと、シナリオの id・題・状態）に書きます。オフラインで使えるよう、ほかのデータと同じく事前にキャッシュします。
- 結果はアプリがエンジンで計算します（toggle と自由に試すで計算が要るため）。ビルドの出力に結果を入れないので、表示とビルドの検査は同じエンジンの同じ結果を見ます。
- `SimsPage` は遅延読み込みのページにします。エンジンとシミュレーターごとの部品は、シナリオの実行と自由に試すの画面だけが読み込む別のチャンクにします（`app/src/sims/<sim>/` を `lazy` で読み、その中でエンジンを読む）。
- 初期表示の JS（gzip 250 KB の目安）は、実装の前と後で `vite build` の出力の初期チャンクの大きさを比べて確かめます。増えるのは、ルートとメニューの数行だけのはずです。エンジンが初期チャンクに入っていないことは、ビルドの出力のチャンクの一覧で確かめます。

## 8. 決めたこと（設計者の案。利用者は未確認）

- エンジンは `scripts/lib/sims/` に置き、validate とアプリの両方から使う（2 章。設計書 13 章の当初の置き場所は `app/src/sims/`）。
- `expect` の一致は、validate とアプリのビルドの両方で検査し、どちらもエラーで止める（3.4）。
- 規則の数値はエンジンの規則の表に置き、図鑑の事実の本文に `evidence` が含まれることを検査する。シナリオの文には差し込みで出す（3.5）。
- toggle は最上位の項目を 1 つだけ変え、toggle では予想を求めない（3.2、4.2）。
- 検証状態の区分は `sims`。参照されていない警告は出さない。検証済みが 0 件のあいだはメニューに出さない（6 章）。
- `sim-run` は実行と toggle ごとに 1 件。予想は最初の実行だけ（5 章）。
- 検証状態のハッシュは、シナリオの欄に、エンジンの結果の全部、使った規則の表の項目、扱わないことの文を加えたものから作る（6 章）。
- `sim-rule-fact` は、事実がない・`evidence` がないをエラー、事実が検証済みでないを警告にする（3.5）。
- 出すシナリオが 0 件のシミュレーターは、`/sims/:sim` も開けない（6.1）。
- 規則の数値を文にそのまま書くことは機械では止めず、差し込みを書き方の規則にする（3.5）。
- 予想の誤答の選択肢には、エンジンが出さない値も使える（3.2）。
