# 問題・レッスンの作成基準

SAA Dojo のコンテンツ（問題、レッスン、フラッシュカード、用語集、早見表、ガイド）を作るときの基準です。形式は `scripts/lib/schema.mjs` が正で、`npm run validate` で検査します。サービス図鑑は 12 章を参照してください。教材の体系、学習コース、網羅の基準は `docs/learning-design.md`、これから足す形式（図、実物を読む、ミニラボ、設計パターン、シミュレーター）の設計は `docs/visual-materials-design.md` にあります。どちらも未実装を含み、実装が済んだ形式からこの文書に移します。例題は `content/saa-c03/questions/*/*/saa-*-ex-*.json` と `content/saa-c03/lessons/d4/lesson-4.1-s3-storage-classes.md` を参照してください。

## 1. 出題範囲と項目 ID

- 出題範囲は `content/saa-c03/blueprint.json` です。4ドメイン・14タスクの「知識（K）」「スキル（S）」の項目に ID（例 `1.1-K3`、`3.4-S2`）があり、問題の `knowledgeRefs` にはそのタスクの項目 ID を1〜4個入れます。
- 基礎講座（AWS 未経験者向け）の項目は `basics-K1`〜`basics-K14` です。
- `services` はサービス台帳（`content/saa-c03/services.json`）の正規名（`name`）で書きます（例 `Amazon S3`、`AWS Key Management Service (AWS KMS)`）。台帳の別名（例 `Amazon Simple Storage Service`）で書くと、validate が表記ごとにまとめて警告します（ビルドは正規名にそろえて出力します）。対象外サービスは誤答の選択肢には使えますが、正解にはしません。

## 3. 問題の項目

| 項目 | 内容 |
|---|---|
| `exam` | `SAA-C03` |
| `domain` / `taskStatement` | タスクの番号（基礎講座は 0 / `basics`） |
| `qualifier` | 問題文の制約語が最優先しているもの。`cost` コスト、`operational` 運用負荷、`availability` 可用性・耐障害性、`performance` 性能、`security` セキュリティ、`minimal-change` 変更最小、`other` |
| `difficulty` | 1〜3（7章） |
| `type` / `selectCount` | `single` は選択肢4つで正解1つ。`multiple` は選択肢5つで正解2つ（まれに6つで3つ） |
| `stem` | 問題文。日本語で150〜350字 |
| `options` | `id` は a から順。`correct` と、その選択肢がなぜ正しい／誤りなのかを書く `rationale` |
| `explanation` | 正解の理由を仕組みで説明する総合解説 |
| `keyPoints` | 他の問題にも使える判断のコツ（1〜5個） |
| `references` | AWS 公式の実在 URL（1〜4個） |
| `lessonRefs` | 関連レッスンの ID |
| `factRefs` | 任意。決め手になる図鑑の事実の ID（最大6個）。既存の問題には、その問題を直す機会に書き足す |
| `pool` | `basics` 基礎講座、`practice` 演習、`mockA`・`mockB` 保留模試（演習には出ない） |
| `needsSourceCheck` | 公式ドキュメントで確認しきれなかった事実を含むとき `true` |

## 4. 問題文の作り方

1. AWS 公式ドキュメントで確かめた事実を出発点にし、独自のシナリオを作ります。
2. 会社や状況、満たすべき要件、制約（予算、期限、既存システム、規制など）を書き、最後に問いを置きます。
3. 正解を決める制約語をはっきり書きます。例:「最もコスト効率が高い」「運用上のオーバーヘッドが最も少ない」「既存アプリケーションの変更を最小限に」「高可用性」「最小権限」。
4. 文体はです・ます調。サービス名は英語の正式名（例 Amazon S3、AWS Lambda）。
5. 改名されたサービスは新しい名前を使い、解説の初出で旧称を併記します。例: Amazon Data Firehose（旧称 Amazon Kinesis Data Firehose）、AWS IAM Identity Center（旧称 AWS Single Sign-On）。

## 5. 選択肢

- 正解は1つ（`multiple` は `selectCount` 個）に決まるようにします。
- 誤答は「もっともらしいが、要件を1点だけ満たさない設計」にし、`rationale` でどの要件を満たさないかを書きます。
- アプリが選択肢をシャッフルするので、記号や位置で他の選択肢を指さない（「A と B」「上記の」「前者」などは使わない）。
- 正解だけが長い・詳しいといった偏りを作らない。「すべて正しい」「いずれでもない」は使わない。

## 6. 正確さ・最新性・独自性

- 2026年時点の仕様で書きます。提供終了や新規受付停止のサービスは正解にしません。既定値が変わった機能は、その既定値に依存する問題を作りません。
- 数値（上限、料金、日数など）は、公式ドキュメントで確認できた安定した値だけを使います。
- 公式のサンプル問題、他の出版社や講座の問題集、流出した試験問題を写したり言い換えたりしません。特徴的な言い回しも再利用しません。

### 6.1 最新性の注意（2026年11月時点）

- **正解にしない**（提供終了・新規受付停止）: Amazon Kinesis Data Analytics for SQL Applications、AWS App Mesh、EC2-Classic、EC2 Auto Scaling の起動設定（Launch Configuration。新しいアカウントでは作成できないので起動テンプレートを使う）、Amazon S3 Select、Amazon S3 Object Lambda、Amazon Glacier の独立サービス（ボールトと旧 API。S3 Glacier の各ストレージクラスは引き続き使える）、AWS WAF Classic、Amazon Aurora Serverless v1、AWS CloudTrail Lake、Amazon SNS のメッセージデータ保護、AWS Directory Service の Simple AD、Amazon FSx File Gateway、AWS Data Pipeline、AWS Proton、AWS Application Discovery Service。
- **AWS Snowball Edge**: 2025年11月から新規顧客の受付が止まっています。用途はレッスンやフラッシュカードで扱ってよいですが、問題の正解にする場合は解説で必ずこの点に触れます。
- **AWS Firewall Manager**: 置き換えていく別のサービスとして AWS Network Security Manager が出ています（改名ではなく別のサービスです。Firewall Manager の販売と提供の終了の日付は、2026年11月時点で発表されていません）。試験ガイドの範囲内のサービスの一覧は AWS Firewall Manager を載せているので、教材は Firewall Manager の名前のまま書き、問題の正解にしてかまいません。終了の日付が発表されたら、扱いを見直します。
- **AWS Application Migration Service**: 今の公式のページでの名前は AWS Transform MGN（旧称 AWS Application Migration Service）です。試験ガイドの範囲内のサービスの一覧は AWS Application Migration Service の名前で載せているので、教材はこの名前のまま書き、初出に今の公式の名前を併記します。
- **Amazon Quick と Amazon QuickSight**: 今の公式のページでの名前は AWS Quick と、Quick の中の機能の AWS Quick Sight（Amazon QuickSight から発展したもの）です。試験ガイドの範囲内のサービスの一覧は Amazon Quick の名前で載せているので、教材は台帳の名前（Amazon Quick、Amazon QuickSight）のまま書き、初出に今の公式の名前を併記します。
- **新旧の名前を併記する**: Amazon Data Firehose（旧称 Amazon Kinesis Data Firehose）、Amazon Managed Service for Apache Flink（旧称 Amazon Kinesis Data Analytics for Apache Flink）、Aurora Serverless v2 は「Aurora serverless」に改称、Aurora Global Database の計画的切り替え（Switchover）と障害時のフェイルオーバー（Failover）の区別、EventBridge のカスタムイベントバス（従来型の classic と新しい enhanced）。
- **既定値に依存する問題を作らない**: S3 の既定の暗号化（SSE-S3）、新しいバケットのブロックパブリックアクセスと ACL 無効化、S3 ライフサイクルで128 KB未満のオブジェクトを移行しない既定動作、Amazon Linux 2023 の IMDSv2 必須、STS のリージョンエンドポイントの扱い、RDS 延長サポートへの自動加入。

## 7. 難易度

| 難易度 | 目安 | 割合 |
|---|---|---|
| 1 | 1つのサービスの基本的な事実を短い状況に当てはめる | 20% |
| 2 | 本番と同程度。1〜2個の制約のもとで、もっともらしい2〜3案を比べる | 50% |
| 3 | 複数の制約、紛らわしい違い（例 CloudFront と Global Accelerator、ゲートウェイ型とインターフェイス型の VPC エンドポイント）、長めのシナリオ | 30% |

`multiple` は全体の約20%にします。保留模試（`mockA`・`mockB`）は難易度2〜3の本番レベルにし、演習問題と内容を重複させません。

## 8. 解説・要点・出典

- `explanation` は「なぜ正しいか」を仕組みで説明し、よく比べられる選択肢との違いにも触れます。
- `keyPoints` には再利用できるコツを書きます。例:「運用負荷を最小に → マネージドサービスやサーバーレスを優先」。
- `references` は docs.aws.amazon.com、aws.amazon.com、d1.awsstatic.com の実在するページだけです。推測で深いリンクを作らず、ユーザーガイドの概要ページや FAQ を優先します。

## 9. 網羅

- blueprint の各項目に、時間をかけて2問以上を用意します。
- 対象サービスはすべて、問題かフラッシュカードで1回以上扱います。
- `npm run coverage` で不足を確認できます。

## 10. レッスン

- front matter（YAML）: `id`、`title`、`domain`、`taskStatement`、`order`、`knowledgeRefs`、`services`、`estimatedMinutes`、`createdBy`。
- AWS を触ったことがない人でも読める構成にします: 基礎 → 使い分け → 設計パターン → 試験のポイント → ひっかけ注意 → 確認問題。
- 2,000〜5,000字。比較は表にします。
- 囲み記事は引用記法で書きます: `> **試験のポイント**`、`> **ひっかけ注意**`。

## 11. フラッシュカード・用語集・早見表・ガイド

- フラッシュカード: `{ "deck", "title", "createdBy", "cards": [{ "id", "front", "back", "taskStatements", "services", "tags" }] }`。表は問い、裏は短い答えと理由。
- 用語集: `{ "createdBy", "entries": [{ "term", "en", "definition", "services", "related" }] }`。
- 早見表・ガイド: Markdown。front matter は `id`、`title`、`order`、`taskStatements`、`services`、`createdBy`。

## 12. サービス図鑑

サービスを引いて、機能・制約・数値・似たサービスとの違いを確かめる辞書です。機能単位の知識（事実）の正本になります。設計の詳細は `docs/service-catalog-design.md` です。

- **エントリ**は台帳の1サービスにつき1ファイルです。台帳で `hostedBy` を持つサービス（例 EC2 スポットインスタンス）はエントリを作らず、親のエントリ（EC2）の事実として書きます。
- **区分**: 1 主要（core の事実 12〜30 件、比較 1 件以上）、2 標準（同 4〜12 件）、3 概要（`summary` と決め手だけ。事実 0〜2 件）。区分 1・2 は `chooseWhen` と `avoidWhen` を書きます。目安から外れると validate が警告します。
- **事実**は1件に1つだけ書き、それだけで意味が通るようにします（40〜400字）。1 エントリの事実は 60 件までです。`kind` は `feature`（機能）・`constraint`（制約・できないこと）・`quota`（数値）・`pricing`（料金の仕組み）・`integration`（連携）です。
  - 出典（`sources`）には実際に開いた AWS 公式のページを入れ、`checkedAt` を確かめた日にします。出典で確かめられないことは書きません。
  - `depth` は、試験の水準なら `core`、試験より細かい可能性があれば `detail`（アプリでは「発展」として折りたたむ）です。
  - 「できないこと」は、試験で誤答の決め手になるものだけを `constraint` にします。数値は試験で問われるものに絞り、Service Quotas で引き上げられるかも書きます。
  - 料金の金額は書きません（仕組みだけ）。既定値に依存する内容は「〜の時点の既定値」と書き、決め手にしません。提供終了のサービス・機能は「新規には選ばない」とだけ書きます（6.1）。
  - **確かめ直す周期**: 事実は、`checkedAt` から半年（180 日）ごとに出典で確かめ直します。既定値に依存する内容と、提供終了に関わる内容は 3 か月（90 日）ごとで、その事実に `recheck` を付けます。値は `default-value`（AWS が決めている既定値・既定の動作に依存する）か `end-of-life`（提供終了、新規受付の停止、サポートの終了、後継への置き換えに関わる）です。両方に当たるときは `end-of-life` にします。周期を過ぎた事実は、validate が警告し、coverage の再確認リストに出ます。
  - 一度公開した事実の ID は変えず、消した ID も再利用しません。
- **文体**は常体です（「〜する」「〜できる」「〜である」。体言止めも使えます）。事実の `text`・`examPoint`・`trap`、エントリの `summary`・`chooseWhen`・`avoidWhen`、比較の文が対象です。レッスン・解説・早見表など、ほかの教材は「です・ます」のままです。
- **他のエントリの事実**は書き写さず、`seeAlso` で ID を指します。比較は組ごとに1ファイルにし、既存の早見表と重なる組は `docRef` で早見表を指すだけにします。
- **本文からのリンク**: レッスン・早見表・ガイドの本文に `[S3 アクセスポイント](#/services/s3?f=access-points)` と書けます。存在しない ID は validate のエラーです。
- **保留模試の答えを写さない**: 監査で見つかった不足（`catalog-needs.json`）は、どの粒度の知識が要るかの見本として使い、事実は機能の一般的な説明として書きます。問題の状況や選択肢の言い回しを写しません。
- **検証状態**は `content/saa-c03/catalog-status.json` に、エントリ・事実・比較ごとに `status`・`checkedAt`・`hash` で記録します。記録したあとに内容が変わると、検証し直すまで未検証として扱います。

## 13. 検証状態

`content/saa-c03/review-status.json` に問題ごとの状態（`verified`、`pending`、`needs-fix`、`rejected`）と確認日を記録します。アプリは `needs-fix` と `rejected` の問題を出さず、記録のない問題は `pending`（未検証）として扱います。図鑑の検証状態は 12 章のとおり別のファイルに、図・実物・ミニラボ・設計パターン・シミュレーターのシナリオの検証状態は 16・18〜21 章のとおり `material-status.json` に記録します。

## 14. コマンド

```bash
npm ci
npm run validate   # 形式の検査（エラーがあれば失敗）

```

## 15. 学習コース

前提知識の順に教材を並べる 1 つのデータです（`content/saa-c03/course.json`）。教材そのものは持たず、今ある教材の ID を指すだけです。考え方とユニットの割り当ては `docs/learning-design.md` の 5 章と付録 A にあります。形式は `scripts/lib/course.mjs` が正です。

- **形**: `stages`（ステージ 0〜4 を順に）→ `units`（`id` は `u00` から出現順に増える。`title`）→ `items`（ユニットの中の順）。ステージは `id`・`title`・`goal` を持ちます。
- **項目の種類**（`kind`）: `lesson`（`ref` にレッスンの ID）、`lab`（`ref` にミニラボの ID）、`doc`（`ref` に早見表かガイドの ID）、`pattern`（`ref` に設計パターンの ID）、`sim`（`ref` にシミュレーターのシナリオの ID。シミュレーターそのものではなく、検証状態を持つシナリオを指す）、`practice`（ユニット演習）、`drill`（判断軸ドリル）、`analysis`（弱点分析）、`mock`（`mock` に `random`・`mockA`・`mockB`）。どれも短い補足 `note`（60 字まで）を付けられます。
- **並べ方**: レッスン → ミニラボ → 早見表・ガイド → 設計パターン → シミュレーター → ユニット演習の順にします（画面は `course.json` の順に並べます。崩れていると validate が警告します。判断軸ドリル・弱点分析・模擬試験の位置は見ません）。ユニット演習は、そのユニットのレッスンの `knowledgeRefs` と重なる問題（`pool` が `practice` か `basics`）から出ます。保留模試（`mockA`・`mockB`）の問題は入りません。
- **まだない教材は書きません**: 図は、教材ができたときに種類を足してから項目に加えます（存在しない ID はエラーになるため）。
- **検証済みでないミニラボ・設計パターン・シナリオ**: 項目に書けますが、validate が警告します。公開のビルドでは、検証済みでない項目をユニットの画面から省きます（開発用のビルドでは未検証の項目も出します。要修正・却下はどちらでも省きます）。ミニラボは front matter の `unit` と同じユニットに入れます（違うと警告）。シナリオは、設計パターンと同じく複数のユニットに入れてかまいません。
- **validate のエラー**: スキーマ違反、ステージの順の誤り、ユニットの ID の重複と順の誤り、同じユニットの中の項目の重複、存在しないレッスン・ミニラボ・早見表・ガイド・設計パターン・シナリオ、2 つ以上のユニットに入るレッスン、どのユニットにも入らないレッスン、レッスンのないユニット演習、候補が 0 問のユニット演習（要修正・却下の問題を除いて数える）。早見表・ガイド・設計パターン・シナリオは、複数のユニットに入れてかまいません（例: ステージ 4 の総ざらい）。
- **validate の警告**: 検証済みでないミニラボ・設計パターン・シナリオを指す（`course-material-unverified`）、ミニラボの `unit` と入れたユニットが違う（`course-lab-unit`）、並べ方の崩れ（`course-item-order`）。「ミニラボのないユニット」（`course-no-lab`）は、今は警告しません。ミニラボの量産が始まったら有効にします（`scripts/lib/course.mjs` の定数を変える、コードの変更が要ります）。

## 16. 図

図は宣言的なデータで書き、アプリが SVG で描きます（座標は書きません）。記法（入れ物・部品・線の形と色）、構成図の書き方と段階表示、レイアウトの規則の詳細は `docs/visual-materials-design.md` の 2〜5 章です。AWS の公式アイコンは使いません。

- **置き場所**: 1 枚 1 ファイル。`content/saa-c03/diagrams/<id>.json`。ID は `dg-<英小文字とハイフン>`（ファイル名と同じ）。
- **共通の項目**: `id`、`type`、`title`（4〜60 字）、`alt`（代替文。40〜600 字。80 字未満は警告。図を見なくても同じ内容がわかるように書く）、`lessonRefs`・`factRefs`（裏づけ。合わせて 1 つ以上）、`createdBy`。
- **新しい事実を持ち込まない**: 図に描く内容（部品とつながり、選択の行き先と結論、順位、時間、担当）は、`lessonRefs` のレッスンの本文か、`factRefs` の図鑑の事実で裏づけます。数値は図鑑の事実を指し、料金の金額は書きません（高低は「高い・安い」などの段階で示す）。
- **なくても読める**: 図が表示されなくても、本文だけで意味が通るようにします。
- **幅 360px で読める**: レイアウトした幅が 328（設計の単位）を超えるとエラーです。部品の短い名前は台帳の `short`、なければ正規名から「Amazon」「AWS」を除いたものです。
- **重なり（構成図）**: 線のラベル・状態の札・段階の番号と、入れ物のラベルの位置は、レイアウトが重ならないように選びます（設計書 4.2.1）。選べなかったときは validate が警告します。`diagram-overlap` は、線か矢じりが入れ物のラベルを横切る（すぐそばを通る）、線が入れ物の枠に沿って走る、線が関係のない部品の上を通る。`diagram-crowded` は、札が部品の文字やラベルに重なる、線のラベルを入れ物の枠が横切る、線のラベルや番号が矢じりに重なる、置き場所がない。直し方は、入れ物と線のラベルを短くする（入れ物のラベルが長いと、中の部品へ上から入る線を避ける場所がなくなる）、並べる向きを替える、部品を分けて図を分ける、です。番号が入れ物の枠に乗るのも `diagram-crowded` です（札と番号は、段階ごとに同時に見えるものどうしだけを調べます）。まっすぐな線はレイアウトが付け替えず、`fromSide`・`toSide` を書いた線は辺を替えない（ポートをずらすだけ）ので、ラベルとの重なりが残りやすくなります。線が札の下を通るのは検査しないので、目で確かめます。警告が 0 でも、描いた図を幅 360px で目で確かめます。

| `type` | 名前 | 主な項目と上限 |
|---|---|---|
| `architecture` | 構成図 | `root`（入れ物 `box` と部品 `node` の木）、`edges`、`steps`（段階表示）。部品 14、入れ子 5、線 16、段階 8。詳細は設計書の 2.2〜2.5、4.2、5 章 |

- 表で足りる比較は、今までどおり Markdown の表で書きます。
- **本文からの参照**: レッスン・早見表・ガイドの本文に、1 行で `![キャプション](#/diagrams/dg-vpc-three-tier)` と書くと、その位置に図が出ます。前後を空行で区切り、画像だけの段落にします（前の行に文が続くと 1 つの段落になり、表示は図ではなくリンクにするので、アプリのビルドが止めます）。図・実物へのリンクの中に図・実物の画像は書けません（validate のエラー）。構成図は `?step=<番号>` で、その段階に止めた図を出せます。存在しない図と、段階の数を超える `step` は validate のエラーです。タイトルつき（`![キャプション](#/diagrams/<id> "題")`）も同じ扱いです。参照形式（`![キャプション][ref]` と `[ref]: #/diagrams/<id>`）は使えません（validate のエラー）。コードフェンスとインラインコードの中の参照は数えません。丸括弧のタイトル、2 段以上の入れ子の角括弧、4 字下げのコードの中など、validate と表示で読み方がずれる書き方は、アプリのビルドが止めます（下の 17 章の突き合わせと同じ）。
- **検証状態**: `content/saa-c03/material-status.json` の区分 `diagrams` に、図ごとに `status`（`verified`・`pending`・`needs-fix`・`rejected`）・`checkedAt`・`hash` を記録します（`{ "diagrams": { "dg-…": { … } } }`。知らない区分はエラー）。`hash` は、`createdBy` を除く全部の欄に、レイアウトした結果（scene）を足したものから作り（`scripts/lib/diagram.mjs` の `diagramHashSubject` を `scripts/lib/material-status.mjs` の `materialHash` に渡す）、記録したあとに内容（裏づけの `lessonRefs`・`factRefs` を含む）か、レイアウトの結果（レイアウトの規則や台帳の短い名前を変えたとき）が変わると、検証し直すまで未検証として扱います。記録のない図も未検証です。色や縁取りのように描画だけを変えたときはハッシュが変わらないので、変わる図の一覧を PR に書き、検証し直します。
  - アプリの公開のビルドには、検証済みの図だけが入ります。未検証の図は開発用のビルド（`npm run dev`）でだけ、「未検証」の札つきで出ます。`needs-fix`・`rejected` の図はどちらにも出ません。
  - 図が出ないときは、図だけを省いて本文を出します（文の途中の画像とリンクの形の参照はリンクのまま残り、開くと「見つかりません」になります）。本文が検証済みでない図を指すと validate が警告します（止めはしない）。既存のレッスンに図を差し込むのは、その図が検証済みになってからです（設計書 11.2）。
  - validate のエラー: スキーマ違反、存在しない図の id の記録。警告: 記録したあとに内容が変わった図、検証済みなのにどこからも参照されていない図、本文が検証済みでない図を指す。

## 17. その場の確認

レッスンの節の終わりに置く小問です。レッスンの Markdown の中に、囲み記事として書きます。

```markdown
> **その場の確認**
> パブリック IP アドレスを持つインスタンスが、インターネットゲートウェイへのルートがないサブネットにあります。このインスタンスはインターネットと通信できますか？
>
> - [ ] 通信できる
> - [x] 通信できない
>
> サブネットがパブリックかどうかは、ルートテーブルで決まります。パブリック IP アドレスがあっても、ルートがなければ届きません。
```

- 問いは 120 字まで。選択肢は 2〜4 個（`- [ ]`。`* [ ]` でも書ける）、正解（`- [x]`）は 1 個。選択肢の後ろの段落が理由で、必須です。形が違うと validate のエラーです。
- 選択肢は続けて書きます。選択肢の間に `>` だけの空行や別の行を入れるとエラーです。
- 見出しは `> **その場の確認**` だけの行にします。`**その場の確認：**` のようにコロンを付けたり、同じ行に問いを続けたりするとエラーです。
- 前の引用（囲み記事など）とは空行（半角の空白とタブだけの行。全角の空白だけの行は空行になりません）で分けます。見出しの直前から空行までに `>` で始まる行があると、前の引用とつながって確認として表示されないので、エラーです（`>` のない継続の行を挟んでも同じ）。
- 確認の行は、見出しの行と同じ字下げで書きます（リストの中なら、すべての `>` の前に同じ数の空白）。字下げが違うとエラーです。
- 選択肢に図・実物・画像と、図や実物へのリンクは書けません（表示は選択肢を文字だけにするため）。問いを 2 段落以上に分けた場合も、問いは文字だけになるので、図は書けません。理由と 1 段落の問いに文と一緒に書いた図は、図ではなく「図: …」のリンクで表示します（理由が図だけなら図として描きます）。図そのものを見せたいときは、確認の外（直後の本文）に置きます。
- タスクリスト（`- [ ]`・`- [x]`）を引用の中に書くのは、その場の確認の選択肢だけにします。
- 同じ文書の中で、同じ問いの文を 2 回使うとエラーです（記録の `checkId` が問いの文から決まるため）。問いの文を直すと `checkId` が変わり、前の回答の記録とはつながらなくなります。
- 記法の例を本文に載せるときは、情報文字列 `markdown`（か `md`）を付けたコードフェンス（```` ```markdown ````）で囲みます（フェンスの中は確認として読みません）。フェンスは、開きと同じ記号で、同じ数以上の行で閉じます。文書の終わりまで閉じていないフェンスと、`markdown`・`md` 以外のフェンスの中にあるその場の確認の見出しは、アプリのビルドが止めます（閉じ忘れで確認がコードになり、正解の印と理由が文字のまま見えるため）。この 2 つは validate では出ず、`npm run content`（`npm run build`）で出ます。
- 確認の理由のすぐ後に、空行を挟まずに囲み記事（`> **試験のポイント**`・`> **ひっかけ注意**`）を続けるとエラーです（囲み記事が理由の中に入り、選ぶまで隠れるため）。囲み記事の見出しは、表示と同じく「行の先頭の強調の中の文字」で見分けます（後ろに文が続いても、強調の中に別の強調があっても見出しです）。
- validate の検査は行単位で、表示（Markdown の解析）と細部が違います。アプリのビルド（`cd app && npm run content`、`npm run build`）は、本文ごとに表示と同じ解析をして、次のときに文書名と行を出して止まります。validate が通した確認が表示で確認にならない（4 字下げ、HTML の直後、前の引用とのつながりなど）、確認の引用が理由のあとも続く、確認にならない引用の中にタスクリストがある、確認の外に「その場の確認」の見出しに見えるものがある（`###` などの見出しと、段落の先頭の強調。文の途中の強調は止めません）、validate と表示で図や実物の参照の読み方が違う（丸括弧のタイトル、2 段の入れ子の角括弧、引用の中の定義など）。
- その節の本文に書いてあることだけを問います。本番形式の問題（シナリオと制約語）にはしません。
- 1 レッスンに 3〜6 個が目安です（1〜2 個のレッスンは警告）。
- アプリは選ぶまで正解と理由を隠し、回答を記録します。記録は合格準備度と復習の予定には使いません。

## 18. 実物

コンソールの画面の代わりに、設定そのもの（ポリシー、ルートテーブル、ルールの一覧、レコードなど）を注目点つきで読む教材です。設計は `docs/visual-materials-design.md` の 6 章、形式の正本は `scripts/lib/schema.mjs` の `ArtifactSchema` と `ARTIFACT_LIMITS` です。

- **置き場所**: 1 件 1 ファイル。`content/saa-c03/artifacts/<id>.json`。ID は `ar-<英小文字とハイフン>`（ファイル名と同じ）。
- **項目**: `id`、`kind`（設計書 6.3 の 22 種類。例 `bucket-policy`、`sg-rules`、`dns-records`）、`title`（4〜60 字）、`format`、本体、`notes`、`ask`（任意）、`lessonRefs`・`factRefs`（裏づけ。合わせて 1 つ以上）、`createdBy`。
- **format と本体**:

| `format` | 本体 | 注目点の場所 | 上限 |
|---|---|---|---|
| `json` | `document`（設定の JSON。オブジェクト） | `path`（`Statement[0].Condition` のように、キーを `.` でつなぎ、配列は `[番号]`） | 整形して 40 行・入れ子 6 段まで。整形した 1 行は字下げを含めて 120 字まで。数字だけのキーは書けない（読み込むと並びが変わり、書いた順に表示できない） |
| `table` | `columns`（列名）と `rows`（行ごとのセルの配列。セルの数は列と同じ） | `row`（1 から数える行の番号） | 列 2〜4（列名 16 字）、行 1〜12、セル 40 字 |
| `text` | `lines`（行の配列。字下げは先頭の半角の空白） | `lines`（1 から数える行の番号の配列） | 1〜30 行、1 行 80 字。字下げは 12 字まで。タブは書けない |

- **注目点**（`notes`）: `{ <場所>, text }`。2〜5 個が目安で、6 個以上はエラー、1 個以下は警告です。文は 10〜120 字。`format` と違う種類の場所（`json` に `row` など）を書くとエラーです。`.` や `[` `]` を含むキーは `path` で指せません。`path` の配列の番号は `0` か、0 で始まらない数字で書きます（`[01]` は形の違い）。注目点は、指す場所の上から順に並べます（番号が本体の上から 1・2・3 になる）。入れ子で重なる範囲（`Statement[0]` と、その中の `Statement[0].Condition` など）を別々の注目点で指すと、どこまでがどちらか見分けにくいので避けます。`text` で飛び飛びの行を指すと、連続した行の塊ごとに、先頭の行へ同じ番号が付きます。
- **問い**（`ask`）: `{ text, answer }`。読んだあとに設定の結果を 1 つ問います（問い 10〜120 字、答え 10〜200 字）。アプリは「答えを見る」で答えを開き、回答は記録しません。
- **新しい事実を持ち込まない**: 本体・注目点・問いの答えに書く値や動きは、`lessonRefs` のレッスンの本文か、`factRefs` の図鑑の事実（検証済みのもの）で裏づけます。料金の金額は書きません。提供終了のサービスは使いません。
- **例に使う名前**は実在しないものにします（`example-bucket`、`example.com`、`111122223333`、`o-exampleorgid`、`sg-0123456789abcdef0` など、公式ドキュメントの例と同じ流儀）。
- **本文からの参照**: レッスン・早見表・ガイドの本文に、1 行で `![キャプション](#/artifacts/<id>)` と書くと、その位置に実物が出ます。扱いは図（16 章）と同じです（存在しない ID・参照形式はエラー、タイトルつきは同じ扱い、コードの中は数えない、文の途中の参照はリンク、読み方のずれはアプリのビルドが止める）。実物には段階がないので、`?step=` などを付けるとエラーです。
- **検証状態**: `material-status.json` の区分 `artifacts` に、図と同じ形で記録します（`hash` は `createdBy` を除く全部の欄）。公開のビルドには検証済みの実物だけが入り、未検証の実物は開発用のビルドでだけ「未検証」の札つきで出ます。`needs-fix`・`rejected` はどちらにも出ません。validate のエラー: スキーマ違反、存在しない実物の id の記録。警告: 記録したあとに内容が変わった実物、検証済みなのにどこからも参照されていない実物、本文が検証済みでない実物を指す。
- **validate のエラー**（実物そのもの）: スキーマ違反（上限を含む）、ID の重複、ファイル名と ID の不一致、裏づけが 0、存在しないレッスン・事実、`format` と本体・場所の不一致、存在しない場所を指す注目点、整形した `document` の行数・入れ子・1 行の字数の上限、`document` の数字だけのキー、`text` の字下げの上限とタブ。

## 19. ミニラボ

AWS アカウントでのハンズオンの代わりに、何をどの順に作るか、部品がどうつながるか、1 か所違うと何が起きるか、何に料金がかかり続けるかを、読んで追う教材です。設計は `docs/visual-materials-design.md` の 8 章、形式の正本は `scripts/lib/schema.mjs` の `LabFrontSchema` と `scripts/lib/lab-pattern.mjs`（`LAB_SECTIONS`・`LAB_LIMITS`）です。見本は `content/saa-c03/labs/lab-vpc-from-scratch.md` です。

- **置き場所**: 1 つ 1 ファイル。`content/saa-c03/labs/<id>.md`。ID は `lab-<英小文字とハイフン>`（ファイル名と同じ）。
- **front matter**: `id`、`title`、`unit`（学習コースのユニットの ID。`course.json` にあるもの）、`order`（一覧の並び。ユニット → `order` → `id` の順に並ぶ）、`knowledgeRefs`（1〜20 個）、`services`（台帳の正規名。1〜20 個）、`estimatedMinutes`（10〜25）、`diagram`（構成が育つ図の ID）、`createdBy`。
- **`diagram`**: 段階表示（`steps`）のある構成図にします。段階の `reveal` で、手順ごとに部品を足して見せます（例 `dg-vpc-build-up`）。
- **節**: 見出し（`##`）は次の 7 つだけを、この順に書きます。最初の見出しより前に短い前置きを書いてもかまいません。

| 節 | 書くこと |
|---|---|
| `## ゴール` | 何を作るか。完成した構成図（`diagram` の全体）と、満たす要件 |
| `## 手順` | `### 1. …` から番号順に。1 手ごとに、作るもの・設定する値、なぜそうするか、その時点の図（`![…](#/diagrams/<diagram>?step=<番号>)`）、必要なら実物 |
| `## 動作を確かめる` | 通信や処理が通る経路を、段階表示で追う |
| `## 壊してみる` | 2〜3 個。設定を 1 か所変えたら何が起きるかを、その場の確認（17 章）で予想させてから理由を示す |
| `## 料金がかかり続けるもの` | 止めても料金がかかるもの、使った分だけのもの。金額は書かない |
| `## 試験での出方` | この構成が問題文でどう書かれるか、どの制約語で何が変わるか |
| `## 確認問題` | 関連する演習問題の ID（レッスンの確認問題と同じ書き方。アプリは本文の問題 ID に「解く」ボタンを付ける） |

- **書き方**: 手順は 5〜9 手で、1 手に 1 つのことだけを作ります。「なぜそうするか」を必ず書きます。設定の値は「項目と値」で書きます（例「ルートテーブル: 送信先 0.0.0.0/0、ターゲット インターネットゲートウェイ」）。画面の場所やボタンの名前は書きません。
- **新しい事実を持ち込まない**: 手順の値、なぜそうするか、壊したときの結果、料金の仕組みは、既存のレッスンの本文か、図鑑の検証済みの事実で裏づけます（図・実物と同じ）。料金の金額は書きません。
- **本文の図・実物・その場の確認**: レッスンと同じ書き方で、同じ検査がかかります（16〜18 章）。その場の確認の回答は記録しません（表示だけ）。
- **validate のエラー**: front matter のスキーマ違反、ファイル名と ID の不一致、ID の重複、固定の見出しの欠け・重複・順の違い、一覧にない `##` 見出し、手順の `###` が `### <番号>. <題>` の形でない・番号が 1 から順でない・1 つもない、`diagram` の図がない・構成図でない・段階がない、`unit` が学習コースにない（`course.json` が読めないときも）、`knowledgeRefs` が blueprint にない。アプリのビルドは、見出しの読み方が表示（remark の解析）と違うとき（setext の見出し、4 字下げなど）も止めます。
- **validate の警告**: 手順が 5〜9 手の外（`lab-steps`）、`## 壊してみる` のその場の確認が 2〜3 個の外（`lab-breaks`）、`diagram` の図の段階（`?step=1` 以上）を指す参照のない手順（`lab-step-diagram`）、本文の字数（空白を除いて数える）が 1,500〜5,000 字の外（`lab-length`）。
- **検証状態**: `material-status.json` の区分 `labs` に、図と同じ形で記録します。`hash` は `createdBy` を除く front matter と本文から作ります（本文を直すと未検証に戻る）。公開のビルドには検証済みのミニラボだけが入り、未検証のものは開発用のビルドでだけ「未検証」の札つきで出ます。`needs-fix`・`rejected` はどちらにも出ません。検証済みでないミニラボの本文が検証済みでない図や実物を指しても、警告は出しません（ミニラボそのものが公開されないため）。validate のエラー: 存在しない id の記録（`material-status-key`）。警告: 記録したあとに内容が変わった（`material-stale-review`）。検証済みのミニラボの `diagram` が検証済みでない図を指すと、validate は警告（`diagram-ref-unverified`）を出し、既定のビルドはそのミニラボを出しません（学習コースのユニットからも省き、件数の行に「図が未検証」と出ます）。図の検証を先に済ませます。エラーにしないのは、検証済みの図も内容を変えると未検証に戻るためです（エラーにすると、図を検証し直すまで validate が通らず、ほかの作業が止まる）。本文の中の図・実物の参照の扱いは、レッスンと同じです。

## 20. 設計パターン

試験によく出る典型の構成を、1 つずつ引ける形にまとめた辞書です。レッスンの「設計パターン」の節の内容を、制約の足し引きと誤答の構成まで含めてまとめます（レッスンの本文は消しません。パターンからレッスンを指します）。設計は `docs/visual-materials-design.md` の 9 章、形式の正本は `PatternFrontSchema` と `scripts/lib/lab-pattern.mjs`（`PATTERN_SECTIONS`・`PATTERN_LIMITS`）です。一覧の候補は `docs/learning-design.md` の付録 B、見本は `content/saa-c03/patterns/pattern-sns-sqs-fanout.md` です。

- **置き場所**: 1 つ 1 ファイル。`content/saa-c03/patterns/<id>.md`。ID は `pattern-<英小文字とハイフン>`（ファイル名と同じ）。
- **front matter**: `id`、`title`、`order`（一覧の並び。`order` → `id` の順に並ぶ）、`taskStatements`（1〜6 個）、`knowledgeRefs`（1〜20 個）、`services`（1〜20 個）、`qualifiers`（このパターンが選ばれる判断軸。1〜3 個）、`diagram`（段階表示のある構成図の ID）、`createdBy`。
- **`qualifiers`**: 問題の `qualifier`（3 章）と同じ語彙から `other` を除いたもの（`cost`、`operational`、`availability`、`performance`、`security`、`minimal-change`）。アプリの一覧は、この判断軸・タスク・サービスで絞れます。
- **節**: 見出し（`##`）は次の 6 つだけを、この順に書きます。

| 節 | 書くこと |
|---|---|
| `## 解く課題` | どんな状況と要件のときに使うか（2〜3 文） |
| `## 構成` | 構成図（`diagram`）と、部品ごとの役割 |
| `## 選ばれる決め手` | 判断軸ごとに 1 行の表（例: 運用の負荷 → サーバーを管理しない）。`qualifiers` と合わせる |
| `## 制約が変わると` | 表（制約 → 構成のどこを変えるか）。例:「順序を保ちたい → FIFO キューにする」 |
| `## ひっかけ` | よく似た誤答の構成と、外す要件 |
| `## 関連` | レッスン、早見表、図鑑の事実と比較、ミニラボ、確認問題の ID |

- **字数**: 600〜1,500 字（空白を除いて数える）。外れると警告（`pattern-length`）です。
- **新しい事実を持ち込まない**: ミニラボと同じです。
- **validate のエラー**: front matter のスキーマ違反（`qualifiers` の重複を含む）、ファイル名と ID の不一致、ID の重複、固定の見出しの欠け・重複・順の違い、一覧にない `##` 見出し、`diagram` の図がない・構成図でない・段階がない、`taskStatements`・`knowledgeRefs` が blueprint にない。見出しの読み方のずれはアプリのビルドが止めます（ミニラボと同じ）。
- **検証状態**: 区分 `patterns` に記録します。扱いはミニラボと同じです。

## 21. シミュレーターのシナリオ

値を変えて結果を見る教材（シミュレーター）の、シナリオのデータです。設計は `docs/sims-design.md`（共通の枠）と、シミュレーターごとの設計書（CIDR とサブネットは `docs/sim-cidr-design.md`）、形式の正本は `scripts/lib/schema.mjs` の `SimScenarioSchema` と `SIM_CONFIG_SCHEMAS`、検査は `scripts/lib/sim.mjs` です。計算はシミュレーターごとのエンジン（`scripts/lib/sims/<シミュレーター>.mjs`）が行います。

- **置き場所**: 1 件 1 ファイル。`content/saa-c03/sims/<シミュレーター>/<id>.json`。ID は `sim-<シミュレーター>-<英小文字・数字・ハイフン>`（ファイル名と同じ。`<シミュレーター>` はフォルダー名と同じ）。今のシミュレーターは `cidr`（CIDR とサブネット）だけです。
- **項目**: `id`、`title`（4〜60 字）、`intro`（状況。20〜300 字）、`predict`（予想の問い）、`config`（最初の設定）、`toggles`（1 か所だけ変えた設定）、`expect`（エンジンの結果の期待値）、`explain`（理由）、`factRefs`・`lessonRefs`（裏づけ。合わせて 1 つ以上）、`createdBy`（作成者 ID。2 章と同じ形）。`intro`・`predict.text`・`explain` は 1 段落のインラインの Markdown で書きます（見出し・箇条書き・空行は書けない）。
- **予想**（`predict`）: `{ text（10〜120 字）, key, choices }`。`key` は最初の設定の結果の項目の名前（文字列・数・真偽の項目だけ）、`choices` は 2〜4 個の `{ text（1〜40 字）, value }` です。`value` は `key` の項目と同じ種類にし、最初の設定の結果と等しいものがちょうど 1 つになるようにします（それが正解）。ほかの `value` は、エンジンが出さない値でもかまいません（よくある誤解を誤答の選択肢にするため）。`value` が重なるとエラーです。
- **設定**（`config`）: シミュレーターごとの形で、`op`（操作の種類）で分けます。CIDR とサブネットは `size`（大きさ）、`overlap`（重なり）、`split`（分割）の 3 つです（`docs/sim-cidr-design.md` 4 章）。重なりの操作でも 2 つの範囲の大きさを確かめ、作れない大きさなら、重なりの判定より先にそれを結果にします（`peering`・`subnets` が `size`）。
- **設定を変える**（`toggles`）: 1〜4 個の `{ id, label（2〜30 字）, set }`。`set` は `config` の最上位の項目をちょうど 1 つだけ書きます（`op` は変えられない。入れ子の項目を変えるときは、その最上位の項目をまるごと書く）。最初の設定と同じになる `set` はエラーです。
- **期待値**（`expect`）: `{ initial, toggles: { <toggle の id>: … } }`。それぞれ、エンジンの結果のうち、そのシナリオで大事な項目だけを書きます（書いた項目だけを比べる）。すべての toggle に要ります。エンジンの結果と 1 つでも食い違うと、validate とアプリのビルドが止まります。食い違いのメッセージは、シナリオ・実行（`initial` か toggle の id）・項目・期待した値・エンジンの値を出します。
- **理由**（`explain`）: `{ initial, toggles }`。それぞれ 20〜400 字（差し込みを展開する前の字数）。すべての toggle に要ります。
- **差し込み**: 規則の数値（VPC とサブネットの大きさの範囲、予約されるアドレスなど）は文にそのまま書かず、`{{rule:<規則の id>}}` と書きます。エンジンの規則の表の文に置き換わり、図鑑のその事実へのリンクになります（図鑑がその事実を表示しないときは文字だけ）。結果の値は `{{out:<項目>}}` と書きます。数は 3 桁ごとに「,」で区切り、アドレスと CIDR はそのまま出します。決まった語の中から選ぶ項目（`sizeIssue` など）、真偽、配列は差し込めません。その実行の結果にない項目、知らない規則と項目はエラーです。`intro` と `predict.text` には `{{out:…}}` を書けません（予想の前に答えが見えるため）。差し込みを展開するのは `intro`・`predict.text`・`explain` だけで、`title`・選択肢の `text`・toggle の `label` に `{{…}}` を書くとエラーです。状況の入力の値（「10.0.0.0/28 のサブネット」など）と、選択肢の文の結果の値（「11 個」）は、そのまま書きます。文に規則の数値をそのまま書いていないかは、機械では確かめず、検証のときに確かめます。
- **裏づけ**: エンジンは、実行ごとに使った規則を返します。最初の設定と全部の toggle で使った規則と、文に差し込んだ規則の裏づけ（図鑑の事実かレッスン）は、すべて `factRefs`・`lessonRefs` に入れます（足りないとエラー）。存在しない事実とレッスンもエラーです。理由に書くことは、裏づけのレッスンの本文か、図鑑の事実に書いてあることだけにします。
- **規則の表**（エンジンの側）: 数値を持つ規則は図鑑の事実を指し、事実の本文にそのまま含まれるはずの文字列（`evidence`）を持ちます。事実がない、本文に文字列がないのはエラー、事実が検証済みでないのは警告です。扱わないことの文（`NOT_COVERED`）は 1〜6 個、それぞれ 10〜80 字です。
- **検証状態**: `material-status.json` の区分 `sims` に、図と同じ形で記録します。`hash` は、`createdBy` を除くシナリオの全部の欄に、最初の設定と全部の toggle のエンジンの結果の全部、使った規則（文に差し込んだ規則を含む）の表の項目、扱わないことの文とそのリンク、シミュレーターの説明を加えたものから作ります（`scripts/lib/sim.mjs` の `simHashSubject`）。エンジンや規則の表を変えて画面の表示が変わると、検証し直すまで未検証に戻ります。画面の部品の決まった語（結果の見出しや判定の語）はハッシュに入らないので、事実に関わる言い方を変えたときは検証し直します。公開のビルドには検証済みのシナリオだけが入り、未検証のシナリオは開発用のビルドでだけ「未検証」の札つきで出ます。`needs-fix`・`rejected` はどちらにも出ません。「どこからも参照されていない」の警告は、シナリオには出しません。
- **validate のエラー**: スキーマ違反（上限を含む）、ID の重複、ファイル名・フォルダー名と ID の不一致、知らないシミュレーター、`config` と toggle を当てた設定の形の違い、エンジンが計算できない設定、`expect` の食い違い、予想の正解が 1 つでない・`value` の種類の違い・重なり、差し込みの誤り、規則の裏づけの不足、存在しない事実とレッスン、存在しないシナリオの検証状態の記録。
