# 学習設計書（SAA Dojo の全体設計）

SAA Dojo が「このアプリだけで合格できる」と言えるために、何を満たし、どう確かめるかを決める文書です。教材の書き方（`content-guide.md`）、アプリの仕様（`app-spec.md`）、図鑑の設計（`service-catalog-design.md`）、図解・操作型教材の設計（`visual-materials-design.md`）は、この文書の要件を受けて決めます。

- この文書と `visual-materials-design.md` は設計で、まだ実装していない内容を含みます。
- `content-guide.md` と `app-spec.md` には、実装が済んだ内容だけを書きます。実装のタスク（9章）が終わるたびに、該当する規則と仕様をそちらへ移します。
- 数値の目標のうち「仮」と書いたものは、試作と中間の監査の結果を見て決め直します。

## 1. 目標と学習者

### 1.1 目標

AWS に触れたことがない人が、このアプリだけで学び、AWS Certified Solutions Architect – Associate に合格することです。

- **使わないもの**: 講義動画、AWS アカウントでのハンズオン、他社の問題集や講座、公式の練習問題。
- **アプリの外で必要なもの**: 受験の申し込みだけです（手順は `guide-registration`）。解説の出典リンクは確認用で、開かなくても学べることを条件にします。
- **学習時間の目安**: 60〜80 時間（推測。内訳は入力 約 24 時間、演習と復習 約 27 時間、模試と見直し 約 15 時間）。利用者の学習記録で確かめて直します。

### 1.2 学習者

- IT の実務経験は問いません。ネットワーク、データベース、暗号の基礎は基礎講座で補います（今の基礎講座と同じ前提です）。
- 主にスマホで、5〜15 分の区切りで学びます。オフラインでも学べます。

### 1.3 目標にしないこと

- 実機を構築・運用する技能そのもの（試験が問う設計の判断に必要な範囲だけを扱います）
- コンソールの画面操作の手順（試験は画面操作を問わず、画面は変わります）
- 換算スコアの予測（根拠がないので、今と同じく表示しません）

## 3. 学習の流れ

1 つのユニットを、次の流れで学びます。どの段階にも、対応する教材と画面を用意します。

| 段階 | 学習者がすること | 教材 |
|---|---|---|
| 1. つかむ | なぜそれが要るのかを知り、全体像を図で見る | レッスンの冒頭（課題、たとえ、全体像の図） |
| 2. 仕組みを見る | 通信や処理の流れを 1 段ずつ追う | 段階表示の図解 |
| 3. 実物を読む | 設定そのものを読み、どこが効いているかを知る | 実物を読む |
| 4. その場で確かめる | 読んだ直後に小問に答える | その場の確認 |
| 5. 使い分ける | 似た候補から、制約に合うものを選ぶ | 選択フロー、位置づけ図、早見表、図鑑の比較 |
| 6. 組み立てる | 構成が 1 手ずつ育つのを追い、壊れ方を予想する | ミニラボ、シミュレーター |
| 7. 型を覚える | 典型の構成と、選ばれる決め手を覚える | 設計パターン |
| 8. 解く | 本番と同じ形式の問題を解く | 演習（ユニット演習、条件を選ぶ演習） |
| 9. 思い出す | 期限が来た概念を解き直す | 復習、暗記カード、判断軸ドリル |
| 10. 試す | 本番と同じ条件で通して解く | ランダム模試、保留模試 |

設計の根拠は次の 4 つです。

- 文章と図を組にすると、片方だけより覚えやすい（段階 1〜3）。
- 読み返すより、思い出す練習のほうが定着する（段階 4・9）。
- 手本を見てから自分で解く順にすると、初学者の負担が小さい（段階 6 → 8）。
- 間隔を空けて繰り返し、分野を混ぜて解くと、本番に近い形で使える（段階 9・10）。

## 4. 教材の体系

### 4.1 教材の種類

| 種類 | 単位 | 役割 | 状態 |
|---|---|---|---|
| レッスン | トピック | 通読して理解する。なぜその設計か | 既存（図解などを差し込む。L-2） |
| 問題 | 1 問 | 本番と同じ形式で、制約に合う設計を選ぶ | 既存 |
| 暗記カード | 問いと答え | 想起の練習 | 既存 |
| 用語集 | 用語 | 語の意味を短く確かめる | 既存 |
| 早見表 | テーマ | 横断の比較 | 既存（選択フロー・位置づけ図を足す） |
| ガイド | テーマ | 試験の進め方、受験の手続き | 既存 |
| 判断軸ドリル | 制約語 | 制約語から設計を素早く選ぶ | 既存 |
| 図鑑（エントリ・事実・比較） | サービスと事実 | 引いて確かめる。機能・制約・数値の正本 | 制作中（第1波まで） |
| 図 | 1 枚 | 構成、流れ、選び方、位置づけ、時間、層を見せる | 新設。ほかの教材に埋め込む部品 |
| 実物を読む | 1 つの設定 | 設定そのものを注目点つきで読む | 新設。部品 |
| その場の確認 | 1 問 | 読んだ直後に確かめる | 新設。レッスンの中に書く |
| ミニラボ | 1 つの構築 | 作る順番、つながり、壊れ方を追う | 新設 |
| 設計パターン | 1 つの典型構成 | 課題、構成図、決め手、変形、ひっかけ | 新設 |
| シミュレーター | 1 つの仕組み | 値を変えて結果を見る | 新設（アプリの機能とシナリオのデータ） |
| 学習コース | 全体 | 学ぶ順番を決める | 新設（データ 1 ファイル） |

新設の種類の形式は `visual-materials-design.md` で決めます。

### 4.2 正本の規則

図鑑の設計書 1.3・1.4 の考え方（正本は 1 か所）を、新しい種類にも広げます。

| 内容 | 正本 |
|---|---|
| 機能・制約・数値・料金の仕組み | 図鑑の事実 |
| なぜその設計か、流れの説明 | レッスン |
| 典型の構成と決め手 | 設計パターン |
| 横断の比較 | 早見表（ある組）、図鑑の比較（ない組） |
| 作る順番と壊れ方 | ミニラボ |
| 語の意味 | 用語集 |

- **図・実物・ミニラボ・設計パターン・シミュレーターは、新しい事実を持ち込みません。** 描く内容・書く内容は、差し込み先のレッスンの本文か、図鑑の verified の事実で裏づけます。裏づけのない内容が要るときは、先に図鑑の事実を足します。
- 同じ図を複数の教材で使うときは、図を写さず、同じ図の ID を指します。

### 4.3 既存の教材の検証状態（【決定 L-11】）

問題と図鑑にしかなかった検証状態を、レッスン・早見表・カード・用語集にも持たせます。ここでは方針を決めます。形式の細部（区分 `lessons`・`cheatsheets`・`guides`・`flashcards`・`glossary`、鍵、ハッシュの範囲、札と注意の出し方）は、仕組みの実装（`visual-materials-design.md` の W6）で決め、`content-guide.md` の 13 章と `app-spec.md` に書きました。検証そのもの（何と照らすかの束と依頼文、記録）は、下の「順序」のとおり別に進めます。

| 教材 | 単位 | 鍵 | `needs-fix` のとき |
|---|---|---|---|
| レッスン（47 本） | 1 本 | レッスンの ID | 表示は続け、「修正待ち」の注意を出す（隠すとコースが切れるため） |
| 早見表（12）、ガイド（2） | 1 本 | 文書の ID | 同上 |
| 暗記カード（180 枚） | 1 枚 | カードの ID | 出さない（問題と同じ） |
| 用語集（172 語） | 1 語 | 用語（`term`） | 出さない |

- **記録**: 新しい教材と同じ `material-status.json` に、`status`・`checkedAt`・`hash` を書きます。記録したあとに内容が変わると、未検証に戻ります。記録のないものには「未検証」バッジを出します（今の問題と同じ見せ方）。ガイドは利用者の決定には入っていませんが、早見表と同じ仕組みで扱えるので、設計者の案として含めました。
- **確かめ方**（【決定 L-15】）: 図鑑の verified の事実と照らします。教材の記述が事実と食い違えば `fix` です。対応する事実が図鑑にない記述は、次の 2 つに分けます。検証役は、書いた系統とは別の系統のモデルにします（問題・図鑑と同じ）。
  - **試験に効く記述**（選択肢の正誤や使い分けの決め手になるもの。数値、上限、できる・できない、既定の動作、サービスの選び分け、だれの責任か）: AWS 公式のページで確かめ、正本の規則（4.2）に従って図鑑に事実を足してから `ok` にします。
  - **例示・呼び名・周辺の説明**（サービスの正式な名前や略称、「〜のような」で挙げる製品の名前、試験の決め手にならない補足）: 図鑑には足しません。確かめは、図鑑の事実の検証と同じやり方で、起草とは別の検証役が AWS 公式のページ（図鑑の出典と同じ、許されたドメイン。英語版を正とする）を開いて行い、URL と原文の引用を検証の出力に残せば `ok` です。引用は主張そのものを言っている文（30 字以上）にします。URL は言語のパスのない英語版のページにします。引用がそのページのテキスト（見出しやリンクの文字を含む）にそのまま含まれることは、道具がページを取得して確かめます。
  - 迷うものは試験に効く記述として扱います。書いた側が例示・周辺と見立てても、本文を事実と照らす検証役か、公式のページで確かめる検証役のどちらかが試験に効くと見たら、試験に効く記述に戻します。公式のページで確かめられない記述は、どちらでも `fix`（本文を直すか外す）です。
  - 記録の条件: 食い違いが 0、事実のない試験に効く記述が 0、例示・周辺の記述はどれも URL と引用がある。同じ内容への検証が最後の回まで `ok` のときだけ記録します。
- **順序**: 図鑑が verified になった分野から、コースの順（ステージ 1 から）に進めます。レッスンは、図解などの差し込み（F3）と同じ回に検証します（差し込みで本文が変わるたびに未検証へ戻るのを避けるため）。先に、図鑑の検証で見つかっている修正待ち 18 件（ops の `catalog/material-fixes.md`）を反映します。
- **合格準備度**: 変えません（7.3）。未検証の教材も、今と同じく読めます。

### 7.2 独立問題セット（【決定 L-10】）

保留模試も図鑑も同じ工程で作っているので、同じ見落としを共有している可能性があります。外部の問題を使わずにこれを確かめるために、別系統のモデルで作った問題のセットを 1 つ持ちます。

- **作り方**: 別系統のモデル（Codex）が、公式の試験ガイド（blueprint）と AWS 公式ドキュメントだけを入力にして、65 問（配分は模試と同じ）を作ります。アプリの教材、既存の問題、図鑑は見せません。検証は通常の工程で行います。
- **使い道**: (1) 不足監査をかけ、アプリの教材が「別の作り手の問題」にも足りているかを測る（独立監査）。(2) 学習者の 3 本目の保留模試にする（プール `mockC`）。
- **注意**: 独立監査で見つかった不足を埋めるときも、図鑑の設計書の【決定 U-6】と同じく、問題に合わせて書きません。

### 7.3 合格準備度

4 条件（`app-spec.md` 5章）は変えません。コースの進み具合と、6章の C3 の到達（学習者が開いた事実の割合ではなく、教材側の網羅）は、合格準備度には入れません。合格準備度は「解けるか」で測り、「読んだか」では測らないためです。

### 9.2 順序の決まり

- **図鑑の中間の監査が先**: 監査は「変わるのは教材の範囲（図鑑の事実）だけ」という条件で前後を比べます（ops の `audit/README.md`）。レッスンへの差し込みと書き足し（F3・F5）は、中間の監査の基準を取ったあとに始めます。F1・F2 は、既存のレッスンを変えない範囲（新しいフォルダと `app/`）で先に進められます。
- **書き込みは 1 つの作業ツリーに 1 セッション**（`AGENTS.md`）: 図・実物・ミニラボ・設計パターンは新しいフォルダの新しいファイルなので、図鑑の作業と並行できます。既存のレッスンに書き込む作業（差し込み、修正待ち 18 件の反映）は、同時に 1 つのセッションだけが行います。
- **図鑑との受け渡し**: 付録 C（比較の組）は、図鑑の第2波の比較の入力にします。レッスンから図鑑へのリンクと `factRefs` は、指す先の事実が verified になってから書きます。
- **不足監査の教材の範囲**: 図の代替文、段階の説明、実物の注目点、ミニラボ、設計パターンを、監査の教材の範囲に加えます（ops の `audit-prep.mjs` の変更）。シミュレーターは、シナリオの説明文だけを加えます。

### 9.3 上位モデルを使うところ

上位モデルを使える期間は限られるので、判断の質が効く仕事に絞ります。

1. 形式の確定（図のスキーマと、幅 360px での試作の評価）
2. 種類ごとの見本と、起草・検証の指示
3. 一覧の確定（付録 B〜D、レッスンごとの図の割り付け）
4. シミュレーターの設計メモ（どの規則を実装し、何を省くか）
5. 意見が分かれた項目の最終判定と、抜き取り検査

## 付録 D. つまずきの型（17 個。候補）

「なぜ動かないのか」「なぜ意図と違う動きになるのか」の型です。ミニラボの「壊してみる」、シミュレーターのシナリオ、問題のどれかで扱います（N5）。

1. EC2 インスタンスがインターネットへ出られない（ルート、パブリック IP、NAT、セキュリティグループ、ネットワーク ACL）
2. プライベートサブネットから S3 に届かない（NAT もエンドポイントもない、エンドポイントのポリシー）
3. セキュリティグループは許可しているのに、戻りの通信が落ちる（ネットワーク ACL はステートレス）
4. S3 でアクセスが拒否される（バケットポリシー、IAM、ブロックパブリックアクセス、KMS キーの権限）
5. 別アカウントのロールを引き受けられない（信頼ポリシー、権限、SCP）
6. 管理者の権限があるのに SCP で拒否される
7. VPC につないだ Lambda 関数が、インターネットや AWS の API に届かない
8. Lambda 関数がデータベースの接続数を使い切る
9. ALB のターゲットが異常と判定される（セキュリティグループ、ヘルスチェックの設定）
10. Auto Scaling の台数が増えすぎる、または増減を繰り返す（ウォームアップ、クールダウン）
11. SQS のメッセージが 2 回処理される、順序が入れ替わる（可視性タイムアウト、標準と FIFO）
12. CloudFront を通さずに S3 へ直接アクセスできてしまう（OAC）
13. 暗号化したスナップショットを、別のアカウントや別のリージョンで復元できない（KMS キーの共有、コピー先のキー）
14. VPC ピアリングで通信できない（ルート、推移的な通信はできない、CIDR の重複）
15. Direct Connect の障害で接続が切れる（冗長化、VPN のバックアップ）
16. DynamoDB でスロットリングが起きる（パーティションキーの偏り、容量）
17. フェイルオーバーのあと、アプリケーションが古い接続先を使い続ける（エンドポイント、DNS のキャッシュ）
